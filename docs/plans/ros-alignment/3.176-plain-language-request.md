# 3.176 A find asked in plain words: the target, how it looks and a room hint

*`PLAN-ros-alignment.md` section 3.176; index: [README.md](README.md).*

**Why.** (the user, 2026-11-12: features of similar products and projects worth
building while the Rover waits on Waveshare.) The hobby project closest to this
one (Zero-Shot-VLN-ROS2) puts a language model in front of the search: it turns
what the person typed into a goal the detector and the navigator can use. Here
the target text goes to the detector as typed. Three known costs:

* a multi-word target once blinded the label gates (3.76 L1);
* a person who knows the room ("my water bottle, probably in the kitchen")
  cannot say so, while the `rooms` goal policy has a slot for exactly that
  (3.96's room prior; 3.116 measured what labels are worth);
* with 3.160's names, "in the kitchen" can name a room on the saved map.

**Scope.**
* One step at mission start: the request becomes `{target, detector prompts,
  attributes, room hint}`. The target stays what the identity check is asked;
  the hint only orders where explore looks, and never ends a search early.
* **A free rule-based parser first** (a room named after "in", "near", "by";
  colour and size words): no model, works offline (3.49).
* A model arm second (the cloud, or the local VLM if it can), behind a config
  key, off by default, one call per mission, bounded like `/room`. Its
  evaluation costs money, so it waits on the user's go with an estimate.
* The twin's Find box takes the sentence and shows what was understood before
  Start, so a wrong reading is caught by the person.

**Criteria (written in step A, before building; CLAUDE.md section 7).** At
least:
* on a written set of requests (pinned before measuring; hints right, wrong and
  absent): the parser's target and room exact-match rates, with bars;
* in the simulator with a right hint: median goals and seconds against no hint
  (progress), finds held; with a **wrong** hint: finds within a bar of no hint
  and a bound on the seconds lost (stability);
* a plain one-word target behaves exactly as today (0 differences);
* offline: the rule arm works with every connection refused;
* phone-size evidence of the understood-request line.

## 3.176.A: criteria and design (written 2026-11-13, before any parser exists)

**What `dev` does today** (read, not measured). `POST /mission/start` takes
`target_object` as typed; the detector, the found rule (the simulator's
substring match) and arrival's identity check all read that one string.
`target_room` already exists and is a different thing: a mission whose goal
is to reach that room. **A hint is therefore a new field, `room_hint`, never
`target_room`**: a hint orders where explore looks and can never end a
mission. Rooms reach explore's goal choice only through the `rooms` policy
(`explore_goal_policy: rooms`, the default since 3.125): each goal's room type
comes from a room-label layer (3.160.D's person's names on the saved map, or
`find_room_labels`), and `RoomGoalPolicy` reads `prior[target][type]`, a type
the target's prior does not name reading as unknown (3.96, 3.116).

### The design

**One parse, at the twin, before Start; the brain runs what the person saw.**
* `brain/request.py` `parse(text, names=()) -> Request`: `target` (the
  identity check's words, or None when no single object was named),
  `detector_prompts` (in B: `[target]`, so perception is unchanged; `[]`
  with no target), `attributes` (`colours`, `size`), `room_hint`
  (`{"type": t}`, `{"name": n}` or None) and `unused` (the words it read past,
  shown so a wrong reading is seen). Pure Python, no model, no I/O (3.49).
* A read-only brain route, `POST /mission/request/parse {text}`, parses
  against the names stored for the current saved map (3.160's store, the
  pose's `frame_id`; none without one). No robot call, no paid call.
* `POST /mission/start` gains `room_hint` (validated against the same
  vocabulary and the stored names; 422 otherwise) and `request` (the
  sentence, recorded only). The twin's Find box (C) shows the reading, lets
  the person drop the room, and starts with exactly the `target_object` and
  `room_hint` shown, plus the sentence. A start with no `room_hint` runs
  `dev`'s mission: `request` changes nothing but the record.
* The sentence is kept in the mission's status and report beside what was
  understood, for the record.

**Where the hint acts: the room prior, nowhere else.** With a hint the
`rooms` policy reads the target's own prior with the hinted room's rate set
to 1.0 (a type: `prior[target][type] = 1.0`; a person's name: that name's
cells read as their own type, rate 1.0). This keeps the policy in the inputs
it was trained on (`garbage bag` is exactly this shape: kitchen 1.0, others
0), and it can only reorder goals:
* no room-label layer (no names, `find_room_labels` off) or the `rule`
  policy: the hint is inert, reported in the status as not applied and why;
* the asks decision (`find_room_labels`' flat-prior skip, 3.116 amendment 7)
  stays on the target's own prior: **a hint never adds a paid call**;
* the hinted room searched and empty: explore goes on as without a hint (the
  mission ends only as `dev`'s can).

**The room vocabulary** (closed; a word outside it is not a room, and is
never guessed into one). Canonical types, then the words read as each:

| Type | Words |
|---|---|
| kitchen | kitchen, kitchenette |
| living room | living room, lounge, family room, sitting room, den |
| bedroom | bedroom, master bedroom, guest room, spare room, nursery |
| bathroom | bathroom, restroom, washroom, powder room, loo |
| dining room | dining room, dining area |
| office | office, home office, study |
| laundry room | laundry room, laundry, utility room |
| garage | garage |
| hallway | hallway, hall, corridor, entryway, foyer |

The first four are the shipped prior's (ProcTHOR's) types; the other five
carry a hint only through a layer that names them (a person's names, a cloud
label). **A person's name on the saved map wins over a type**, matched whole
and without case ("the den" on a map with a room named "Den" is that room,
not "living room").

**What the set encodes** (the rules B's parser is scored against, not code):
* The target is the object phrase in lower case, without a request verb
  ("find", "look for", "where is", "have you seen", "I lost", ...), leading
  determiners and owners ("my", "the", "Ben's"), or end punctuation. Colour and
  size words stay in it ("small black wallet"), and are also read as
  attributes (canonical: `grey` for "gray"; `small` for "little", "tiny";
  `large` for "big", "huge").
* The target ends at the first of: a location phrase ("in", "on", "near",
  "by", "under", "behind", "next to", "beside", "inside"); a comma, dash,
  parenthesis or sentence end (".", "?", "!"); a verb after it ("is", "are":
  "my glasses are in the bedroom"); a place word ("upstairs", "downstairs",
  "anywhere"); or a closing filler ("please", "for me"). "with" and "of" are
  not locations ("cup with a lid", "box of tissues").
* A room is a vocabulary word (or a person's name) in what follows the target,
  including inside a furniture phrase ("on the kitchen counter" -> kitchen).
  A room word inside the target names the thing, not a room ("kitchen
  scissors", "bathroom scale"). **"near", "by" or "next to" a room still names
  that room** ("the basketball near the bedroom" -> bedroom): a decision, not
  a reading of the words. The person is pointing at that part of the house;
  the hint only orders goals, so a thing just outside the room costs the
  bounded detour S5 measures, while dropping the hint loses what the person
  knew.
* **Never a guess:** two rooms ("kitchen or living room"), a negation ("not in
  the kitchen"), a misspelling ("kitchn"), or a room outside the vocabulary
  and the names ("playroom", "basement", "upstairs") give no hint.
* **No object, or two, gives no target** ("find it in the kitchen", "check
  the bedroom"; two things joined by "and" or "or": "my keys and my phone",
  "the remote or the charger"; colour words joined by "and" are one object:
  "black and white sneakers"). The room is still read and shown. The twin
  keeps Start off and the brain refuses a start whose `target_object` is
  empty or blank (422, as a missing one is today): one search finds one
  thing, a room alone is `target_room`'s mission, and an empty target would
  match every label in the simulator's substring rule.
* **A room the house lacks** is read as said (the parser does not know the
  house; the set's `absent_room` rows check it is not dropped). On the map it
  is inert: no labelled cell carries it, so no goal's score changes. The
  status reports how many labelled cells carry the hinted room so far
  (`hint_cells`), never "absent": the map is discovered, and a room not yet
  labelled looks the same.

### The request set (written and pinned now)

`evaluations/request-3176/requests.jsonl`: 152 hand-written sentences in 17
kinds (plain, request verb, question, attributes, the four prior types and
the others, synonyms, a hedge before the room, a room inside a furniture
phrase, a location that is not a room, a room word in the target, compound
targets, ambiguous or unknown rooms, case and punctuation, a person's names,
no target, two targets, a room the house lacks). Each row has `text`, the
map's `names` (empty for most), and `expect` (`target`, or null for none;
`room`; `colours`; `size`).

**The split rule** (mechanical, no judgement per row): within each kind, in
file order, the 1st, 3rd, 5th ... row is `dev` and the 2nd, 4th ... is
`test`. **dev 76** (B builds against it) and **test 76** (scored as below;
38 test rows carry a room). The rule was applied by the authoring script,
not chosen row by row, and no parser existed when it ran, so nothing could
be tuned to the test half; B must not edit the set (the pin). Rows added
later are appended, so an id always names the same sentence (r001-r138 are
the first round's). `tests/test_request_set_3176.py` pins its sha256 and its
shape (every expected room in the vocabulary or that row's names, both splits
covering every kind). A change to the set is an amendment written here first,
with the new hash.

### What this cannot show

The simulator's frames name every object, so B's sweeps measure where explore
looks, not what the detector sees: splitting the colour off the detector's
prompt (`detector_prompts`) needs real frames and is not in B. ProcTHOR has
only the four prior types, so the other five types and a person's own names
are scored by the parser bars and the live run only. The names in the sweep
are an oracle (3.160.D's ceiling), and a person's real wording is wider than
152 sentences: the set's misses are the parser's known gaps, not its error
rate in a home.

**Review** (`/code-review`, Sonnet, before any parser; all eight taken). The
fixes: P1's count (62 of 69 is under 90%: now 63); a test row with the room
before the target (r054, rewritten); the target's end rules written out (a
sentence end, a verb, a place word, a filler); the sentence recorded through
`request` without changing the mission; "near" a room written as a decision;
colours compared as a set. In the pin test, the said-words check now uses
whole words, and a new check guards "a name wins over a type".

**The orchestrator's round (2026-11-13, before any parser).** Three kinds
added (no target 6, two targets 4, a room the house lacks 4; set 138 -> 152,

Its review (`/code-review`, Sonnet; all nine taken): the null target's

**What the numbers say.** A right hint helps: one goal fewer at the median in
both modes, with mode U's reward interval above 0. That is short of S2's
goals bar by one goal in six. A wrong hint is expensive. At rate 1.0 the
policy sends the robot through the wrong room before anything else, and the
median search takes 1.6x as long (S5). Off is off (S6): with no hint, with
no labels and with a room no house has, every mission is `dev`'s.

**S7 traced** (2026-11-14, the three missions replayed in process on the
same harness; deterministic, identical to the sweep's rows). A frame is
counted as seeing the target when the simulator's own detections
(`GridWorld.frame_description()`) name it.

| Mission | Target, its room | Hint | Frames | In the target's room | Closest | Frames naming the target | Camera-seen points within 0.3 m of it | `none` |
|---|---|---|---|---|---|---|---|---|
| right 195 R | garbage can, bathroom | bathroom (right) | 136 | 21 | 0.84 m | **0** | 1 | found at 6 goals, first seen from 1.2 m |
| right 194 U | red backpack, kitchen | kitchen (right) | 72 | 30 | 0.66 m | **0** | 2 | found at 9 goals, seen from 1.6 m |
| wrong 247 R | house plant, kitchen | bedroom (wrong) | 97 | 37 | 1.5 m | **1** (frame 85, bearing -24 deg) | 3 | found at 3 goals |

**The cause.** In the two right-hint misses the robot stood in the target's
own room for 21 and 30 frames, within a metre of it, and never faced it.
Explore's camera-coverage record (`ExploreAgent.seen`, which its view goals
fill) still counted points within 0.3 m of the target as seen. So no view
goal sent the camera back, the frontiers ran out, and explore ended
`exhausted` by its existing rule.

The hint is the trigger, not the fault: it changed the order and direction
in which the robot came at the room. The no-hint run happened to enter
facing the target. `hinted_prior()` did what it is specified to do (every
goal still in the pool, only reordered), so this is not a bug in B's code.
The gap is in explore, which is not B's: its "seen" record and the
simulator's detection rule disagree about what the camera covered.

In the wrong-hint mission the target was named in one frame (85 of 97, at
1.5 m and -24 deg) and explore did not act on it. `_sighting_now()` passes
over a frame while the camera is panned or the lidar shows an edge at that
bearing; which of those applied is not traced. The trace scripts are this
session's scratch, not kept.

Not measured here: how often `dev` itself loses a find this way. No `none`
or `dev` mission ended `exhausted` in these 400, and the hinted arms lost 3
of 400. A candidate for explore (not B): count a point as camera-seen only
where a detection could have fired, or keep sending view goals inside a
room until its floor has been faced from inside detection range.

**L1 not run.** It needs explore's goals (nav2) and a saved map with named
rooms, both from the ROS container. This cloud session has no Docker, and
under `world: sim` the robot server refuses goals (501, "goals need nav2").
It is owed on the desktop.

**Candidates (not built; each would need its bars written first):**
* **A softer hint.** Set the hinted room's rate to a value below 1.0 (for
  example the larger of the target's own rate and 0.5), measured on the same
  seven arms, to trade S2's gain against S5's cost. That is an amendment to
  B, the orchestrator's and the user's call.
* **A blind request set.** Sentences written by a session that never saw
  `brain/request.py` or this set, with the same fields and split rule,
  scored once. That would measure the parser on wording it was not fitted
  to.
* **A capitalised room name gets no prior on `dev`** (a candidate bug, not
  fixed here: S1-S7 did not need it). `RoomGoalPolicy.extend` keeps a goal's
  type only `if t in prior`, so a room a person named "Kitchen" reads as
  unknown. Repro: `python -c "from brain.goal_policy import RoomGoalPolicy as
  P; pr=P.load().prior['garbage bag']; print([t if t in pr else None for t in
  ['kitchen','Kitchen']])"` prints `['kitchen', None]`. A hint matches
  without case, so it still finds such a room.

**Review** (`/code-review` and the Thermos pass, both on Sonnet, on
`d9104b97..7fe9f7e5`). Confirmed by both: a name hint ending in a number
("Bedroom 2") matches every room of that stem, because goal types are cut to

* (Thermos) a ValueError subclass from the pose read (a non-JSON body) could

* (Thermos) the start check and the mission now read an unmarked pose the
  same way (not usable);
* (Thermos) `hint_cells` no longer goes stale when the labels go away;
* comments that said the hint "never ends a mission" now say "by itself" and

Not taken: sharing the saved-map names lookup with 3.160's routes (CR, a
