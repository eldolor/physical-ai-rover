# 3.127 The twin names a stopped room labeller and a nav2 still starting

*`PLAN-ros-alignment.md` section 3.127; index: [README.md](README.md).*

**Why.** Two open items from earlier sections, both "the twin cannot say
what is happening":

* **3.70 S2, review round 2:** a room-label source that refuses for good
  (401/403, `/room` not deployed, a reply that is not JSON) stops the
  asking and `status.survey.source_error` names why
  (`brain/room_labels.py`), but the twin's survey row
  (`renderSurveyRow`, `web-twin/app.js`) reads only `no_source`: "nothing
  can name rooms here", in the alarm colour, the same words as a brain with
  no source configured at all. The operator cannot tell a wrong secret from
  a missing source. Left as "a page change, the user's call".
* **3.105, open for the user:** while nav2's lifecycle manager is not yet
  active (~10-13 s of a container start) or slam_toolbox is not `ready` (a
  start, a reload being judged, a re-map), the bridge answers `POST /goal`
  503 with a body naming the hold (`{"nav2": {...}}` or `{"slam": state}`).
  The robot server answers every bridge error `ros_unavailable`, so (read
  2026-10-31 on `dev` `989ba9f8`) a person's map tap toasts, as an error,
  "Could not send the goal: the ROS bridge did not take the goal: the ROS
  bridge answered 503 to POST /goal: nav2 is not active..." and explore's
  Why line reads `goal refused: ros_unavailable` -- a normal start-up wait
  worded as an outage. 3.105 proposed "its own reason (`nav2_starting`)".

**Checked before starting (the user asked, 2026-10-31):** no other
session works on either. Cloud and desktop sessions listed with
`list_sessions`; the live ones are on 3.125 (rooms policy timing) and 3.126
(the bridge's 304), both local to the desktop and unpushed, neither touching
the survey row, the refusal labels or the goal route. 3.125 and 3.126 were
therefore skipped when reserving this number.

**Design.**

* **Robot server** (`robot/server.py` `POST /world/goal`): a bridge
  `HTTPStatusError` whose 503 body carries `nav2` (lifecycle not active) is
  refused `nav2_starting`; one whose body carries `slam` (not `ready`) is
  `slam_not_ready`. Everything else stays `ros_unavailable`. `detail`,
  `bridge_status` and `retryable` (true for both) are unchanged, so explore
  still waits on it (it branches on `retryable`, never on this reason) and
  `RemoteRobot`'s `/action` handling is untouched (verbs are not held by
  3.105). The body is read by one helper in `world/bridge_faults.py`
  (`hold_reason()`), beside the other bridge-fault rule.
* **Twin:** `REFUSAL_LABEL` gains `nav2_starting` -> `NAV2 STARTING` and
  `slam_not_ready` -> `SLAM NOT READY`, both calm (no alarm colour, no
  flash). A map tap refused by either toasts as information ("nav2 is still
  starting -- try again in a few seconds" / "SLAM is not ready yet ...")
  instead of an error.
* **Twin, survey row:** with `source_error` set, the note reads "room naming
  stopped: <reason>" (the first 100 characters, as text) instead of
  "nothing can name rooms here", still in the alarm colour (it is a setup
  fault a person must fix). `no_source` without `source_error` reads as
  today.
* Not changed: explore's own wording (it prints the reason it was given, so
  it now reads `goal refused: nav2_starting`); the goal read/cancel routes'
  503s (`_bridge_call`, rare during a hold); the find's `status.room_labels`
  (3.116 says the twin shows none of it, for a survey's sibling -- its own
  item).

**Criteria (written before building; CLAUDE.md section 7):**

1. **Robot server, red first.** In `tests/`: a `POST /world/goal` against a
   bridge that answers 503 `{"error": "nav2 is not active: ...", "nav2":
   {...}}` is refused `nav2_starting` with `retryable` true and
   `bridge_status` 503; one answering 503 `{"error": "SLAM is not ready
   (starting)", "slam": "starting"}` is `slam_not_ready`; a 503 with neither
   key, a 500, a 401 and a transport error stay `ros_unavailable` with
   their old `retryable`. The two hold cases fail on `dev` `989ba9f8`.
2. **Explore still waits.** A held goal in explore returns `WAIT` and does
   not fail the place (an existing explore test, or a new one, run on the
   new reason).
3. **Twin, red first** (Playwright, 390 px, `tests/test_ui*.py`'s pattern):
   (a) a map tap answered `{accepted: false, reason: "nav2_starting"}` shows
   an information toast containing "nav2 is still starting" and no error
   toast; (b) `/health` `last_refusal.reason` `nav2_starting` reads `NAV2
   STARTING` in the refusal readout without the alarm or warning class;
   (c) a survey status with `no_source: true, source_error: "/room: ... 401
   ..."` shows "room naming stopped" and the 401 text in the survey row,
   never "nothing can name rooms here"; `no_source` alone still shows the
   old words (a guard). (a)-(c) fail on `dev` and pass with the fix; each
   test also run in its module's real order.
4. **Evidence:** 390 px screenshots of the survey row with a `source_error`
   and of the nav2 toast.
5. **The gate:** `/code-review` and the Thermos bug pass (the goal route is
   on the motion path), recorded with `reviewed --thermos`; `ready` passes.
6. **Deployed** (asks the user first; CLAUDE.md 3c): `service/static/sync.sh`,
   the invalidation `Completed`, the deployed `app.js` byte-identical to
   `git show HEAD:web-twin/app.js`; the board's robot server updated to the
   merge (its `picar-stack` serves the twin).

**Review round 1** (`/code-review` medium and the Thermos bug pass on
`5b619fb6`; nothing on the safety path, `retryable` and arbitration
unchanged). Both found, fixed red first:
* a SLAM `failed` for good read as the calm hold -- now only `starting`,
  `checking` and `remapping` (`SLAM_PASSING`) are;
* a nav2 down for minutes (3.105's open case) read as "still starting" --
  now only while the bridge's `nav2.inactive_s` is at most
  `NAV2_START_MAX_S` (60 s; 3.105 measured ~13 s to active);
* the dead readout labels (above).
One reviewer each, checked and fixed: the SLAM toast omitted re-mapping;
the survey cut split a surrogate pair (red with the old cut); a stale
docstring in `evaluations/nav2-gate-3105/live.py`. Not taken: an explicit
`hold` field set by the bridge (needs a bridge change and an image rebuild;
the contract test pins the bodies instead); the bridge's other 503 ("nav2
is not up", no action server) stays `ros_unavailable` (also a nav2 crash).

**Review round 2** (both reviewers on `876e0b93`; nothing above low,
nothing on the safety path). Both: `nav2.inactive_s` runs from the bridge's
start or its last active-to-inactive change, so (i) a slow cold start whose
SLAM wait plus nav2's start passes 60 s reads `ros_unavailable` (the old
behaviour, the safe direction; the Jetson's cold start is unmeasured
against the bar), (ii) a nav2 that crashes mid-run reads as the hold for
its first 60 s -- the toast now says "not active yet (starting, or
restarting)" -- and (iii) a nav2 whose `is_active` answers flap never
reaches the bar. All three are the client guessing what the bridge knows:
the root fix is the bridge setting an explicit `hold` field (a bridge change
and an image rebuild; the user's call). Taken: criterion 3(b) recorded
FAILED, not "met as amended" (section 7); `SLAM_PASSING` pinned to the
bridge source's `slam_state` assignments; the test's two error builders
made one; the UI test's letters.

**Known limits.** `vision-picar-ros:latest` (rebuilt 2026-10-18 from
`778846d`) predates 3.105, so until it is rebuilt from `dev` its bridge
neither holds goals for nav2 nor sends `inactive_s`: on that image this
step changes only the twin's survey row and the SLAM holds. At a fresh container start a tap is refused `no SLAM
session yet` before the bridge is asked (`/slam/pose` holds the start
truth until `ready`), so that window still toasts as an error; the SLAM
hold is mostly seen during a re-map. The find's `status.room_labels`
(3.116) is still not shown.
