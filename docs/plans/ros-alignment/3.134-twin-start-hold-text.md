# 3.134 The twin's nav2 hold says only a start

*`PLAN-ros-alignment.md` section 3.134; index: [README.md](README.md).
Opened 2026-11-01 on the user's word ("Fix it"): 3.133's known limit.*

**Why.** Since 3.133 the bridge refuses a goal `nav2_starting` only while
nav2 is still in its start: never yet active, the manager never having
replied. A nav2 that restarts after being active reads `ros_unavailable`.
The twin's Engineer-voice toast for `nav2_starting` still says "nav2 is not
active yet (starting, or restarting)" (`web-twin/strings.js`
`eng.goal.hold.nav2_starting`), wording left over from 3.127, which
guessed. The operator voice ("The robot's navigation is still starting")
is already right. The twin engineering spec's row still names
`GOAL_HOLD_TEXT` and quotes the old text, though 3.132.2 moved the words
to `strings.js`.

**Checked before starting (2026-11-01):** no other session is on this.
The `plan/*` branches on origin are 3.80, 3.83, 3.98 and 3.116, none
touching `strings.js`. `overlap` was clean.

**Design.** The Engineer string becomes "nav2 is not active yet (the ROS
container is starting) — try again in a few seconds". It keeps the prefix
the UI test reads and drops "or restarting". The operator string is
unchanged. The twin spec's row names `strings.js` `goal.hold.<reason>` and
quotes the current words. Nothing else changes.

   `d46c5173`.

   refused `nav2_starting` shows the information toast without "restart".
   It fails on `dev`. Run the module whole, in its real order.
3. **Evidence:** a 390 px screenshot of the toast (`UI_SHOTS`), committed
   under `evaluations/twin-3134/`.
4. **The gate:** `/code-review`, recorded with `reviewed` (a text-only

5. **Deployed** only on the user's go: `service/static/sync.sh`, the
