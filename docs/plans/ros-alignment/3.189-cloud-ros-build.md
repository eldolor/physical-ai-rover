# 3.189 Build the ROS image and run the live stack in a cloud session

*`PLAN-ros-alignment.md` section 3.189; index: [README.md](README.md).*

**Why.** The user chose, 2026-11-18, to find out whether a cloud session can
build `service/slam/` and run the live stack validly, so the desktop's Docker
tasks (3.161.B, 3.70.S4, 3.70.M1, 3.175.C's live check, 3.156.E's live bars)
could move to the cloud.

**Facts going in** (probed 2026-11-18 by the orchestrator, not re-probed):
Docker runs in a cloud session (`dockerd` by hand); the egress proxy carries
HTTPS only and re-terminates TLS with its own CA; `packages.ros.org` is
HTTP-only for apt and so unusable; the OSUOSL mirror
`https://ftp.osuosl.org/pub/ros/packages.ros.org/ros2/ubuntu` is allowed; the
Ubuntu archive, PyPI and GitHub are reachable. 4 cores, about 50 GB free.

**Design.** `service/slam/Dockerfile` gains `ARG BASE_IMAGE=ros:humble-ros-base`
and nothing else: with the default the build is the desktop's and the
Jetson's, unchanged. `service/slam/build-cloud.sh` first builds a local base
(`ros:humble-ros-base` plus the proxy's CA, an apt proxy, HTTPS sources and the
OSUOSL ROS mirror), then builds the real Dockerfile on it. The CA is copied
into a temporary context at build time and is never committed. The source-built
tf2 0.25.24 and the pinned `slam_toolbox` stay as they are (CLAUDE.md section 6).

**Criteria (written before building; CLAUDE.md section 7):**

1. **Build.** `build-cloud.sh` produces `vision-picar-ros:plan-3.189`
   (never `:latest`) with exit 0, within 90 minutes. Recorded: wall time,
   image size, disk used, the first failure and its host if any.
2. **Default build untouched.** `docker build` of the Dockerfile with no build
   args resolves `FROM ros:humble-ros-base`: the diff is one `ARG` and the
   `FROM` line, pinned by a test.
3. **nav2 up.** Under `SIM_MAP=scaled_house`, robot server first, then the
   container (`PICAR_ROS_NETWORK=host`, `-v picar-maps:/maps`), nav2's lifecycle
   nodes all `active` and the bridge's status green within 120 s.
4. **A goal reached.** One goal posted through `POST /world/goal` is accepted
   and the robot ends within 0.5 m of it (nav2 reports success) within 180 s.
5. **Valid run.** Load average sampled by `uptime` every 10 s through the run
   (steps 3-4): **max <= 4** (the 3.79 rule: above ~4 a run is invalid).
   Recorded: max and median.
6. **Cleanup.** No container, robot server or `dockerd` job of this section is
   left running at the end.

A failed criterion is recorded as failed, not re-scoped.

## Results

Run 2026-11-18/19, a cloud session (4 cores, `dockerd` started by hand,
Docker 29.10), image `vision-picar-ros:plan-3.189`, base `vision-picar-ros-base:plan-3.189`.

| # | Criterion | Result |
|---|---|---|
| 1 | Build | **Met.** `build-cloud.sh`, exit 0, **398 s wall** (6.6 min; the desktop's is longer, the Jetson's ~15 min). Image **3.95 GB** (base 1.13 GB); disk used on `/` grew **5.6 GB** (12.0 -> 17.6 GB). No failure. Every stage reached its host: Ubuntu archive over HTTPS, the OSUOSL ROS mirror, GitHub (the pinned tf2 and `slam_toolbox` clones, colcon builds from source). |
| 2 | Default build untouched | **Met.** The Dockerfile diff is `ARG BASE_IMAGE=ros:humble-ros-base` and `FROM ${BASE_IMAGE}`; `tests/test_slam_dockerfile.py` pins both. (A no-arg `docker build` was not run here: the cloud's stock apt source is unusable.) |
| 3 | nav2 up | **Met.** `tests.demo_explore.stack("scaled_house")` (the repo's own harness: robot server, brain, container with `--network host`) reported `drive.ros_up` and a usable `/world/map` after **10.9 s**. Deviation: the harness runs the container without `-v picar-maps:/maps`, so no map was saved; that is the harness's own choice, not the cloud's. |
| 4 | A goal reached | **Met.** After the scripted mapping lap (`demo_nav_goals.map_first`), `POST /world/goal` "hallway, north" (4.35, 0.75): `succeeded` in **13.7 s**, ground-truth end error **0.096 m**, closest approach to any surface 0.404 m, wheels stopped. One goal only; the six-goal suite (`tests/test_nav_live.py`) was not run. |
| 5 | Valid run (load <= 4) | **FAILED.** 20 samples of `/proc/loadavg` (1-min), one per 10 s, **max 4.68, median 1.37**. Two samples exceeded 4 (4.50 and 4.68), during the mapping lap and the goal; before them the load sat at 0.8-1.4 (stack idle). The load is a 1-minute average that rises with the lap, so the peak is the run's real load: 4 cores saturated by the sim, the ROS stack and the brain. By 3.79's rule that part of the run is not valid for timing. |
| 6 | Cleanup | **Met.** Container removed, robot server and brain killed, no run process left; `dockerd` stopped at the end. |

**What this says.** A cloud session builds the image and runs nav2 to a
goal correctly. It is not a timing-valid host: on 4 cores a single mapping
lap plus one goal peaks the load above the 3.79 bar, so any live bar judged
on smoothness, late ticks or latency (3.42-style) cannot be taken here. A
bar judged on outcome (a goal reached, a map saved, a mission's result) can,
with the load recorded and the exclusive lock's rule kept in mind.
