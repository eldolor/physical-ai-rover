## 3.166.A: design and criteria (written 2026-11-07, before building)

What it rests on: `tools/plan_claims.py` as on `dev` -- a claim file per
step in the shared `.git` (`plan-claims/<step>.json`, its `touches` copied
from the plan row when taken), `claim/<step>` on origin (3.139), `assess()`
(the board's statuses), `tracked()` / `covered()` (what a path belongs to,
and whether this session may change it), the three hooks (`hook_edit`,
`commit_check`, `push_refusals`) and `allow`. Other sessions' hooks run
this code live, so every change keeps an old claim file readable as it is
(no field required that an old file lacks; new fields optional) and fails
open where it fails today (a guard never breaks editing).

**F1. Touches are read from the plan, not frozen in the claim.** Wherever a
claim's Touches decide something (the edit hook's foreign claims, `covered()`
for this session's own claims, the push gate, the board's overlap and
`claim`'s rival check), the step's **current** row is read
(`quick_steps`: origin/dev's tables, and this checkout's own section from
HEAD) and the stored `touches` only when the step is no longer in any
table (a renamed or deleted row). A narrowing on dev frees the edits at
once; a widening fences at once (the guide's rule stands: widen on dev
first, before using it). The stored field is still written, so an older
tool reading a new file behaves as today.

**F2. An unclaimed step's whole top-level directory fences nothing.** In
`tracked()`, a Touches entry that is a top-level directory (`tests/`,
`brain/`, `control/`, `web-twin/`, `tools/`, ...: one path component and a
`/`) does not fence a path while **no one holds that step**; its files and
globs, and deeper directories (`evaluations/x/`, `service/slam/`), still
do. A held step's claim fences its whole Touches as today (the foreign-claim
check, F1's current row). Spec lint keeps its rule; only fencing by an
unclaimed step changes.

**F3. A lost push race, and a release before the push landed.**
* `claim <step>` accepts a step whose State reads done **only on this
  checkout's own section branch** (the row done in HEAD's committed table
  while origin/dev's row is not closed): the push that would have made it
  done has not landed, so the step is still open on dev. The claim says so.
* `release` refuses, by default, while this checkout is the section's
  `plan/*` branch and holds commits that are not on origin/dev and change
  the released steps' Touches or the section's file ("N commits not on
  origin/dev: push first, or `release --unpushed` to give the claim back
  anyway"). `--unpushed` is the holder's own flag (it gives back the
  holder's claim; it overrides nobody's), so it is not a user-only switch.
  A failed push piped through `tail` then leaves the claim held, as it
  should, instead of freeing it.

**F4. A section with no `## Steps` table can be claimed whole.**
`Board.whole(3.N)` knows a section whose file is on origin/dev (as it knows
one with a branch or a step table), so `claim 3.N` works for it and the push
gate's demand for a claim to edit its file can be met.

**F5. Refusals name the claim that holds the file, and `allow` works from
the user's shell.**
* When a fenced path lies inside another session's live claim, every
  refusal (the edit hook, the commit warning, the push gate) names that
  claim (its step id, as `allow` reads it) and its holder, and the exact
  command the user would run: `python3 tools/plan_claims.py allow <claim's
  step> --session <this session's id>`. It never suggests `claim` for a
  step another session holds.
* `allow <step> --session <id>` records the named session, so the user can
  run it from any shell (no Claude process above); without `--session`, it
  is today's form (the calling Claude process). A claim held on another host
  (origin only, no local file) is refused with that reason. Still the user
  alone (CLAUDE.md, rule 12): the wording says so, and nothing in the tool
  lets an agent run it on its own behalf any more than today.

**F6. `--accept-overlap` reaches an active, unclaimed branch of the step's
own section.** `assess()`'s two `active` returns, when the caller passes
`accepted` (`claim --accept-overlap`), record the branch
(`"<branch>: active, unclaimed, same section"`) in the claim's
`accepted_overlap` and go on to the remaining checks instead of refusing.
Another session's **claim** still refuses (the one-session-per-section rule
is about claims), and without the flag nothing changes.

**Not changed.** Who may override: the user alone, by `PICAR_CLAIM_BYPASS=1`,
`allow` and `release --force` (the section's scope). The claim-on-origin
protocol (3.139), the lock, the push gate's fail-closed reads.
