# 3.208 A failure budget for POST /action; a failed action is never re-sent

*`PLAN-ros-alignment.md` section 3.208; index: [README.md](README.md).*

**Why.** S7's chaos run (3.202, finding K7: the brain-robot link degraded,
5% of requests reset) showed that ONE connection reset on the brain's
`POST /action` ends the mission `failed`: `RemoteRobot._request` turns any
`httpx` error into `RobotTransportError`, nothing in `brain/` catches it, and
`MissionRunner._step_tick`'s catch-all ends the mission at once ("step
failed: ..."). B3.2 already gives the vision call a consecutive-failure
budget and 3.153 gave the frame read one; the action, the call most exposed
to the link, has none. Decided by the orchestrator under the user's
delegation, 2026-11-21.

**The rule that is not negotiable: a failed action is NEVER re-sent.** The
API has no idempotency key, and a reset after the request was written may
come after the robot executed it. Nothing retries the POST. The failed tick
stops the car (a stop is idempotent, not the failed action), records no
step, and the NEXT tick re-decides from fresh sensing (a new frame, a new
depth grid and scan), which may or may not pick the same verb.

**What counts.** Only a transport failure on `POST /action` itself: the
request never got an HTTP answer (connection refused or reset, a read or
write error, a timeout, a protocol error: `httpx.TransportError` but
`UnsupportedProtocol` and `LocalProtocolError`, which are our own
configuration or code). Raised as `RobotUnreachable`, a subclass of
`RobotTransportError`, so every existing `except RobotTransportError` keeps
catching it. Every answer the robot server GAVE keeps its meaning exactly:

| what the robot server answered | raised | mission | kept? |
|---|---|---|---|
| 200 `executed: false`, no reason / a safety reason | `SafetyViolation` | a veto for this move; counts toward `stuck_after` | kept |
| 200 `executed: false`, `battery_check` | `SafetyViolation` | a veto, not counted as blocked | kept |
| 200 `executed: false`, `preempted` | `Preempted` | `cancelled` (dpad) or `failed` (arbitration fault) | kept |
| 200 `executed: false`, `person_stop` | `StoppedByPerson` | `cancelled` by stop | kept |
| 200 `executed: false`, `autonomy_lapsed` / battery reserve / poweroff | as before | as before | kept |
| 200 `executed: false`, `ros_unavailable` / `no_feedback` | `RobotTransportError` | `failed` at once | kept |
| 400 | `ValueError` | `failed` at once | kept |
| 401/403/404/409/422, any other 4xx, any 5xx | `RobotTransportError` | `failed` at once | kept |
| no answer (reset, refused, timeout) | `RobotUnreachable` | **budgeted (new)** | changed |

A transport failure on any GET (scan, depth, odometry, pose) is out of
scope and still ends the mission at once; recorded as a follow-up, not
fixed here.

**The three failsafes stay three.** This is a fourth budget inside B3.2's
runner, beside vision's and the camera's; the robot watchdog (B3.1) still
stops motors a lost link left energised, and B3.3 still catches a tick that
never returns (a hung POST is bounded by `RemoteRobot`'s 10 s timeout, under
B3.3's deadline).

**Criteria (written 2026-11-21, before building; CLAUDE.md section 7):**

1. **K7 reproduced, red first.** A test in which exactly one `POST /action`
   (a move, mid-mission) loses its connection, over a real `RemoteRobot`
   against an in-process `robot/server.py`, ends `failed` ("step failed")
   on `dev` `49dcad18` and ends `found` after the change. Both halves of a
   reset: the request lost before the robot saw it, and the answer lost
   after the robot executed it.
2. **The budget.** `DEFAULT_MAX_ACTION_FAILURES = 3` consecutive failed
   ticks end the mission `failed` with `end_reason` starting
   `robot unreachable 3 times in a row:` (the named reason; the outcome
   stays `failed`, a fault, as vision's and the camera's budgets end -- no
   new outcome for the phone and 3.70's end-state table). A completed tick
   resets the count (`status.action_failures`). Each failed tick stops the
   car and idles `ACTION_RETRY_S` (0.5 s, so a refused connection that fails
   in a millisecond cannot spend the budget at once). A link that never
   comes back ends after exactly 3 failed POSTs and no move after the first.
   A failure landing after `stop()`/`abort()` does nothing (not counted, no
   stop), as for the other budgets.
3. **Never sent twice.** Under injected resets (both halves), for every
   decided action the number of `POST /action` carrying it that reached the
   wire is exactly 1 (counted per decision at the transport). Over the sweep
   of criterion 4: 0 decisions with 2 or more POSTs.
4. **Progress pair, through the real path** (`MissionRunner` -> agent ->
   `robot/safety.py` -> `RemoteRobot` -> `robot/server.py` -> backend, in
   process): the frontier backpack hunt in three houses (`SIM_MAP`
   `starter_house`, `scaled_house`, `home_first_floor`; the server's
   simulator has one start per house, so the draw is over houses and fault
   seeds), a no-fault arm (one mission per house: deterministic) and a fault
   arm of 10 seeds per house (30 missions) where each `POST /action` is
   reset with probability 5% (seeded; half before, half after the robot
   sees it). The
   fault arm's found rate is >= the no-fault arm's minus one mission, and
   >= 90% (3.135's bar); on `dev` the fault arm's found rate is reported
   beside it. Stability half: 0 missions ending "step failed" from a reset;
   every reset counted in `action_failures` at the time.
5. **The existing failsafe tests pass unchanged**: `tests/test_failsafes.py`,
   `tests/test_camera_budget_3153.py`, `tests/test_remote_robot.py`, and
   the full fast tier (`plan_section.py ready`).
6. **Live.** One mission against the live local stack (robot server and
   brain server as processes, the brain's HTTP API) with a TCP proxy between
   the brain and the robot server that resets chosen `POST /action`
   connections (two, non-consecutive: one before forwarding, one after the
   robot answered): the mission ends `found`, its log shows `robot
   unreachable 1/3` twice, and the proxy's count of forwarded POSTs per
   decision shows no repeat. One more with every `POST /action` reset from
   step 3: ends `failed`, `robot unreachable 3 times in a row`, within
   3 x (`ACTION_RETRY_S` + the request's time) + one tick.

A failed criterion is recorded FAILED with its numbers, not re-scoped.

*Why the budget of 3 is too tight.* A frontier tick sends 3.15
`POST /action` (three peeks and the move; counted over a no-fault starter
mission: 192 POSTs in 61 steps), so 5% per request is about 15% per tick,
and three failed ticks in a row about 0.3% per tick: about 16% of
60-tick missions -- what the sweep shows (4/30).

*Found on the way: K7 is mostly GETs.* The same mission makes 8.5 robot
GETs a tick (`/scan` 2.7, `/distance` 2.1, `/depth` 1.7, `/frame`,
`/odometry`). Under 3.202's K7 (5% of ALL requests lost) a lost `/frame`
spends the camera budget (3.153), a lost `/scan` inside the frontier's
`vision_fn` spends B3.2's vision budget, and a lost `/distance`, `/depth`
or `/scan` in the safety check or a peek still ends the mission at once
("step failed"). This section's scope (`POST /action` only) cannot make K7
pass by itself.

**Amendment 1 (2026-11-21, decided by the orchestrator under the user's
delegation after criterion 4's FAILED run; written before any re-measure;
criterion 4's run above stays on record as FAILED).** Option (a)+(b) of the
interim report: one budget for the robot LINK, not for `POST /action`.

* *What counts.* A request to the robot server with no HTTP answer, on any
  route: `RemoteRobot` (`RobotUnreachable`, any method and path) and
  `RemoteWorld` (`WorldUnreachable`, a `WorldTransportError` with no
  status), sharing one `LinkHealth` record when the world is served by the
  robot's server (the brain server's default). `RemoteNavigator` (explore's
  nav2 goals) is out of scope and unchanged. Every HTTP answer keeps its
  meaning (the table above). Nothing retries anything; a `POST /action` is
  never re-sent.
* *Where a wrapped one lands.* An error whose explicit-cause chain holds a
  `RobotUnreachable` or `WorldUnreachable` lands in the LINK budget, never in
  the camera's (3.153) or vision's (B3.2): a lost `/frame` (wrapped as
  `CameraUnavailable`) and a lost `/scan` inside the frontier's `vision_fn`
  (wrapped as `VisionUnavailable`) are link failures. The camera budget
  keeps counting a frame read that got an ANSWER (a 503); the vision budget
  keeps counting the cloud's failures and timeouts.
* *No move from partial sensing.* In a step tick in which any robot request
  went unanswered (`LinkHealth.unanswered` advanced since the tick began --
  also the reads that code swallows, such as `robot/safety.py`'s
  `_has_wheels()` or the frontier's `_pose()`), `_HaltGate` refuses every
  movement and pan command and `_GatedNavigator` every goal, raising
  `LinkLost`; the tick is a link-failed tick.
* *The budget.* Each link-failed tick stops the car, records no step and
  idles `LINK_RETRY_S` (0.5 s). A completed tick with every request
  answered resets the count; a completed tick in which a swallowed read
  went unanswered (it moved nothing) leaves it as it is. The mission ends
  `failed` when BOTH hold: no robot request has been answered for
  `LINK_DEAD_S` (counted on the runner's clock, from the end of the last
  tick in which one was answered, or the mission's start) AND at least
  `LINK_MIN_FAILED_TICKS` = 3 consecutive link-failed ticks; reason
  `robot link lost: no answer for <s> s, <n> failed ticks in a row:
  <error>`. Backstop: `LINK_MAX_FAILED_TICKS` = 20 consecutive link-failed
  ticks end it whatever answered (`robot link failing: 20 ticks in a row
  with an unanswered request: <error>`) -- a link that answers reads but
  loses every POST would otherwise never end, and an in-process harness
  with no time limit would loop forever (a failed tick records no step).
  At K7's model a tick fails about 46% of the time; 0.46^20 is 2e-7.
* *`LINK_DEAD_S` = 3.0 s, and why.* Three times the robot watchdog's 1 s
  (B3.1): by then the robot server has stopped the motors on its own for
  2 s, so the wait costs no safety, only a later report. Far above the gap
  between answers on a flaky link (at 5% loss a tick answers something
  unless its first request is lost; 3 s with no answer is 6 failed ticks
  each lost at their first request, 0.05^6 = 2e-8). Below the 10 s request
  timeout, so a link that resets or refuses ends in about 3 s.
* *Status.* `action_failures` becomes `link_failures`.

**Decisions after the results** (the orchestrator, under the user's
delegation, 2026-11-21):

* `LINK_MAX_FAILED_TICKS` stays 20. The measured 0.2-1% false-end risk is at
  5% loss of every request, a chaos rate far above a real link, and a false
  end leaves the car stopped. The corrected margin (longest failed-tick
  streak per K7-all mission: median 8, max 14) is a known fact, not a bar.
* The first tick's `look_center()` retried after a lost one is allowed: an
  absolute pan is idempotent and not a decided move; "a failed action is
  never re-sent" covers decided moves.
* The Thermos pass was run on the test-only commit `cb004a2a` (no findings),
  so its `reviewed --thermos` record is true.
