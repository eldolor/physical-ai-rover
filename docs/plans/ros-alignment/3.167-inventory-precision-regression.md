# 3.167 Inventory precision fell below 3.60's bar

*`PLAN-ros-alignment.md` section 3.167; index: [README.md](README.md).*

**Why.** 3.165 found it. 3.60's sweep
(`python -m tests.inventory_sweep --seed 3463`: 20 frontier missions in
`complex_house`, detector errors on) read **97.1%** precision of reported
when 3.60 merged (`87603bc1`, 2026-10-09), against a bar of 95%. On `dev`
of 2026-11-07 it reads **93.8%** (97 reported; 3.165's
`evaluations/inventory-3165/dev-sweep.json`). Recall moved the other way,
from 93.5% to 94.1%.

## 3.167.A: what counts as found (written before bisecting)

**Method.** `git bisect` from `87603bc1` (good) to `dev` (bad), one sweep
at a time under the shared desktop lock, with no other job of this
session's beside it.
* **The test:** each commit's own `tests.inventory_sweep --seed 3463`, run
  in a separate checkout. Its own harness is used, because the harness is
  part of what may have changed.
* **Good** is precision of reported >= 95% (3.60's bar); **bad** is below
  it.
* A commit where the sweep cannot run is skipped (exit 125).
* Each step's full score is kept (`evaluations/inventory-precision-3167/bisect.jsonl`).
* The endpoints are run first: if `87603bc1` does not read >= 95% today,
  that is recorded and the method stops for a rethink, not forced.

**Found** means all three of:
1. **The commit:** the first bad commit, with its score and its parent's,
   both runs recorded.
2. **A mechanism:** which landmarks turn from right to wrong, compared
   field by field between that commit and its parent (as 3.165 did), and
   why, traced to the lines that changed.
3. **A test that pins it:**
   * **If it is a bug:** a test that fails on the bad commit's behaviour
     and passes with the fix, red first, and the fix reviewed
     (`/code-review` + Thermos, Sonnet; the inventory is stored data). The
     sweep must come back to >= 95% with recall within 1 point of `dev`'s
     94.1%.
   * **If it is deliberate** (a later honesty fix in the simulator, a
     harness or detector change, a policy change that drives elsewhere):
     no "fix". Record the reason, and pin the mechanism in a test (the
     change's own effect, shown on a small case). Propose to the user to
     re-baseline 3.60's bar on today's numbers. Nothing is re-baselined
     here.

If the drop is spread over several commits (no single step from >= 95% to
< 95% explains it, or the bisect lands on a commit whose diff cannot touch
the sweep), that is recorded as the finding, with each step's score.

## 3.167.B: found (2026-11-07) -- deliberate; a re-baseline is proposed

Records: `evaluations/inventory-precision-3167/` (`bisect.jsonl` every
step; `seeds.jsonl`; `compare-90f81fcb-fc5c2122.json`; `mechanism.py`,
`pose_trace.py`). Each sweep ran alone under the shared desktop lock, in a
separate checkout (`/tmp`), with that commit's own harness.

1. **The commit: `fc5c2122`, "3.74 part B: the depth camera's floor band
   in robot/safety.py"** (2026-10-12). The bisect has exactly two states.
   * Every commit from `87603bc1` (3.60's merge, re-run today: 97.06%, so
     the endpoint holds) to its parent `90f81fcb`: 97.06% precision, recall
     93.5%, 92 seen, 102 reported.
   * It and every commit after, up to today's `dev`: 93.81% precision,
     recall 94.1%, 85 seen, 97 reported.
   * No step skipped; 11 steps.
2. **The mechanism:** the floor band, a deliberate safety change, clamps
   some FORWARD moves among `complex_house`'s small floor things.
   `brain/inventory.py` is not in the commit.
   * 11 of the 20 missions take different actions. In 10 of the 11, the
     parent's FORWARD is a turn at the first divergence.
   * The other 9 take the same actions but not the same poses. In mission
     1, tick 14's FORWARD ends about a millimetre shorter, and every later
     pose carries it.
   * The inventory's thresholds (0.5 m new view and merge, the 2 deg range
     gate's choice of return) then fall differently, so the landmarks
     differ (7 of those 9 missions differ in their reports).
   * Wrong reported landmarks (none of their class within `MATCH_M`): 3 ->
     6, and the two sets share none (`compare-90f81fcb-fc5c2122.json`).
     Whether each is a relabel or a misplacement was not traced; the four
     seeds below make it moot.
3. **Pinned:** `tests/test_inventory_precision_3167.py`.
   * Mission 1 with the band patched off takes the same actions, and the
     FORWARD where the poses part travels further than with the band on
     today's `dev`.
   * The bisect's two states and the seeds below are pinned.

**It is one seed's variance, not a loss of precision.** The parent and the
culprit on 3.46's other seeds:

| Seed | parent `90f81fcb` | `fc5c2122` (band) |
|---|---|---|
| 3463 (3.60's) | 97.1% (102 reported) | **93.8%** (97) |
| 346 | **93.8%** (129) | 97.4% (117) |
| 3461 | 98.9% (89) | 97.8% (93) |
| 3462 | 97.2% (106) | 98.1% (107) |
| pooled | 96.5% (411 / 426) | 96.9% (401 / 414) |

The parent fails the 95% bar on seed 346 too. A single seed's precision
moves about +/-3 points with any change that moves the robot, and pooled
over four seeds the band changes nothing (+0.4 points).

**Proposed to the user (not done here):** judge 3.60's precision bar
(95% of reported) on the four seeds pooled (346, 3461, 3462, 3463), not on
seed 3463 alone. Today's measured rows: the culprit pools at 96.9%, which
meets it. `dev`'s own four-seed pool is not measured here. No fix: the
band is the safety layer working as 3.74 designed it.
