# 3.155 The robot server memory-locked: its wheel loop under an OOM squeeze (3.135.B F2's new record)

*`PLAN-ros-alignment.md` section 3.155; index: [README.md](README.md).*

**Why.** 3.135.B F2's new record (2026-11-05, `dev` `a0a5bc9e`, after 3.151
locked the truth body) FAILED on a product bar: late wheel ticks in 3 of 5
runs (2, 2, 1; max 204, 221, 439 ms) when `MemAvailable` reached 10-11 MB
(the first record, 15-99 MB, had 0 late). VE's driver was still the only OOM
kill and every process lived. The robot server runs at `oom_score_adj` -900
but is not memory-locked: under the squeeze its pages are reclaimed and
faulted back, the stall 3.151 removed from the truth body, now in the wheel
loop -- the motion path, which on the Rover matters. The orchestrating
session's call (2026-11-05, under the user's standing instruction): lock the
robot server's pages. (3.153's failed frame read is a different cause: the
robot server answered every `/health` and ran 0 late ticks there; it was the
simulator's sensor program that stalled. 3.153 stays its own.)

**Measured before the criteria (2026-11-05, the board, read-only):** the
running robot server (`picar-stack`, sim mode) holds 51 MB resident and maps
74 MB, one thread at idle; `picar-stack`'s unit gives it a memlock limit of
**64 KB** (systemd's default), so no lock is possible there today. The brain
holds 65 MB, also at -900.

**Criteria (written before building; CLAUDE.md section 7):**

1. **A launcher locks, then serves.** `robot/locked_serve.py` takes
   uvicorn's arguments for `robot.server:app`, calls `mlockall(MCL_CURRENT |
   MCL_FUTURE | MCL_ONFAULT)` (3.151's `MCL_ONFAULT`: touched pages only) when
   the memlock limit is unlimited -- waiting up to `PICAR_MEMLOCK_WAIT_S`
   (default 0) for it, so a harness can raise it after the spawn -- and
   otherwise serves unlocked; either way one log line says what happened
   (locked, the errno, the limits, `VmLck`/`VmRSS`). `robot/server.py` is not
   touched (3.145 holds it). Pinned in process: the lock call and its flags,
   the refusal under a finite limit, the wait.
2. **Wired where the robot server starts:** `service/tunnel/run.sh` runs the
   robot server through the launcher; `picar-stack.service` gains
   `LimitMEMLOCK=infinity`. Installing the unit on the board is a board
   change: done only on the orchestrator's or the user's word, else recorded
   as owed. 3.135's `stack.py` starts the robot server through the launcher
   (`PICAR_MEMLOCK_WAIT_S` 10, its limit raised by `sudo -n prlimit` after
   the spawn, as 3.151 does the body), and records the answer
   (`robot_lock.json`; `FMEA_ROBOT_LOCK=0` skips it).
3. **The board's F2 check** (`run.py row F2 --runs 5`, 15 W, sim mode, no
   motion, the board lock, left as found; before Saturday 2026-11-07 night),
   the robot server locked in all five. Bars:
   * **0 late wheel ticks in every run**, each reaching `MemAvailable` <= 15
     MB (the new record reached 10-11 MB);
   * **VE's driver the only OOM kill** in every run; the brain, ROS, the
     robot server and the truth body alive after (3.151's truth log held); 0 contacts; every mission ends;
   * the lock starves nothing: the robot server's resident memory at most
     64 MB above the new record's.
   If a run never reaches 15 MB, it is reported, not counted as met.
   The baseline (the plant) is the new record itself: unlocked, 3 of 5 late.
4. The suite passes; `/code-review` and the Thermos pass (the motion path),
   at most two rounds.
