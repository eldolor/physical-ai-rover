# 3.203 The twin polls no robot before one is connected

*`PLAN-ros-alignment.md` section 3.203; index: [README.md](README.md).*

**Why.** On 2026-11-21 the deployed twin (CloudFront, dev b584df63) at 390 px
with no robot saved requested `/frame` and `/battery` on its own origin, both
403. app.js prefilled the robot field with `location.origin` on any http page
and auto-connected, so a static host was treated as a robot. Only a robot
server may claim its origin: `robot/server.py` now injects
`<meta name="picar-robot-origin">` into the page it serves, and app.js
prefills (and so connects) only when that marker is present.

**Criteria (written before building; CLAUDE.md section 7):**

1. A first-run page on a non-robot origin makes 0 requests to robot routes
   (`/frame`, `/battery`, `/health`, `/depth`) in 10 s.
2. A first-run page served by the robot server (same origin) still prefills
   its own address, polls and connects.
3. A saved robot is still polled, from a page on any origin.
4. Each has a UI test (`tests/test_ui_first_run_polls.py`). Test 1 fails
   before the fix. Tests 2-3 guard behaviour the fix must not change, so
   they pass before it; test 2 was shown to fail with the marker removed.

**Result.** 3 tests pass; stage3b (first-run) passes. `/health` is not a
robot-only route here: the env banner reads the page origin's `/health`,
which the deployed page answers from the vision service (left alone).
