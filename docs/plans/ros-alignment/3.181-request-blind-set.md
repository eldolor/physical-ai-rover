# 3.181 A blind request set for the plain-words find

*`PLAN-ros-alignment.md` section 3.181; index: [README.md](README.md).*

**Why.** 3.176.B's rule parser (`brain/request.py`) scored 76 of 76 on 3.176's
request set, but one session wrote both the sentences and the parser, so the
score shows the parser reads its author's phrasing, not people's. This step
writes a second set **blind**: by a session (the orchestrator's worker,
2026-11-15) that has never opened `brain/request.py`, its tests or 3.176's set,
working only from 3.176's written rules: lines 1-148 of its section as of
`dev` `223214a4` (why, scope, the design, "The room vocabulary" and "What the
set encodes") and its criteria table (lines 172-186); not its request set
(lines 149-171) and not its results (line 281 on). The
set is frozen with a sha256 pin before the parser is run on it, and the parser
is scored on it once. Nothing in the parser changes here: misses become
candidates for 3.176.

**Scope.** No code under `brain/`; no paid call; no model.
* `evaluations/request-3181/blind_set.jsonl`: one row per sentence, written
  the way people ask a robot to find things (varied verbs, politeness,
  indirect wording, typos, relative places, several kinds of object), each
  with the parse 3.176's rules give it.
* `tests/test_request_blind_3181.py`: the sha256 pin (the set cannot change
  unseen) and the scorer's own tests.
* `evaluations/request-3181/score.py`: scores `parse()` on the set, once,
  writing `score.json`.

## Criteria (written 2026-11-15, before any sentence or score)

Two groups of rows:
* **`rules` rows** (the bars): each expected parse follows 3.176's written
  rules exactly, including where a person might mean otherwise.
* **`gap` rows** (reported, no bar): natural sentences the written rules do
  not settle or settle against what the person means (a room said before the
  target, "go to the kitchen and find ..."); the expected parse is what the
  person means. They show where the rules, not the parser, stop.

The bars are 3.176's P1-P5, on the `rules` rows, scored once:

| # | Metric | Bar | Kind |
|---|---|---|---|
| R1 | target exact match (lower case; null for no target or two) | **>= 90%** | progress |
| R2 | room exact match (type, a person's name, or none) | **>= 95%** | progress |
| R3 | a room given where none was said, or the wrong room | **<= 1** row | stability |
| R4 | attributes exact (colours as a set, and size) | **>= 95%** | progress |
| R5 | `plain` rows: the target equals the text, no room, no attributes beyond the words | **100%** | stability |

Reported beside them, no bar: each bar per kind; the `gap` rows' matches; every
miss with its sentence, expected and got.

**Scoring rules, fixed now.** One run of `score.py` on the frozen set against
`dev`'s parser at the commit named in the results; the first full score is the
result. A row's names (a person's room names on the saved map) are passed as
`parse(text, names=...)`. Colours compare as sets of canonical words (`grey`
for "gray"); size is `small`, `large` or none; a room is `{"type": t}`,
`{"name": n}` or none. A failed criterion is recorded as failed, not
re-scoped.

**What the misses say.** Nine of the ten `rules` misses are a polite or
indirect opening the parser does not strip ("could you please look for",
"hey robot,", "would you mind finding", "any idea where", "do you know where",
"have you spotted", "I'm looking for", "I need ... ,") or a modal after the
target ("might be"); the parser then hands the whole opening on as the target,
which the detector and the identity check would be asked for. Two cut the
target short at the wrong end ("could you", "hey robot": a comma or "please"
ended a target that had not begun). "search the garage" reads "search" as part
of the object. The Find box (3.176.C) shows the reading before Start, so a
person sees each of these; none gives a wrong room.

**Review** (`/code-review`, 2026-11-15, on the pin test and the scorer). Taken:
R4 counts a row's attributes even when its target is wrong (the parser reads
colours from whatever it took as the target, so b030's wrong target still
carried `blue`): R4's definition is 3.176's P4 and stays, and the stricter
count, 82 of 92, is reported beside it, computed from the committed run's rows
(no second parse). The floor test pins the missed rows, not only the counts.
The scorer refuses to overwrite `score.json` and records whether the tree was
dirty. R5 counts `rules` rows only (it did already: no gap row is plain).
Expected colours are normalised as the parser's are. The room types are
checked against the parser's vocabulary (after the freeze). The section now
says exactly which lines of 3.176 were read.

**Candidates for 3.176** (not built here; each needs its bars written first):
* the target starts after an opening, not at the first word: a wider lead
  (vocatives before a comma, "would you mind" with a gerund, "do you know /
  any idea where", "have you spotted/noticed", "I'm looking for", "I need");
* a comma or "please" before any object word ends nothing;
* modal verbs after the target end it ("might be", "could be", "should be");
* "search/check the <room>" with no object is no target, the room read;
* the `gap` group: a room said before the target, and verb typos, are what
  people say; 3.176's rules would have to name them before a parser is held
  to them.
