# 3.185 A person's room name that is a synonym reaches its room type

*`PLAN-ros-alignment.md` section 3.185; index: [README.md](README.md).*

**Why.** 3.183.B's review candidate. Since 3.183 the rooms policy
(`RoomGoalPolicy.extend`) reads a room's type without case, but only when the
name IS one of the prior's types (kitchen, living room, bedroom, bathroom). A
person's room named with a vocabulary synonym -- "Lounge", "Den", "Master
Bedroom", "Washroom" (3.176.A's table, `brain/request.py` `ROOM_WORDS`) --
still reads as no type and gets no prior, while a type hint already reads the
same name through the vocabulary (`hint_matches` -> `canonical_room`).

## Design and bars (written 2026-11-15, before the change)

**The change** (the rooms policy only, reading the shared vocabulary, which is
not edited): after the hint is applied, a goal type that is not itself a key
of the target's prior is read through `canonical_room()`, and kept as that
canonical type if the prior names it; otherwise none, as today. Order matters:
a name hint ("Lounge") matches the room's own name first (`hinted_prior`), so a
hinted room keeps its 1.0; only an unhinted synonym falls back to its type.

**What must NOT map, and how that is decided.** Only the shared vocabulary
decides, and only whole names: `canonical_room` tokenises the name and looks
the whole of it up, so a name that merely contains a room word is not that room
-- "Kids Den", "Bathroom Closet", "Kitchen Pantry", "Guest Room Closet",
"Ben's Room" read as none. A word the vocabulary maps is mapped as 3.176.A
decided it, even where a household might mean otherwise ("Den" as a playroom is
a living room; "Study" is an office, which the prior does not name, so none):
this step adds no words and removes none; a disputed word is the vocabulary's
to change, with its own bars. A name outside the vocabulary ("Sunroom",
"Playroom") stays none.

**Harness.** 3.183.B's sweep (`evaluations/small-fixes-3183/sweep_b.py`),
copied to `evaluations/room-synonyms-3185/sweep.py` with two more arms over
3.116's 100 selection houses x modes R and U (their rooms carry only the four
canonical types, 479 rooms):
* `names_syn`: each room named by a synonym of its type -- living room ->
  "Lounge", bedroom -> "Guest Room", bathroom -> "Washroom", kitchen ->
  "Kitchenette";
* `names_near`: each room named so that it contains its type's word but is not
  a vocabulary entry -- "Living Room Closet", "Bedroom Closet", "Bathroom
  Closet", "Kitchen Pantry".
The `dev` arms run from INSIDE a `dev` worktree and every record names the
brain it imported (3.180).

**Expected effect, stated before the run.** On `dev`, `names_syn` reads every
room as unknown, so it should equal no names exactly (as 3.183.B's capitalised
names did: 0 of 200 differ from no names, mode R goals 9.78 and metres 32.91)
and differ from `names` in most missions. After the change it should equal
`names` exactly (mode R goals 6.26, metres 21.99). `names_near` should equal no
names on both trees.

**Reported, not a bar: the baseline moved.** The absolute means are not the
ones the expected effect quoted (3.160.D/3.183.B: R goals 9.78 and 6.26):
today's `dev` no-names arm differs from both of 3.183.B's no-names arms
(`b_dev_dev`, `b_branch_dev`) in 15 of 200 missions. This change cannot cause
it (S2 compares this branch with today's `dev`: 0 differ); something merged to
`dev` after 3.183.B's run moved them. Probable cause, not bisected: 3.180.A,
which changes explore's view goals by design; its code reached `dev` at
2026-11-15 06:49 UTC (`4fd20feb`, amendments to `06d5e315`), after 3.183.B's
arms ran (results committed 07:17). A candidate for whoever owns the sweep's
pins.
