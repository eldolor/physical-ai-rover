# 3.130 A staged UX redesign of the twin and consoles

*`PLAN-ros-alignment.md` section 3.130; index: [README.md](README.md).*

**Why.** The user is not happy with the experience of any UI this project
built (2026-10-31). There are three user-facing pages:

* the twin (`web-twin/index.html` and `app.js`);
* the walks console (`control/admin.html` and `admin.js`, served at `/admin`);
* the metrics console (`control/metrics.html` and `metrics.js`, static).

`docs/guides/FEATURES.html` is not deployed. The review behind this section
used 390 px screenshots of every page and two read-only code audits. Six
things are wrong, ranked by how much they hurt:

1. **Nobody is designed for.** Every surface speaks to the engineer who
   built it:
   * The Sim tab names `control/brain_server.py`, "a SLAM map of your
     hallway at R5", and drills tagged "(B3.2)".
   * The Guide HUD uses 15 three-letter codes with no legend.
   * Toasts print raw outcomes: "Mission arrived_unconfirmed".
   * The consoles say "x-app-secret", "persistent volume", and "Replays are
     the controlled evidence -- same pixels, one variable".
2. **The page layout works against the tasks.**
   * Watching a mission means scrolling past the D-pad to 21 monospace
     readouts, or 29 under tiered.
   * Brain missions start on Sim, but their model picker is on Guide
     (`app.js` `2899`).
   * Settings sits behind a 34 px gear.
   * The header always says "sim mode".
   * An idle robot shows its watchdog in alarm red.
3. **Paid actions are silent.**
   * Opening `/admin` runs the paid judge on every unscored walk
     (`admin.js` `scorePendingWalks`).
   * A replay starts when its dropdown changes, with no confirm.
   * No cost is shown anywhere in the consoles.
4. **Real bugs.**
   * The active "Guide me" button is blue on green and unreadable
     (`index.html` `214` against `961`).
   * The metrics page loads with no secret, so a newcomer's first sight is
     an error.
   * Typing in the admin search collapses an open walk.
   * Admin has no doctype, charset, `lang`, `<label>` or ARIA.
   * A walk's name is a `div` that the keyboard cannot reach.
   * The metrics table scrolls sideways at 390 px.
5. **No shared look.**
   * Three palettes (`#12151A`, `#0f1115`, `#0b0e14`) and three corner radii.
   * About 50 hard-coded colours bypass the twin's own tokens.
   * Targets under 44 px: the gear is 34, close is 38, the rotate dismiss is 30.
   * 2 of 17 animations honour reduced motion.
   * No light mode.
6. **The structure makes every change costly.**
   * `app.js` is one 6,691-line closure with 216 `getElementById` calls.
   * There is no string catalogue.
   * About 70 UI-test assertions pin exact jargon.

**Audiences (proposed by the reviewer at the user's request, approved with
the plan 2026-10-31):**

| | Who | Their jobs | Surface |
|---|---|---|---|
| A, primary for the twin | anyone at home with the Rover, on a phone, with no project knowledge | find an object, survey the house, watch progress, Stop, drive by hand, read "found / couldn't find / needs you" | the twin, default (operator) mode |
| B | the engineer (the user, and sessions) | the sim, drills, telemetry, policies and models, recording walks, scoring, replays, metrics | the twin's Engineer mode (today's "Show developer readouts") and one merged Lab console |
| C | demo visitors | the phone-only "Guide me" arrow | kept, as a secondary entry |

A is primary because, once the Rover arrives, the twin is the surface a
person drives from (CLAUDE.md section 7). B keeps every readout.

**The user's choices (2026-10-31):**
* a staged redesign: vanilla JS, no build step, the deploy stays
  `service/static/sync.sh`;
* the twin first;
* the two consoles merged into one with tabs, keeping `/admin` and
  `/metrics` working.

**Constraints carried.** Nothing about how the robot moves changes:
* STOP is `/stop`, through arbitration and `robot/safety.py`.
* 3.84's person-Stop latch stays.
* 3.86's colour rule stays: only a safety veto takes the alarm colour.
* 3.76 D's dropped secret on a moved setup link stays.
* Stored data goes into `innerHTML` only escaped (3.76 F and N2).

Every changed behaviour gets a UI test, seen failing first and run in its
module's real order.

## Stages

Each stage after 0 states its own criteria in an amendment before it is
built. Each one ends with:
* `/code-review`, plus the Thermos pass where the stage is risky (the
  console's judge and replay are paid calls);
* 390 px screenshots in both themes;
* `ready`, then a push to `dev`.

Deploys are asked first.

* **Stage 0: baseline (records only).** A harness measures the metrics
  below on today's `dev`. The same harness judges every later stage.
* **Stage 1: one design system.** `web-shared/ui.css` holds:
  * tokens for colour, spacing, radius, type and motion;
  * dark and light themes;
  * the components.

  The twin's inline style moves out. Every target becomes 44 px, reduced
  motion becomes global, and the Guide-me contrast bug is fixed red-first.
  The new files go in `assets.json` and the static routes.
* **Stage 2: the twin's structure and words.** `app.js` is split into ES
  modules, one behaviour-identical move at a time. `strings.js` holds every
  sentence in two voices, operator and engineer. Outcomes and refusals are
  said plainly. Tests move from exact jargon to `data-state` attributes.
* **Stage 3: the twin's information architecture.**
  * Tabs: Home (Find/Survey, the live mission card, results), Drive
    (camera, D-pad, map), Record (walks, and Guide me) and Settings.
  * A STOP bar is visible on every tab while anything moves.
  * A one-sentence mission card, with the readouts behind Engineer mode.
  * A first-run connection wizard.
  * A header that names the real mode.
  * Idle is neutral, not red.
* **Stage 4: one Lab console.**
  * `control/lab.html` with Walks and Metrics tabs, one secret, and the
    shared CSS.
  * No paid call without a click.
  * Score and replay confirm with an estimated cost, from the token counts
    and the price table the eval tools already use.
  * Labels, keyboard rows, a focus-trapped slideshow, and filters.
  * Metrics as cards at phone width.
* **Stage 5: verify, document, deploy.** The harness's bars become suite
  tests. FEATURES.md, the twin's README and the specs change with the code.
  Deploys are asked first.

## Stage 0: the measurement harness

`evaluations/ux-3130/measure.py` uses Python Playwright and Chromium at
390 x 844. It starts this section's own robot, brain and admin servers
(`plan_section.py env` ports). It serves `web-twin/` from a separate plain
static server, as CloudFront does, so first run is the deployed case. It
writes `results.json` and screenshots to a run directory.

**Page states (12):**

| Page | States |
|---|---|
| Twin | first run, nothing saved (Guide) · Guide connected · Guide's Robot view · Sim idle (robot and brain connected) · Sim with a Find mission running (`frontier` policy, free) · Settings · Engineer mode on, Sim idle |
| Walks console | not connected · connected with walks · a walk expanded |
| Metrics | first open, no secret · loaded |

Light mode is screenshotted too (`prefers-color-scheme: light`).

Walk, model and metrics data come from Playwright route stubs, as in
`tests/test_ui_admin.py`, so no recordings volume, vision service or paid
call is involved.

**Metrics, fixed before measuring:**

* **M1, taps per task.** A scripted path per task counts taps (a click,
  tap or select). Typing into a field is counted apart, as fields. A task
  counts only if its goal state is verified; otherwise it is reported
  failed. The twin starts from its default tab.

  | Task | Goal state |
  |---|---|
  | T1 | first-run connect to the robot server: "Connected" |
  | T2 | start a Find: `POST /mission/start` answered 200 |
  | T3 | start a Survey: the same with `job: survey` |
  | T4 | Stop a running mission from the Guide tab: `POST /mission/stop` or the robot's `/stop` |
  | T5 | one manual FORWARD: `/action` FORWARD sent |
  | T6 | see the mission's state: the element naming it on screen; taps plus the scroll in px needed |
  | T7 | begin a recorded walk with a fake camera: the twin's recording-start request sent, stubbed |
  | A1 | open a walk's frames |
  | A2 | replay a walk under another model: the replay request sent, stubbed |
  | A3 | delete a walk: the DELETE sent, stubbed |
  | A4 | see the metrics with the secret saved by the walks console |

* **M2, accessibility.** axe-core 4.10.3 runs on each state with WCAG
  2.0/2.1/2.2 A and AA rules. It is fetched by version and checked against
  npm's sha512, then cached outside the repo. The count is the serious and
  critical violations (rules, and the nodes they cover).
* **M3, small targets.** The count is visible, enabled, interactive
  elements (button, a, input, select, summary, `[role=button]`,
  `[tabindex]` >= 0) whose box is under 44 CSS px wide or high. Inline text
  links are exempt (`display: inline`, the WCAG 2.5.8 exception).
* **M4, sideways scroll.** Whether the document's `scrollWidth` exceeds
  its `clientWidth` by more than 1 px.
* **M5, jargon in operator mode.** This covers the twin's visible text
  with Engineer mode off, plus toasts and labels' text. It is reported for
  the consoles, which serve audience B, but no bar is set there. A hit is
  any visible text matching the frozen deny-list in `measure.py`:
  * file names (`*.py`, `.yaml`, `.js`, `.json`, `.md`, `.html`);
  * plan codes (`B3.2`, `R5`, `3.84`);
  * snake_case identifiers;
  * `ENV_VARS`;
  * API paths (`/navigate`);
  * the terms SLAM, nav2, ROS, frontier, CLIP, YOLO(E), watchdog,
    tier(ed), x-app-secret, uvicorn, CORS, odometry, deliberation,
    corroboration, p50/p90/p99, drill, preempt(ed), brain service;
  * the HUD codes RMS, CLD, VF, STA, ERR, OUT, LATE, SEQ, OBS, VIS, ACT,
    TGT, VOTE.

  The count is distinct (text, pattern) hits.
* **M6, paid calls without a click.** Requests to paid routes within 8 s
  of opening a page, with no input. The paid routes are the walks
  console's `GET .../evaluation`, any `.../replay` POST, and the cloud's
  `/navigate`, `/room` and `/describe`. In each case the secret and
  services are already saved.

**Bars for the redesign (written now, judged at Stage 5, on the twin's
operator mode and the Lab console):**

| Metric | Bar |
|---|---|
| T4 | Stop takes at most 1 tap from any tab while a mission runs |
| T2 | Find takes at most 2 taps once connected |
| T6 | the mission's state is on screen with 0 taps and 0 scroll from Home |
| M2 | 0 serious or critical |
| M3 | 0 |
| M4 | no sideways scroll on any state |
| M5 | 0 in operator mode |
| M6 | 0 on every page |
| M1 | no other task takes more taps than in this baseline |

**Criteria for Stage 0 itself:**

1. Every one of the 12 states loads, and every task in M1 reaches its
   verified goal or is reported failed with the reason.
2. The harness is repeatable: two runs on the same commit give identical
   M1-M6 numbers.
3. The harness sees what it is meant to see, on today's `dev`:
   * M2 flags the Guide-me button (`#btn-mode-guide`, `color-contrast`);
   * M3 flags the gear (`#btn-settings`);
   * M5 flags `control/brain_server.py` on Sim;
   * M6 counts the walks console's auto-judge.

   Any of the four missing means the harness is wrong, not the page.
4. The baseline is recorded here and in
   `evaluations/ux-3130/baseline/results.json`, with the commit and the
   screenshots. No product code changes in this stage.

**Amendments (written before the recorded baseline runs).**

* **1. T3's goal is the twin's request.** Trial runs, made while building
  the harness, showed that the plain simulator's brain answers 400 to a
  survey: a survey needs explore, and explore needs nav2. So T3's goal
  becomes this: the twin sends `POST /mission/start` with `job: survey`,
  and the harness records the status it gets back. What T3 measures is the
  twin's taps; whether the backend can run a survey is not a UI question.
  T2 keeps its goal of an answer of 200.
* **2. T4 and T6 use a mission the person started on the twin.** The trial
  runs also showed that a twin which is connected and idle never notices a
  mission started elsewhere (the finding below). So the harness starts the
  mission from the Sim panel, uncounted, with a target that is in no house
  so that the mission keeps running. It then goes back to the Guide tab.

**Findings while building the harness (not measured as metrics; for Stage 3).**

* **F1. A mission started elsewhere is invisible to a connected twin.**
  The twin picks up a running mission only when it connects (`app.js`
  `connectBrain`, its `pollBrainOnce`). Once connected and idle, its
  liveness loop pings `/health` and nothing else.

  Reproduced: `POST /mission/start` through the API with the twin open. The
  Sim panel still read "idle" and its button "Start". A tap on that button
  started a second mission request.

  Audience A meets this whenever two phones share the robot, which is the
  observer promise the Sim panel's own text makes.
