# 3.50 Saving and reloading the map: options for the user

*`PLAN-ros-alignment.md` section 3.50; index: [README.md](README.md).*

**A decision document. No code.** Written 2026-10-09 because idea 4
("remember where things were seen, across missions") cannot be built
until the map outlives a session. The user chose "decide map save/reload
first". Idea 4 then builds on this decision plus 3.46's phase C.

Each claim below is marked **[code]** (read in this repo at `origin/dev`
`54b6c4e`), **[upstream]** (slam_toolbox's Humble README or the pinned
source), or **[inference]** (my reasoning, not yet measured).

## The question

When the robot restarts, should it come back on the **same** map, and if
so, how is that map kept honest as the house changes?

## Why idea 4 needs it

* **Every restart is a new map today.** `map_id` is `slam-<session>`
  (`world/ros_world.py:121`), and the session is a random id the bridge
  makes when the container starts (`picar_bridge/bridge.py:123`) **[code]**.
  Nothing is saved: `slam.yaml` runs `mode: mapping` with no
  `map_file_name`, and no serialise or `map_saver` call exists anywhere
  in the repo **[code]**.
* **3.46's inventory is keyed on `map_id` and refuses to mix maps**
  (`brain/inventory.py:283-287`) **[code]**. So, correctly, nothing it
  records survives a restart. A sighting's position means nothing outside
  the map frame it was taken in.
* **3.46's phase E** ("persist with the saved map, `map_id` keyed, beside
  slam_toolbox's pose graph") is exactly idea 4, and it names this as its
  dependency **[code]**.
* In the in-process sim world, `map_id` is a fixed `sim-grid`, so the
  dependency never shows up there. It shows up only under `WORLD_MODE=ros`
  and on the car **[code]**.

## What is already decided (open question 6, 2026-10-01)

* Save slam_toolbox's serialised pose graph and nav2 `map_saver` files to
  a disk that survives restarts (a Docker volume in the sim, the NVMe on
  the car).
* Back them up to a private, encrypted, versioned S3 prefix
  `maps/<robot>/<map_id>/`. This is a floor plan of a home, so the design
  is driven by privacy, not cost.
* **Reload the pose graph and keep mapping on top of it**, so a moved
  sofa fades as it is re-seen, with a fresh map as the fallback. The user
  said "let's go with your recommendation".
* Lifelong mode is ruled out unless pose-graph growth becomes the
  measured problem.

Still open there: where the robot starts on a reloaded map, the
fallback's trigger, and the N/M thresholds. This document closes those,
and asks whether the 2026-10-01 choice still holds now that 3.38-3.40
have measured the furnished house.

## Facts about the tools

* **The pin is slam_toolbox 2.6.10** (`SLAM_TOOLBOX_SHA=1729c0f`,
  `service/slam/Dockerfile:48`) **[code]**. It is built from source for
  `restamp_tf` **[code]**.
* **Serialise and deserialise services exist in the pin**
  **[upstream]**. `DeserializePoseGraph.srv` takes a filename, an
  `initial_pose` and one of four `match_type` values: `UNSET`,
  `START_AT_FIRST_NODE` (the "dock"), `START_AT_GIVEN_POSE`, and
  `LOCALIZE_AT_POSE`. Parameters `map_file_name`, `map_start_pose` and
  `map_start_at_dock` load a graph at start-up.
* **Correction to question 6's text.** It says deserialise offers "a
  whole-map localise". The service definition does not: every mode
  starts from the first node or from a given pose **[upstream]**. So
  **[inference]** the robot must start at a known place or a known pose.
  There is no global relocalisation from nothing.
* **Localisation mode** loads a graph and keeps "a rolling buffer of
  recent scans ... after expiring from the buffer scans are removed and
  the underlying map is not affected" **[upstream]**.
* **Lifelong mode** is described upstream as "**highly** experimental".
  Upstream advises continuing to map until the map is complete, then
  switching to localisation mode "until node decay is implemented"
  **[upstream]**.
* **The serialised format changed in 2021** for 360-degree lidars
  **[upstream]**. Our pin postdates that change. A future slam_toolbox
  bump (question 12, leaving Humble) could orphan saved maps
  **[inference]**.
* **The executables in the image are not verified.** Docker could not be
  run from this session's isolated worktree. **[inference]** The pinned
  build should include `localization_slam_toolbox_node` and
  `lifelong_slam_toolbox_node` alongside the `async_slam_toolbox_node`
  that `picar.launch.py:81` runs. A first step must list them.
* **nav2 takes its static layer from slam_toolbox's `/map`.** No
  `map_server` runs **[code]**. So whatever slam_toolbox publishes after
  a reload is what nav2 plans on.
* **The bridge is at its route cap**: 13 of `MAX_BRIDGE_ROUTES = 13`
  (`tests/test_wall_linters.py:71`) **[code]**. A "save the map" route
  raises the cap. **[inference]** That can be avoided: the bridge already
  polls the brain's `/mission/status` (`bridge.py:186`), so it could
  serialise when a mission ends.
* **The ground-truth error readout depends on the session.**
  `RosWorld._ensure_session()` anchors SLAM's frame to the truth at the
  session's start (`start_truth`) **[code]**. After a reload the map
  frame starts where the first session started, not this one. **[inference]**
  So `start_truth` must be saved with the map, or `/world/error` and
  every criterion measured with it read wrong.

## What 3.38-3.40 add to the risk

* In the furnished house, an 8 m loop-search window closed loops to the
  wrong place in 3 of 3 runs, 1.6-2.5 m off, and never recovered.
* Narrowing the window to 2 m ended that: 0 of 9 runs jumped (3.38).
* Lowering the smear from 0.10 to 0.03 m fixed a 2.5-6 degree bend (3.40).

These are the numbers for ONE session. **[inference]** With the map
reloaded and mapping continued, a wrong closure would be saved and
reloaded every session after, rather than lost at the next restart. The
2 m window bounds how far one closure can move things, but continued
mapping turns an occasional transient error into a permanent one. Every
option that keeps mapping on a saved graph needs a check on this.

## The options

### A. A fresh map every session (today)

*(Annotated 2026-10-11: "today" is the code as of this document. It stays
true until this section is built. As a design it is withdrawn: an empty map
is now the first visit only, and later runs reload the robot's own saved
map. See "Decided by the user, 2026-10-11" below.)*

* **Gives:** nothing new. Zero risk, zero work. Each mission explores
  from scratch.
* **Costs:** idea 4 cannot exist beyond one mission. The inventory stays
  per-mission. Every mission re-explores the house.
* **Inventory / nav2:** unchanged.

### B. Reload and keep mapping (the 2026-10-01 decision)

* **Gives:** one frame across sessions, so `map_id` and inventory
  positions persist. A moved sofa fades from `/map` as it is re-seen, and
  new rooms get added.
* **Costs:**
  * Saving: a volume, plus a bridge save trigger (on mission end, or one
    new route).
  * Saving `start_truth` and a stable `map_id` with the map.
  * The S3 backup.
* **Risks:**
  * **[inference]** A wrong loop closure becomes permanent (above).
  * **[inference]** The graph grows every session, so Ceres time and
    memory on the Jetson rise. This is what lifelong mode exists to fix.
  * Starting away from the dock or the given pose matches badly.
* **Inventory:** positions persist. A landmark that moved is a 3.46 belief
  question (looks from new viewpoints, decay when not re-seen).
* **nav2:** the static layer heals as the robot re-sees the spot.

### C. Save once, then localise against a frozen map

* **Gives:** one frame, bounded compute (a rolling buffer), and no
  growth. A bad closure cannot enter the saved map after the first save.
* **Costs:** as B, plus a deliberate "re-map" action when the house
  changes.
* **Risks:**
  * **Rejected 2026-10-01 for this reason:** a moved sofa stays a phantom
    obstacle in nav2's static layer, because the obstacle layer cannot
    clear it. A phantom across a doorway makes a room look unreachable.
  * A new room is never added.
* **Inventory:** positions persist, and are steadiest of all options.
* **nav2:** plans on the frozen map plus live obstacles. Phantoms remain.

### D. Localise by default; re-map on a trigger (B and C combined, upstream's advice)

* **Gives:**
  * C's stability most of the time.
  * B's healing when it is needed. Continue-mapping on the same graph
    keeps the same frame, so `map_id` and inventory positions survive.
  * Then save a new version, and keep the previous one as a rollback.
* **Costs:** as B and C, plus a trigger. **[inference]** Three candidates:
  * a share of scans contradicting `/map` beyond a bar;
  * nav2 calling a known-reachable area unreachable;
  * the user asking for a re-map.
* **Risks:**
  * The trigger can be wrong.
  * Re-map sessions carry B's closure risk, but only in those sessions,
    and with a version to roll back to.
* **Inventory / nav2:** as C between re-maps, as B during one.

### E. Lifelong mode

**Not recommended.** It is "highly experimental" upstream, and our pin's
behaviour with it is unmeasured. Kept as the fallback if B's or D's
growth is measured as the problem (the 2026-10-01 rule).

## Recommendation

**D, starting from the dock (`START_AT_FIRST_NODE`), with versioned
saves and a fall-back to a fresh map.**

* B's healing is real. But its weak point is the furnished house's
  measured weak point: a loop closing to the wrong place. B writes that
  error into the saved map. D confines it to re-map sessions, each with a
  rollback.
* **Start from the dock.** Since no mode relocalises from nothing, the
  simplest honest start is a fixed spot: the robot begins every session
  where the first mapping session began. On the car that is a marked
  spot or a dock.
* **Use the last saved pose only as a hint**, never as the start. A
  robot carried while off would start from a wrong pose silently.
* **Fall back** to a fresh map, with a new `map_id`, whenever the reload
  matches badly. The inventory then ignores the old map's landmarks
  (3.46 already refuses mixed `map_id`s).

If the user prefers to keep the 2026-10-01 choice (B), the same criteria
apply. Criterion 5 is then the one to watch.

## Criteria (written now, before any build or measurement)

All in the sim under `WORLD_MODE=ros`, on this section's own ports and ROS
domain. Truth comes from `/world/truth`, read by the measurement only.
Unless a criterion says otherwise, each runs on `scaled_house` and on
`home_first_floor`. Stability and progress are paired: 1, 4 and 5 are
stability; 2, 3 and 7 are progress.

1. **The frame persists.** Three sessions, the container restarted
   between them. Each session reloads from the dock.
   * `map_id` is identical in all three.
   * At rest, within 5 s of the first scans, the pose is within **10 cm
     and 3 degrees** of the truth.
2. **A reload costs nothing when nothing changed.** On 3.14's lap after
   a no-change reload, the final error is within **2 cm** of a fresh
   map's on the same lap.
3. **A moved object heals** (B, or D's re-map). Move one object across a
   doorway between sessions (`move_object`).
   * On session 2 the doorway reads free on `/map` within **3 passes**
     (N = 3).
   * A nav2 goal through it succeeds in **3 of 3** tries.
   * Under D this is measured in a re-map session, triggered as D
     specifies.
4. **Localisation survives clutter.** With **3 objects moved** (M = 3),
   the error stays within criterion 1's bars at rest.
5. **No permanent wrong closure.** Over **5 consecutive sessions** in
   `home_first_floor`:
   * **0** jumps over 0.5 m (3.38's metric);
   * the session-5 map's walls still **100%** true (3.40's metric).
6. **Growth is bounded.** After **10 sessions**:
   * p90 scan-processing time and container memory at most **1.5x**
     session 1's;
   * the saved graph at most **50 MB**;
   * reload time on the Jetson at most **10 s**.
7. **Sightings carry over.** A 3.46 landmark recorded in session 1 lies
   within **15 cm** of the same object's truth-mapped position when read
   back in session 2. After a fall-back to a fresh map, **0** old
   landmarks are used.
8. **A bad start is caught.**
   * The robot is started at least 1 m and 30 degrees away from the dock.
     The reload is detected as a bad match within **10 s** and falls back
     to a fresh map in **5 of 5** trials.
   * It never runs a mission on the mismatched frame.
9. **Safety is untouched.** No change to `robot/safety.py` or the
   collars. 3.18's ground-truth sweep is unchanged.

The thresholds above are this document's proposal and are the user's to
amend **before** the first run. A failed criterion is recorded as failed.

## Decided by the user, 2026-10-11 (while reviewing the Claude Doc "ROS 2 for vision-picar")

* **`slam_toolbox` does both mapping and localisation.** nav2's AMCL is
  not used, because AMCL localises on a fixed map and cannot extend it.
  That matches the code: no `map_server` or `amcl` runs, and nav2's static
  layer is `slam_toolbox`'s `/map` **[code]**.
* **Every map the robot builds is saved.** The next run reloads it in
  localisation/lifelong mode, which can still add rooms the robot has not
  seen.
* **Self-built maps only.** The robot is never given the simulator's floor
  plan. A first visit starts from an empty map, and later runs reload the
  robot's own saved map.
* **Maps are stored privately**, because they are floor plans of a home.
  That restates open question 6's private, encrypted, versioned S3 prefix
  and the local disk; it is not a change.

The survey, the missions and the end states that use the saved map are
3.70's.

**How this sits with 2026-10-09's decision (D)** (flagged for the user;
item 2 decided the same day, below it):

1. **Lifelong mode.** D localises against the saved map by default and
   re-maps only on a trigger. Option E (lifelong) was "not recommended",
   and open question 6 says "Not lifelong mode". The new decision names
   lifelong mode as one way to reload.
2. **Localisation mode cannot add a room.** Upstream, it keeps a rolling
   buffer of scans, "and the underlying map is not affected" **[upstream]**.
   Only a mapping session on the reloaded graph (B, or D's re-map) or
   lifelong mode adds cells. So "reloads in localisation mode, and can
   still add rooms" needs one of:
   * (a) D, with "the robot has entered space the saved map calls unknown"
     as a re-map trigger;
   * (b) lifelong mode, which upstream calls "**highly** experimental";
   * (c) B, continue mapping every run, which the user replaced on
     2026-10-09.

   Criterion 11 measures whichever is picked. Criteria 5 and 6 (no
   permanent wrong closure; bounded growth) are the risks that ruled out B
   and E before, and they still apply.

   **Decided by the user 2026-10-11: (a)** ("I will go with your
   recommendation"). D stays: localise on the saved map by default. A
   re-map session on the same graph is also triggered when the robot
   enters space the saved map calls unknown. That is how a reload adds a
   room. Lifelong mode stays ruled out (option E's rule above). D's
   protection holds: a wrong loop closure can enter the map only in a
   re-map session, which saves a new version that can be rolled back.
   "Localisation/lifelong mode" in the decision above reads as D plus this
   trigger.
3. **"Every map is saved"** fits D's versioned saves if each run's map is a
   new version and three are kept locally (the default above).
4. **The start rule** (the dock) is unchanged by the new decision.

**Criteria added 2026-10-11** (written before building; proposed numbers,
for the user to confirm; item 2's choice is (a)). The conditions are
those of 1-9: the sim under `WORLD_MODE=ros`, truth read only by the
measurement, `scaled_house` and `home_first_floor`.

10. **The save/reload round trip.**
    * Run 1 maps from an empty map and saves.
    * The container is restarted. Run 2 reloads from the dock.
    * Before run 2's first new scan:
      * the reloaded `/map` equals the saved map in **>= 99%** of cells;
      * `map_id` is unchanged;
      * the pose is within criterion 1's bars (**10 cm, 3 deg**) within
        **5 s**.
    * *Sim tests:* an offline test of the serialise call and `meta.json`
      against a fake bridge (red first), and the live run.
11. **A reloaded map can add a room.**
    * In run 1, one room's only door is closed with a solid object
      (`move_object`), so the room stays unknown.
    * Run 2 reloads, opens the door and drives a goal through it.
    * After run 2:
      * at least **90%** of that room's truth-reachable floor is known
        free, on `/map` and in run 2's saved map;
      * every other room's walls are still **100%** true (3.40's metric);
      * **0** jumps over 0.5 m (3.38's metric).
    * Measured on (a): D with the "entered unknown space" trigger. The
      re-map session must start within **10 s** of the robot's centre
      entering a cell the saved map calls unknown, and saves a new
      version of the map.
12. **Self-built only.**
    * No code path seeds SLAM, nav2 or a saved map from the simulator's
      layout.
    * A test pins three things:
      * a first run loads no map file;
      * `map_file_name` is only ever a file the robot saved;
      * `start_truth` in `meta.json` is read only by `/world/error`, never
        by the estimate.
    * On a first run, the known cells at the first scan are no more than
      that one scan can see.
    * A sample of truth cells that no scan ever had in line of sight are
      all unknown in the saved map.
13. **No AMCL.** A test reads the launch files and `nav2.yaml`: no `amcl`
    and no `map_server` node. It pins the decision against a later
    "simplification".
14. **Private storage.**
    * A saved map, and 3.70's room labels and object notes, are written
      only to the robot's disk and to the private, encrypted, versioned
      S3 prefix.
    * An empty bucket setting means local only (3.55's lesson with
      `INVENTORY_BUCKET=`).
    * A test asserts the upload asks for server-side encryption.
    * `docs/policy/ARCHITECTURE.md`'s table of what leaves the house (3.52)
      lists the map, in the same commit as the code.

## 3.50.D3 criteria (written 2026-10-23, before building or measuring)

**How D3 reloads.** The bridge starts slam_toolbox itself, not the launch
file, so it can choose the mode and swap it at run time (D4 needs the same).
At container start, with a store mounted and a current map in it, the bridge
starts `localization_slam_toolbox_node` with `map_file_name` (the store's
current version) and `map_start_pose` (0, 0, 0), the dock (the node turns
those into `LOCALIZE_AT_POSE`, 3.50.D1). It then checks the match on the
robot's scans at rest:

* **agreement**: the share of scan returns lying within **0.10 m** of an
  occupied cell of the reloaded `/map`, the median of **5** scans, at least
  **0.60**;
* **at the dock**: the localised pose within **0.5 m** and **15 deg** of
  (0, 0, 0).

slam.yaml's search window is +-0.25 m and +-20 deg, so a robot 1 m and
30 deg off the dock is not pulled back: its scans disagree with the map. If
either test fails, or no pose comes within **8 s** of the node's start, the
bridge stops the node and starts the async node on a fresh map with a new
`map_id`. These numbers are design values written before any measurement;
a run that shows them wrong is recorded, not re-tuned on the same runs.

Until the verdict, `/slam/pose` publishes no map pose and
`start_truth_pending` stays true (so `world/ros_world.py` anchors nothing
and the pose and map read unusable), and `POST /goal` answers 503. A
matched reload reports the saved `start_truth` (the map frame is session
1's), a fresh map this session's. A mission end in localisation mode saves
nothing (localisation cannot serialise, and the map has not changed), and
`/health` says so. `world/ros_world.py`'s own `map_id` stays per session in
D3; carrying it across sessions is D5's (the inventory reads it).

**Measured on this branch's image, its ports and ROS domain 50.** The
saved maps are made once per house by an explore mission ended with Stop
(`scaled_house`, `home_first_floor`). "At the dock" is the sim's start pose,
with a fresh robot server; "off the dock" is the same robot server after a
drive of >= 1 m and a turn of >= 30 deg, with only the container restarted.

* **D3-a (criterion 10, the round trip).** After the map run, container and
  robot server restarted, the reload: the reloaded `/map` equals the last
  `/map` of the map run in **>= 99%** of cells (tri-state), `map_id`
  unchanged, the pose within **10 cm and 3 deg** of the truth within **5 s**
  of the verdict. Both houses.
* **D3-b (criterion 1, the frame persists).** Three such sessions in a row
  per house: `map_id` identical in all three, each within **10 cm, 3 deg**
  at rest within 5 s of the verdict, and again at rest after a 1 m drive
  and a 90 deg turn (so a scan has been matched against the saved map).
* **D3-c (criterion 2).** 3.14's lap in `starter_house` (where the lap is
  defined) after a no-change reload: the final error within **2 cm** of a
  fresh map's on the same lap.
* **D3-d (criterion 4).** Three objects moved (`/sim/objects/move`) before
  the reload: the check still matches (no fall-back), and the pose within
  **10 cm, 3 deg** at rest at the dock and after the drive and turn of D3-b.
  Both houses.
* **D3-e (criterion 8).** Off the dock: the bad match is found and the
  async node on a fresh map started within **10 s** of the localisation
  node's start, in **5 of 5** trials per house; no goal is accepted and no

  the `map_id` is new.
* **D3-f (nav2 held, offline).** Tests, red first: `POST /goal` refused and

## 3.50.D4: the trigger cannot see a moved object (found 2026-10-23, before building)

**Measured** (a probe, not a criterion run; `scaled_house`'s D3 map,
reloaded and matched): with the robot localising, the sofa was moved two
cells (`/sim/objects/move`) and the robot driven 3 m past it. On `/map`
afterwards the sofa's 12 occupied edge cells were **still occupied**, its
new place read **free**, and 31 of 11,174 cells changed in all, every one
unknown -> free. So in localisation mode slam_toolbox's `/map` keeps the
saved map's obstacles and lets the rolling buffer only fill in unknown
space.

**What that does to D4 as decided** (the re-map trigger is "the robot
enters space the saved map calls unknown", 2026-10-11 (a)):

* nav2's static layer is that `/map`, so an object moved INTO a doorway
  since the save is not seen, and one moved OUT of it still blocks it. A
  room behind a door that was closed in run 1 (criterion 11) stays behind
  an occupied doorway: nav2 will not plan through it, the robot never
  enters the unknown room, and the trigger never fires. Criterion 3 (a
  moved object heals) has the same problem.
* The trigger still fires at the saved map's open edges (a frontier explore
  drives to), so rooms reached through an open doorway are added.

**Options for the user** (D4 waits on the choice):

1. **Add a second trigger: the scans contradict the map** (option D's
   first candidate trigger in the plan): a re-map when, for a few scans
   in a row, a share of returns lands in cells the saved map calls free
   (something new), or beams pass through cells it calls occupied
   (something gone). Covers criteria 3 and 11. Risk: people and pets
   (movers) contradict the map too, so the bar has to tolerate them.
2. **Re-map every mission, localise only to check the start.** Simplest,
   always heals, but every mission is a mapping session: B's closure risk
   in every session (the reason D was chosen), and criterion 6's growth
   (one `home_first_floor` session already saved 50.7 MB).
3. **Keep the one trigger and the person's request** (a "re-map now"
   control); criteria 3 and 11 are measured with a person asking.

**Decided by the user, 2026-10-24: option 1** (add the scan-contradiction
trigger; put to them in the 3.76 session). D4 keeps "the robot enters
space the saved map calls unknown" and adds a re-map when, for several
scans in a row, a share of returns lands in cells the saved map calls free
or beams pass through cells it calls occupied. The bar (scans in a row,
share of returns) is written before measuring and must tolerate movers:
measured with `SIM_MOVERS` on, so a person or pet crossing alone does not
re-map, while criteria 3 (a moved object heals) and 11 (a door closed in
run 1) are met.

## Decided by the user, 2026-10-23: D4 is option 1 plus option 3

"Scans contradict + button": the re-map has **three** triggers, and any one
of them starts it.

1. **Entered unknown** (2026-10-11 (a), unchanged): the robot's centre
   enters a cell that the map **as reloaded** calls unknown. It is judged
   against a copy of the first `/map` after `ready`, frozen, because the
   localisation node's rolling buffer fills unknown cells on `/map` itself
   (the probe above).
2. **The scans contradict the map** (new): the bridge compares each scan
   with the frozen map, while localising and `ready` only.
3. **A person asks** (new): `POST /slam/remap` on the bridge, reached as
   `POST /world/remap` on the robot server. The twin's button is its own
   step (3.50.D4b), so this step does not touch `web-twin/` or need a
   deploy.

**The re-map** (as decided for D4): slam_toolbox is restarted as the async
node on the version just localised on (`map_file_name`, `map_start_pose` =
the robot's current map pose), `slam.state` is `remapping` until that node
places the robot, then `ready` again in `mode: mapping`. The `map_id` stays
(the same graph), so the mission-end save writes the next version of it.
The session stays mapping to its end. Goals are refused (503) while
`remapping`, as while `checking`; a goal already in flight is left to nav2.

**The contradiction detector** (`picar_bridge/remap.py`, plain Python, on
the 0.05 m map; numbers written now, before any measurement):

* Only returns within **4.0 m** of the laser are used.
* **Something new:** a return whose cell has no occupied **and no unknown**
  cell within **0.10 m** (`relocalise.AGREE_TOL_M`) on the frozen map. A
  return into unknown is trigger 1's business, not this one's.
* **Something gone:** a cell the frozen map calls occupied that a beam
  passes through at least **0.15 m** short of its own return. A beam with
  no return is not used.
* **Persistent:** a cell counts when, over the last **10 s**, at least
  **10** scans looked at it (a return there or a beam through it) and at
  least **80%** of them contradicted the map there. A person or pet walking
  by (`SIM_MOVERS`: a 30 cm hop a second) does not hold a cell that long.
* **Fires** when at least **10** persistent cells lie in one group (cells
  within 0.15 m of each other): about 0.5 m of edge. A moved sofa showed 12
  edge cells in the probe; a 30 cm mover shows about 6.
* **Not a change, a lost robot:** if fewer than **60%** of the scan's
  returns agree with the map (`relocalise.AGREE_MIN`), the scan is not
  used, and it is counted as `lost`. A re-map on a frame that has slipped
  would save the slip.

**Amendment 1 to D4's detector (2026-10-23, from its offline tests, before
any live run).** Three changes; D4's criteria are unchanged.

* **A hold time, `HOLD_S` 5 s.** "10 scans in 10 s" is one second at
  10 Hz: a person standing for one hop passed it (the offline walker test
  fired). A persistent cell's contradictions must now also span at least
  5 s. A mover that stops longer than that is, for the map, a new object.
* **"Gone" is judged at each beam's expected hit**, the first occupied cell
  the saved map puts on its line, and a beam meeting that surface at under
  **20 deg** is not judged. Counting every occupied cell a beam crosses
  would read a beam grazing a wall, with the pose 2 cm out, as a wall that
  is gone. Once a beam is judged gone, every occupied cell from its
  expected hit to 0.15 m short of its return counts: on the expected cell
  alone a removed 60 x 40 cm box gave 7 cells, under the 10 to fire.
* **Each scan is laid at the laser's pose at its own capture stamp**, not
  the newest transform: turning at 1 rad/s, 50 ms of lag puts a return
  4 m out 20 cm off. A scan whose transform has not arrived within 0.5 s
  is skipped.

**Amendment 2 to D4 (2026-10-23, from the two reviews, before any live
run).** How the swap is made; D4's criteria are unchanged.

* **The swap waits for the robot.** A trigger holds goals at once (503),
  then the swap waits until no goal is live and odometry has been at rest
  for 0.5 s (under 0.01 m/s and 0.02 rad/s), at most **5 s**; a goal still
  live then is cancelled (`re-map`) and rest awaited up to 3 s more. The
  swap goes ahead either way, and the record says what happened
  (`waited_s`, `cancelled_goal`, `at_rest`). Before this, the pose was read
  before the old node stopped (up to 5 s), so a moving robot's re-map began
  from a stale pose and saved the offset, and a goal in flight drove on a
  frozen `map -> odom`. D4-a's 10 s bar now holds the wait too.
* **The pose is composed after the old node stops:** its last
  `map -> odom` with the current `odom -> base_footprint`.
* **A failed re-map localises again** on the same version from that pose
  (`result: failed_localising`); `failed`, with no SLAM, only if that fails
  too. The watch starts over on the same frozen map.
* **The frozen map is the localisation node's first `/map`**, before its
  rolling buffer fills any unknown cell near the dock.
* **"Lost" uses relocalise's tolerance** (a return within 0.10 m of an
  occupied cell's square), so a reload that matched at 60-65% is not read as
  lost by a stricter measure.
* A trigger whose re-map could not start backs off 2 s; a mission end met
  during the swap saves once it is mapping (the Thermos pass's lows).

Kept as it is: `POST /world/remap` is not arbitrated (nothing moves, and
the swap now waits for rest), and it takes any `x-driver`.

**Review round 2 of D4 (2026-10-23, before any live run).** No criterion
changed. A robot still moving after amendment 2's waits now calls the swap
off (`deferred`) rather than swapping under it; a failed re-map latches the
automatic triggers off for the session (both reviewers: a graph the mapping
node cannot load looped); rest needs fresh odometry and no superseded goal
still cancelling; a goal that registers after a re-map began is refused;
the agreement for `lost` is relocalise's own point-to-centre test.

**Design.**
* **Which frame.** The bridge keeps one `map_id` (`map-<8 hex>`) per map:
  the same on every reload that matched, the same through a re-map, new on
  a fall-back or a fresh start. `/slam/pose` adds it as `map_id` once

  fall back to a new id).
* **A new pose field, not a new `map_id`.** `RosWorld`'s `map_id` stays
  `slam-<session>`: the map's ETag (3.123, its version restarts each
  session), the keepout spots' session tag, the room labeller's cut cache

  gains `frame_id`: the saved map whose frame these coordinates are in, the
  same across sessions. Every backend answers it (`None` in the sim's own
  world, before anchoring, and when unusable), so the world contract's pose
  shape gains the key. `RosWorld` sets it only when its anchor came from
  the bridge's start truth (a matched reload replays the saved one) or when
  there is no truth at all (the car: SLAM's frame is the map's); a
  first-contact anchor is not the saved frame, so `None`.
* **The inventory.** It records `frame_id` with `map_id`; frames from a
  pose on another `frame_id` (or, with none, another `map_id`) are
  refused as now. Its report carries `frame_id`, and each carried landmark
  says so (`carried: true`).

  saves what it carried plus what it saw, so the next carries both, once.
  No `frame_id`, or none saved on it: nothing carried. S3 is never read.

**Review round 4 (both reviewers on `23c9760d`; decided as principles, not

**The method** (how each number is read; no other bar changes):

* **A session:** robot server, brain and container fresh (`d3_runs.servers`,
  `container`), on this section's ports, domain and an image built from this
  branch. Session 1 maps from an empty store: explore for an absent target for
  `MAP_RUN_S` (420 s `scaled_house`, 900 s `home_first_floor`). Sessions 2-10

  the next version. A re-map is the only path that grows the graph (a
  localisation session saves nothing), so ten of them are the worst case.
* **Scan-processing time:** slam_toolbox publishes `/pose` once per processed
  scan, stamped with that scan's capture time (`slam_toolbox_common.cpp`
  `publishPose`). A recorder in the container takes receipt minus stamp for
  every `/pose` over the session's mission; the bar is on the p90 per session
  (it includes the scan's wait in the queue, alike in every session).
* **Container memory:** `docker stats` every 5 s over the mission; the bar is
  on each session's peak.
* **Graph size:** after the session's save, the version `current.json` names:
  `graph.posegraph` + `graph.data`.
* **Reload time:** from the bridge's `/health` watched at 10 Hz, `starting` to
  `ready`. On the laptop it is recorded only. The bar is the Jetson's: session
  10's `home_first_floor` store copied to the board, the container started
  there with the simulator on that house on the dock, three reloads, the
  slowest at most 10 s. The board lock is held, `picar-stack` and
  `picar-ngrok` stopped for the bench and put back as found.
* **Criterion 7, per house, in the same chain:** session 1 (criterion 6's map
  run, with `INVENTORY_DIR` kept for the whole chain) records landmarks. Then
  a plain reload (no re-map; not one of criterion 6's ten) starts an explore

  landmarks (at most 60 s). Each carried landmark is judged against the
  truth: the distance from its position to the nearest cell of a simulator

### What was built (written 2026-11-01, before any trial run)

* **Lifelong:** `PICAR_SLAM_LIFELONG=1` (bridge env; off) maps with
  `lifelong_slam_toolbox_node`, both from empty and in a re-map on the saved
  graph; a reload still localises with the localisation node. Upstream builds
  it under `src/experimental/` but does not install it: the Dockerfile adds
  it to the install list and fails the build if it is missing. Its
  parameters are upstream's documented ones (`mapper_params_lifelong.yaml` at
  the pinned SHA: removal score 0.04, overlap scale 0.06, constraint
  multiplier 0.08, IoU match 0.85, minimum score 0.1), added to `slam.yaml`,
  where no other node reads them.
* **The cap:** `PICAR_MAP_CAP=<ratio>` (bridge env; off). The store's meta
  now carries `first_bytes`, the map's first version's graph size, through
  every later version. At a container start, a saved map whose graph has
  grown past `ratio` times `first_bytes` is not reloaded: the session maps
  afresh from the dock (`reload.result: "capped"`, a new `map_id`).
  **Why at the start, not at the re-map** (the user asked for "the next
  re-map starts a fresh map"): a fresh slam_toolbox map's origin is wherever
  it starts, and every later reload assumes the origin is the dock
  (`dock_pose`). A re-map starts wherever the robot is (entering the saved
  unknown happens mid-house), so a fresh map begun there could never be
  reloaded from the dock. The first session start after the map passes the
  cap is the earliest point that keeps the dock as the origin.
* `/health` `slam.lifelong` and `slam.map_cap` name the settings; the harness
  records them and checks that the lifelong executable is the one running, so
  an arm the bridge did not run reads INVALID.

### The proposed threshold (written before measuring)

**`PICAR_MAP_CAP=1.5`: a map is mapped afresh once its graph passes 1.5x its
first version.** 1.5x is criterion 6's own growth bar, and a ratio needs no
per-house number. What follows from it, before any run:

* The cap bounds the graph at about 1.5x the first version plus one
  session's growth: the re-map that crosses the cap still saves. On D5's
  first runs one re-map session nearly doubled `home_first_floor` (53 -> 106
  MB), so **cap only cannot meet the 1.5x bar there** if session 10 is a
  crossing session. It is still bounded, which the uncapped graph was not.
* A capped start is a new `map_id`, so every landmark of the old map is
  dropped (criterion 7's fall-back rule): the cap trades the inventory's
  history for size. The trial records how many sessions were capped.
* Under "both", the cap only acts if lifelong still grows the graph past
  1.5x.

### Amendment 3: the area cap (written 2026-11-02, before building or measuring)

* **What is recorded:** at every save the bridge records `area_m2` in the
  version's meta. That is the known cells (free or occupied) of
  slam_toolbox's `/map` at the save, times the cell area. The meta also
  carries `first_area_m2` beside `first_bytes`, from the same first version,
  with the same carry-over rule (the first recorded value of any kept
  version).
* **The rule:** density = graph bytes / `area_m2`. At a container start, a
  saved map whose density is more than `PICAR_MAP_CAP` (still 1.5) times its
  first version's density is mapped afresh from the dock (`capped`, as now).
  For a version with no recorded area (saved before this amendment), the
  current size rule applies, and before D5 nothing is capped, as now.
* **Why 1.5 again:** on a chain whose first session already covers the
  house (the trial's), area barely changes, so the density ratio is
  roughly the size ratio and the trial's results should repeat. The number
  is not re-tuned.
* **A known weakness, recorded rather than fixed:** a first session that
  circles a small area densely has a high first density, which makes the
  cap lenient for that map. The chains below record each version's density
  so this can be seen.
