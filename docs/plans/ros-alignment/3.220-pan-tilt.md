# 3.220 Pan-tilt camera control on the Rover

*`PLAN-ros-alignment.md` section 3.220; index: [README.md](README.md).*

**Why.** On the car `HardwareRobot.look_left/right/center` answered
`{"pan": None}`: nothing sent the gimbal a command, so the twin's look
buttons and a mission's peek did nothing on the Rover (the user,
2026-11-26). The pan-tilt servos hang off the same ESP32 board as the
wheels, so this section revises the motor-board domain's D9 ("the board is
only the motors"): the board is the motors and the camera's gimbal.

**What the firmware does** (`waveshareteam/ugv_base_ros` @ `2e7df97`,
`ROS_Driver/`, read 2026-11-26):

* `T:133 {X, Y, SPD, ACC}` (`gimbalCtrlSimple()`) clamps X to -180..180
  and Y to -30..90, then writes both bus servos' goal positions:
  `2047 + map(X, 0, 360, 0, 4095)` and `2047 - map(Y, ...)`. Arduino's
  `map()` takes longs, so the angle is truncated to a whole degree first.
  `T:134` is the same with speeds; `T:135` drops both gimbal servos' torque
  for `SERVO_STOP_DELAY` and re-enables it; `T:137` is the IMU steady mode.
* **The command is obeyed whatever the module type** (`uart_ctrl.h`
  dispatches 133-141 unconditionally).
* **The feedback frame reports the gimbal's MEASURED angle only when the
  module type is 2** (`ugv_advance.h baseInfoFeedback()`: `"pan"` and
  `"tilt"` from `panAngleCompute(gimbalFeedback[0].pos)`, which
  `getGimbalFeedback()` reads off the servo bus every loop, again only in
  module type 2). This board's saved module type is 0, so its frames carry
  no angle today.
* **`T:4 {"cmd": 2}` (`changeModuleType()`) sets the module type in RAM
  only**; `T:900` writes it to the boot mission. T:4 therefore turns the
  angle report on for this boot without rewriting the board's boot
  mission, and the host re-sends it with the rest of its set-up after a
  reboot. (Not yet tried on the real board; the board step below.)
* A servo that stops answering keeps its last position in
  `gimbalFeedback` (the failure branch clears `servoFeedback`, the arm's
  array, not the gimbal's), so a dead servo reports a stale angle.
* `T:0` drops every bus servo's torque; the host never sends it (3c).

**How the stack knows where the camera points.** From the board's
measured angle, never from what it commanded. With `hardware.gimbal` on
(`ROBOT_GIMBAL=1`), the set-up sends `T:4 cmd 2` and a centring `T:133`;
a look sends one `T:133`; `HardwareRobot` reads `pan`/`tilt` off every
`1001` frame. The camera frame's `pan_deg` is that measured angle. With
no fresh measured angle (feedback stale, module type still 0, or the goal
not reached in time) `pan_deg` is `null` and a look sends nothing. Off
(the default on the real board until the board step), everything is as
before.

**What safety reads.** `robot/safety.py` picks the depth cone by the
GRID's own `pan_deg` (3.18 part 2), which the depth sensor publishes about
itself; the gimbal's command never reaches it. On the Rover no safety
sensor pans: the lidar and the OAK-D are fixed. In the simulator the
sensor server's grid follows the body's pan, which the fake board's servo
model now drives.

**Criteria (written before building; CLAUDE.md section 7):**

1. **Limits.** Every gimbal command the host sends has |X| <= 90 deg
   (`PAN_LIMIT_DEG`, the URDF's `pan_limit`, set by the camera cable) and
   Y = 0 (`LOOK_TILT_DEG`; the host clamps any tilt to -30..+30,
   `TILT_LIMITS_DEG`, -30 being the firmware's own floor). Measured over
   every look verb and an out-of-range request: 0 commands outside.
2. **`pan_deg` is never a pan the servo did not reach.** In the fake-board
   stack: at rest, the frame's `pan_deg` is within 1.0 deg of the sim
   body's true pan; while moving, the look answer says `settled: false`.
   With the look's command lost (the web route refusing it), the reported
   pan stays within 1.0 deg of where the servo really is (the old angle),
   never the goal.
3. **A lost Wi-Fi command.** The goal not reached within
   `PAN_SETTLE_TIMEOUT_S` = 1.5 s raises `gimbal_fault` in
   `/health`'s `feedback_status()` and `pan_deg` turns `null` until a
   command is reached; a lost command is retried by the route, and a
   further look is still sent (it may get through; its answer says
   `settled: false`). *Amended 2026-11-26, before any run: first written
   "a further look is refused", which would never recover from one lost
   request.* The fault is raised within 1.5 s + one 0.25 s feedback window. No
   wheel command is changed by any of it (a gimbal command is a set-up
   command on the route, 3.217: it can age the route like any other).
4. **The fake board models the gimbal from the firmware source**:
   T:133/134 with their clamps and the whole-degree `map()`; T:135; T:4;
   T:900's module; `pan`/`tilt` in `1001` only in module type 2; a servo
   speed; and it turns the sim body's camera, so the frame, depth grid and
   detections follow the servo, not the command. Each rule pinned by a
   test citing its function. The web face (`FakeEsp32Http`) runs the same
   handler, so it follows for free; pinned by one test.
5. **The twin's look buttons drive it.** The buttons are unchanged
   (`manualAction("LOOK_*")` -> `POST /action`); through the robot server
   in `mode: hardware` on the fake board, `LOOK_LEFT` turns the measured
   pan to -90 +/- 1 deg within 1.0 s, and `LOOK_CENTER` back to 0.
6. **On the real board (open: a desktop session, the board lock, the user
   present).** With the user's go: T:4 cmd 2 makes the `1001` frame carry
   `pan`/`tilt` (yes/no); the look verbs point the camera left and right
   as named (this fixes `PAN_SIGN`, `[PLACEHOLDER]` +1); at +/-90 deg and
   tilt -30..+30 nothing touches the chassis, lidar or cable (by eye); the
   lidar's self box (3.218) still holds at pan +/-90 (no self return
   outside it in 40 scans); the `1001` frame interval with module type 2
   stays at median 50 +/- 5 ms (the servo-bus reads run every loop); a
   look settles within 1.5 s over the web route.

Rule 1 (body state through `RobotInterface`) and rule 4 (safety on every
path) hold: the look verbs are the interface's, they are `CAMERA_ONLY` in
the robot server and move no wheel.
