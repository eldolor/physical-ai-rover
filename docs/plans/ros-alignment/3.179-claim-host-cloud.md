# 3.179 Claim host identity unique per cloud container

*`PLAN-ros-alignment.md` section 3.179; index: [README.md](README.md).*

**Why.** (the user, 2026-11-14, through the orchestrating session.)
`tools/plan_claims.py` `host()` names a machine by a digest of
`socket.gethostname()` and the inode of `/proc/self/ns/pid` (3.139 review:
"two containers sharing a host name (cloud sessions) are two machines").
In Claude Code's cloud containers both are the same in every container:
the host name is `vm` and the pid namespace is the same, so every cloud
claim carries one host, `h-c4e23b41f984`. Each cloud session then reads
another cloud session's claim as made on THIS machine by a process that
has gone:

* `board` and `next` list claimed steps as free (on 2026-11-14: 3.156.E,
  3.175.B, 3.176.A and 3.178.A, all held by live cloud sessions);
* `held()` returns False for them, so the edit, commit and push hooks
  judge them unclaimed;
* `claim` attempts a takeover. It fails today only because cloud sessions
  cannot delete branches; origin's create-only lease is what holds.

Measured in two cloud containers on 2026-11-13/14 (this session and the
orchestrator's): the host name is `vm` in both; `/etc/machine-id` is
`d165c2d8...` in both (baked into the image, so it is no use);
`/proc/sys/kernel/random/boot_id` differs, but it is per boot, and a
worker restart in one session (2026-11-13) would have changed it under a
live claim; `CLAUDE_CODE_REMOTE_SESSION_ID` (`cse_...`) differs between
sessions and survived that restart. In the cloud one container is one
session, so that id names the container for as long as its claims live.
There is no DMI `product_uuid`.

**Scope.** `host()` only, plus its tests and rule 12's text. Ownership is
untouched: `same_owner()` compares sessions first, so a cloud session's
claims made under the old shared digest stay its own. A release path that
works where branch deletes are refused is a candidate, below, not built.

## Design

* **Cloud:** when `CLAUDE_CODE_REMOTE_SESSION_ID` is set and non-empty,
  `host()` = `_digest("h-", f"{hostname}|{pid-ns inode}|{remote session id}")`.
  It is a digest like today's, so the raw id never reaches origin, which is a
  public repository.
* **Anywhere else** (the desktop, the Jetson, a laptop): the same
  expression as today, `_digest("h-", f"{hostname}|{pid-ns inode}")`,
  byte for byte, so every existing claim on those machines still reads as
  made here.
* `PICAR_CLAIM_HOST` still overrides both (tests).

## Criteria (written before building; CLAUDE.md section 7)

1. **Two cloud containers are two machines.** Simulated: the same host
   name and pid namespace, different `CLAUDE_CODE_REMOTE_SESSION_ID`.
   Container B reads A's claim (A's pid not running in B) as **held**:
   * `held()` is True;
   * `board` shows it `claimed`, never free;
   * `next` does not offer it;
   * B's `claim` of that step is refused as claimed, and no takeover is
     attempted (origin's ref is unchanged).
2. **One container is one machine.** With the same remote session id, a
   claim whose process has exited is taken over as today (criterion 5 of
   3.139 holds in the cloud).
3. **The desktop is unchanged (stability).** With no
   `CLAUDE_CODE_REMOTE_SESSION_ID` (unset or empty), `host()` returns
   exactly today's digest of host name and pid namespace. A test pins it
   against the expression copied from `dev` before this change.
4. **Public-safe.** The raw remote session id appears in no claim message
   and no `host()` value; the host field matches `h-[0-9a-f]{12}`.
5. **A legacy cloud claim stays its owner's.** A claim carrying the old
   shared digest and this session's `session` is still this session's
   (`same_owner`), so `release` and the hooks keep working for claims made
   before the change.
6. **The suite:** `tests/test_plan_section.py` and every
   `tests/test_plan_claims*.py` pass, and the fast tier (`ready`) passes.

Each of 1-5 gets a test that fails on `dev` before the change (red first),
where `dev`'s behaviour differs.

## Candidate, not built: a release that needs no branch delete

Cloud sessions cannot delete branches, so `release` (and a takeover)
fails there, and claims outlive their sessions until a person deletes
them. A candidate: release by a lease-guarded **update** of
`claim/<step>` to a "released" record (an orphan commit whose message
says `released`, pushed with `--force-with-lease=<ref>:<sha it holds>`),
which `board`, `next` and `claim` read as free; `claim` then replaces it
with the same lease. Needs its own section and criteria: the hooks' and
gate's reading, races between two claimers of a released ref, and a
cleanup of released refs by anyone with delete rights.
