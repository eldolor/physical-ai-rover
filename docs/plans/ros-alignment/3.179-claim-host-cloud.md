# 3.179 Claim host identity unique per cloud container

*`PLAN-ros-alignment.md` section 3.179; index: [README.md](README.md).*

**Why.** (the user, 2026-11-14, through the orchestrating session.)
`tools/plan_claims.py` `host()` names a machine by a digest of
`socket.gethostname()` and the inode of `/proc/self/ns/pid` (3.139 review:
"two containers sharing a host name (cloud sessions) are two machines").
In Claude Code's cloud containers both are the same in every container:
the host name is `vm` and the pid namespace is the same, so every cloud
claim carries one host, `h-c4e23b41f984`. Each cloud session then reads
another cloud session's claim as made on THIS machine by a process that
has gone:

* `board` and `next` list claimed steps as free (on 2026-11-14: 3.156.E,
  3.175.B, 3.176.A and 3.178.A, all held by live cloud sessions);
* `held()` returns False for them, so the edit, commit and push hooks
  judge them unclaimed;
* `claim` attempts a takeover. It fails today only because cloud sessions
  cannot delete branches; origin's create-only lease is what holds.

Measured in two cloud containers on 2026-11-13/14 (this session and the
orchestrator's): the host name is `vm` in both; `/etc/machine-id` is
`d165c2d8...` in both (baked into the image, so it is no use);
`/proc/sys/kernel/random/boot_id` differs, but it is per boot, and a
worker restart in one session (2026-11-13) would have changed it under a
live claim; `CLAUDE_CODE_REMOTE_SESSION_ID` (`cse_...`) differs between
sessions and survived that restart. In the cloud one container is one
session, so that id names the container for as long as its claims live.
There is no DMI `product_uuid`.

**Scope.** `host()` only, plus its tests and rule 12's text. Ownership is
untouched: `same_owner()` compares sessions first, so a cloud session's
claims made under the old shared digest stay its own. A release path that
works where branch deletes are refused is a candidate, below, not built.

## Design

* **Cloud:** when `CLAUDE_CODE_REMOTE` is `true` and
  `CLAUDE_CODE_REMOTE_SESSION_ID` is non-empty, `host()` =
  `_digest("h-", f"cloud|{remote session id}")`. The host name and pid
  namespace are left out there: they are the same in every container, so
  they add nothing. (The pid namespace inode measured is `0xeffffffc`, the
  kernel's initial namespace, the same on every machine that has one.) It
  is a digest like today's, so the raw id never reaches origin, which is
  public. Requiring `CLAUDE_CODE_REMOTE=true` (review round 1) keeps a
  desktop or Jetson session that inherits a remote id, through Remote
  Control, on its machine's digest.
* **Anywhere else** (the desktop, the Jetson, a laptop): the same
  expression as today, `_digest("h-", f"{hostname}|{pid-ns inode}")`,
  byte for byte, so every existing claim on those machines still reads as
  made here.
* `PICAR_CLAIM_HOST` still overrides both (tests).

## Criteria (written before building; CLAUDE.md section 7)

1. **Two cloud containers are two machines.** Simulated: the same host
   name and pid namespace, different `CLAUDE_CODE_REMOTE_SESSION_ID`.
   Container B reads A's claim (A's pid not running in B) as **held**:
   * `held()` is True;
   * `board` shows it `claimed`, never free;
   * `next` does not offer it;
   * B's `claim` of that step is refused as claimed, and no takeover is
     attempted (origin's ref is unchanged).
2. **One container is one machine.** With the same remote session id, a
   claim whose process has exited is taken over as today (criterion 5 of
   3.139 holds in the cloud).
3. **The desktop is unchanged (stability).** With no
   `CLAUDE_CODE_REMOTE_SESSION_ID` (unset or empty), `host()` returns
   exactly today's digest of host name and pid namespace. A test pins it
   against the expression copied from `dev` before this change.
4. **Public-safe.** The raw remote session id appears in no claim message
   and no `host()` value; the host field matches `h-[0-9a-f]{12}`.
5. **A legacy cloud claim stays its owner's.** A claim carrying the old
   shared digest and this session's `session` is still this session's
   (`same_owner`), so `release` and the hooks keep working for claims made
   before the change.
6. **The suite:** `tests/test_plan_section.py` and every
   `tests/test_plan_claims*.py` pass, and the fast tier (`ready`) passes.

Each of 1-5 gets a test that fails on `dev` before the change (red first),
where `dev`'s behaviour differs.

## The cost, named (review round 1, the Thermos pass)

* **A cloud claim outlives its container until a person frees it.** Once
  each container is its own machine, a claim left by an ended container
  reads as another machine's: held, shown `claimed (stale?)` after 24 h
  without commits, and freed only by the user (`release --force`). Before
  3.179 it read as free and would have been taken over, but in the cloud
  that takeover deletes the old branch, which is refused there. So in
  practice a cloud claim already needed a person, and nothing is lost. The
  candidate below is the fix.
* **Claims already on origin under the old shared digest** (all eight on
  2026-11-14 carry `h-c4e23b41f984`, each with a session) stay their own
  sessions' through `same_owner` (criterion 5). For every other session
  they are now held, not free. Ones whose sessions have ended need the
  user's `release --force`, a one-off cleanup.
* **A session-less cloud claim** (no `CLAUDE_CODE_SESSION_ID`) made before
  the change would not be its owner's after it. None exists on origin
  (2026-11-14), and every cloud session exports a session id.
* **Hooks** compute `host()` in their own process. `tools/hooks/pre-commit`,
  `pre-push` and `.claude/hooks/plan-board.sh` inherit the environment
  (checked in review). A process with a scrubbed environment would compute
  the desktop digest. It fails closed for other containers' claims, and
  its own claims stay its own through the session.

## Candidate, not built: a release that needs no branch delete

Cloud sessions cannot delete branches, so `release` (and a takeover)
fails there, and claims outlive their sessions until a person deletes
them. A candidate: release by a lease-guarded **update** of
`claim/<step>` to a "released" record (an orphan commit whose message
says `released`, pushed with `--force-with-lease=<ref>:<sha it holds>`),
which `board`, `next` and `claim` read as free; `claim` then replaces it
with the same lease. Needs its own section and criteria: the hooks' and
gate's reading, races between two claimers of a released ref, and a
cleanup of released refs by anyone with delete rights.

## 3.179.B: release where branch deletes are refused (2026-11-15)

**Why now.** (the user, 2026-11-15, through the orchestrating session:
"keep going".) Since 3.179.A an ended cloud session's claim stays held, and
one session holds a section, so a finished step keeps its whole section
locked (3.175 and 3.176 are each locked to a session on 2026-11-15). Cloud
sessions cannot release: a branch delete through the cloud's git proxy
fails with `HTTP 403` (measured 2026-11-15 on a throwaway ref, below), which
`release` reports as origin not answering.

**Measured first (2026-11-15, throwaway ref
`refs/heads/claim-test/3179b-probe-1`, left on origin because the cloud
cannot delete it):**
* create with an empty lease: works;
* delete with a lease: `HTTP 403`, the ref unchanged;
* a non-fast-forward update to an unrelated orphan commit with
  `--force-with-lease=<ref>:<sha it holds>`: works (`forced update`);
* the same update with a stale lease: `! [rejected] (stale info)`, the ref
  unchanged.

So a lease-guarded update is a compare-and-swap that works where deletes
are refused.

**Design.**
* **A released record** is an orphan commit on `claim/<step>` whose
  message's first line is `released <step>`, followed by `by:` (the
  releaser's session digest), `forced:` (`yes` for the user's
  `release --force`), `was:` (the sha of the claim it replaced) and `at:`
  (UTC). Digests and shas only: public-safe.
* **Release:** delete with a lease, as today. If the delete fails and
  origin did not refuse the lease (a `403`, or any other non-lease error),
  update the ref to a released record with a lease on the claim's sha. A
  lease refusal on either means someone changed the ref since it was read:
  nothing is overwritten.
* **Reading:** `remote_claims()` never returns a released record as a
  claim. So `board`, `next`, `claim`, `release`, the hooks and the push gate
  all read it as no claim. `claim` gets the released sha separately to
  lease against.
* **Claim over a released record:** one push replaces it with the new
  claim, `--force-with-lease=<ref>:<released sha>`. A lease refusal means
  another claimer won: refused as claimed.
* **Takeover of a dead same-host holder:** delete then create, as today.
  If the delete fails without a lease refusal, the new claim replaces the
  dead one in one leased push instead.
* **A rival found after claiming** withdraws its claim the same way as a
  release (delete, else a released record).
* `plan_section.py new` still counts every `claim/3.N` ref, released or
  not, when reserving a number (unchanged).

**Criteria (written before building).**
1. **Release in a cloud container** (deletes refused, simulated by an
   origin whose `pre-receive` hook refuses ref deletions): `release` leaves
   `claim/<step>` holding a released record whose `was:` is the claim's sha,
   and reports the step released. The local claim file is gone.
2. **Read as free:** after 1, `board` shows the step `free` and `next`
   offers it; the hooks' readers (`remote_claims`, `Board.live`) hold no
   claim for it.
3. **Claimed again by a lease-update:** another session's `claim` succeeds
   and `claim/<step>` holds its claim.
4. **Never over a live claim:** a released-record update or a replacing
   claim pushed against a stale lease (the ref moved since it was read) is
   refused, and the ref keeps the newer commit.
5. **No two holders:** two claimers of one released step, racing from two
   clones (two `.git`, two local locks): exactly one wins, the other is
   refused as claimed (20 racers, as 3.139 criterion 1).
6. **The user's `release --force`** works the same way where deletes are
   refused (a released record with `forced: yes`).
7. **Where deletes work, release still deletes** (the ref is gone, no
   record; 3.139's tests unchanged and passing).
8. **A legacy claim** (the old shared digest, its owner's session) is
   released by its owner with it.
9. **Public-safe:** a released record holds no raw session id, host name
   or path: only `h-`/`s-` digests, shas and the time.
10. **The suite:** every `tests/test_plan_claims*.py` and
    `tests/test_plan_section.py`, then `ready`.

Each of 1-6 and 8 fails on `dev` first.

**Results (2026-11-15).** `tests/test_plan_claims_3179b.py`, 13 tests. Against
`dev`'s `tools/plan_claims.py` 9 of the first 11 fail (criteria 1-6, 8, 9
and the record's later deletion). The 2 that pass pin `dev`'s behaviour
(criterion 7's delete, and another session's claim untouched without
`--force`). With the change all 13 pass, and so do the 131 claim and
plan-section tests. The race (criterion 5, 20 racers on two clones) passed
10 runs of 10. **The race and criterion 4 caught a real bug while
building:** a `+` on the replacing push's refspec overrode the lease, and
two racers both won. The refspec carries no `+`, and the line says why.
Criteria 1-9 **met**; 10: `ready` below.

**Review round 1** (`/code-review` 9 findings, the Thermos pass 5).
* **Fixed:**
  * only a refused delete (a 403, `[remote rejected]`, `declined`,
    `prohibited`) falls back to a released record; a timeout does not,
    which also stops the doubled wait (new test);
  * the same rule for a dead holder's takeover;
  * a claim whose lease is refused but finds no holder (a released record
    deleted or released again since the board read it) tries once more
    against what is there, instead of refusing a free step (new test);
  * the messages and `release`'s docstring now say "give back", and the
    commit helper's error is no longer claim-specific;
  * the guide says a released `claim/3.N` still reserves its number;
  * criterion 9's test checks every field's form instead of searching for
    the host name.
* **Checked, not a bug:** the Thermos pass's HIGH finding (an unreadable
  claim commit read as a dead local claim and overwritten). An empty
  message gives host `?`, which is held, and `remote_claims` returns
  "could not read the holder", so `claim` and `release` refuse before any
  push.
* **Named, not changed:**
  * released records pile up until someone whose origin allows deletes
    removes them (and an unreadable one blocks claims, as any unreadable
    claim does);
  * a release whose lease lost to a newer claim reports the step given
    back, as a delete did before.
