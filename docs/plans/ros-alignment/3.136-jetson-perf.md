# 3.136 Performance tests on the Jetson, run from the desktop

*`PLAN-ros-alignment.md` section 3.136; index: [README.md](README.md).*

**Why.** The user (2026-11-01): a list of performance tests for the Jetson in
the plan, like the third item named that day (3.74.C, floor hazards:
perception given more to do). The board's numbers so far were each measured
once, for the section that needed them (3.33, 3.80.E, 3.81, 3.87, 3.125.B,
3.131), and several sit on thin margins: F-large's whole choice 95.2 ms
against 100 in one scored run (3.131; live choices with real seen cells run
over it), arrival to verdict 1.91 s against 2.0 over five arrivals (3.80.E),
VE's margin over the memory floor ~500 MB (3.81). This section re-measures
them together, on one commit, with enough samples to trust a p90, and adds
the latencies never measured on the board (a safety stop, a person's Stop
under load, a cold start, sustained heat). Companion section: 3.135 (FMEA
and resiliency tests on the Jetson).

**How the tests run (the user, 2026-11-01: from the desktop, which reaches
the board).** As 3.135: the harness in `evaluations/jetson-perf-3136/` on
the desktop, a git checkout of the commit under test copied to the board
(3.131's `board_time.sh` method), every board run under `board_lock.py run
--why 3.136` and a desktop lock (exclusive for the timed runs, 3.128),
`picar-stack` / `picar-ngrok` stopped first and the board put back as found
after (`tools/jetson/README.md` sections 4-5). Existing harnesses are reused
where they fit: `headroom_identity.sh` (`RUNTIME=trt`, VE's engines, the
full stack), `headroom_mission.sh`, `perception_loop.py`,
`bench_local_vlm.py`, `memory_account.py`, 3.131's `board_time.sh`.

**Every timed run is valid only if** (3.131's rule): the bench ends inside
the full-stack window, the window has 0 late wheel ticks and 0 OOM kills,
nav2's goals all succeeded, the board is at 15 W, and the desktop's load is
recorded. An invalid run is run again, not scored. Quiet-board numbers are
reported beside the full-stack ones, with no bar. Temperature is recorded
for every run (`tegrastats` on JetPack 6 prints no throttling, 3.76 P1, so
clocks are read from sysfs as well).

"Full stack" below means: the robot server in sim mode (fake board, fake
lidar), the brain on a tiered explore mission, the ROS container
(`vision-picar-ros:latest`) with nav2, YOLOE + CLIP, and VE resident.

## The tests

| ID | What | Measured how, on the board | Bar (written before measuring) |
|---|---|---|---|

| P2 | **Floor-hazard prompts' cost** (3.74.C, the item named) | P1 again with YOLOE given 3.74.C's five hazard classes (`cable`, `sock`, `shoe`, `pet bowl`, `toy`) beside the target, on the same frames | perception p90 **<= 250 ms** with them, and their added memory **<= 100 MB** (`MemAvailable` minimum against P1's); 3.74.C3's steering criteria stay 3.74's, run in the sim |
| P3 | Goal choice on live maps | `status.explore.choice_ms` from 5 explore missions on the board, `explore_goal_policy: rooms` (explore's real seen cells, not 3.96's benchmark) | p90 **<= 100 ms** (3.96 criterion 6); 3.131's caveat says it may not be met: recorded either way |
| P4 | Wheel loop under the worst overlap | a 30 min run where explore's map fetch, a frame question to VE, perception, the room cut and a SLAM map update overlap (the harness counts how often all of them overlap) | **0 late ticks**, `max_dt_s` reported (3.87's H3 margin: 99 ms) |

| P10 | Sustained heat | 60 min of back-to-back missions on the full stack at 15 W, the room temperature recorded | max SoC temperature reported against the throttle point; perception p90 in the last 10 min within **10%** of the first 10; clocks never below the 15 W mode's maximum |
| P11 | SLAM and nav2 keep pace | during P4: slam_toolbox's scan-to-map lag (3.40's capture stamps), nav2's controller loop rate against its configured rate | controller **>= 90%** of its rate; scan skew p90 reported (3.40: 7 ms) |
| P12 | Map and room work | during P4: `/world/map` reply time and bytes (3.123/3.126's ETag and 304), `segment()` and spacing's walk per call | pause on the mission thread **<= 10%** (3.118/3.120: ~4-9%); the rest reported |
| P13 | `[rover]` The same on the Rover | P1-P12 and P14 with the real camera, lidar and motor board, after 3.26 | waits for 3.26 |
| P14 | **Power draw, and the runtime it implies** (added 2026-11-01 for 3.137) | the board's input power from `tegrastats`' `VDD_IN` at 1 Hz: quiet, parked with the full stack, and during a tiered explore mission, 10 min each | reported, no bar: mean and p90 watts per state, and the runtime they imply on the Rover's ~20 Wh usable (3.137's estimate is ~16 W parked, ~20 W searching, before motors and the OAK-D, which only the Rover adds) |

**Criteria (written before building; CLAUDE.md section 7; confirmed by the user 2026-11-01):**

1. **Each row's bar, on one commit of `dev`**, every timed run valid by the
   rule above. A failed row is recorded FAILED with its numbers and becomes
   its own plan section for the fix; it is not re-scoped here.
2. **Enough samples:** each p90 from >= 200 samples (P5 and P6's p99 from
   their stated counts, recorded as "p99 of 40" / "p99 of 20": the run
   counts are the bar), and the timed rows run twice on different days; the
   two runs' p90s are reported side by side, and a row passes only if both
   do.
3. **The harness tells the truth:** each timed row run once on the desktop's
   local stack with a planted delay (100 ms added where it measures) must
   show that delay to within 10%.
4. **The board is left as found** after every run, checked by the harness
   and recorded.
