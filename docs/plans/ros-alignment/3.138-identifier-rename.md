# 3.138 Rename the code's own identifiers from vision-picar to the new name

*`PLAN-ros-alignment.md` section 3.138; index: [README.md](README.md).*

**Why.** The project is now the **Physical AI Autonomous Rover**: the GitHub
repo was renamed `eldolor/vision-picar` -> `eldolor/physical-ai-rover` on
2026-11-01, and the markdown files' prose was updated the same day (only
where "vision-picar" named the project). Everything that is a real
identifier kept the old name, because renaming it in the docs alone would
make the docs wrong. The user (2026-11-01): "Save that step in the plan for
later." Nothing here is started; every step waits on the user's go.

**What still carries the old name (inventoried 2026-11-01 on `dev`
`621d6980`), by how hard it is to change:**

* **What a person sees** (repo only, then a twin deploy): the twin's
  `<title>`, its `<h1>vision-picar</h1>` and `manifest.json`'s `name` (the
  home-screen name); the Lab console's `<title>`; the FastAPI titles of the
  robot, brain, admin, sim and local-VLM servers (their `/docs` pages).
* **Logged identity strings** (repo only): `log_identity("vision-picar robot
  server" ...)` and its brain and sim-body twins, which `/health`'s
  `identity.service` carries. Docs quote them
  (`docs/engineering/control-api/`, `docs/engineering/mission/`), and a log
  search for the old string would stop matching.
* **Repo-wide conventions shared by parallel sessions:** the ROS image
  `vision-picar-ros` (`:latest` on the desktop and the Jetson, and
  `:plan-3.N` per section from `tools/plan_section.py env`),
  `EXPLORE_LOGDIR=/tmp/vision-picar-3.N`, the test host `vision-picar.test`
  (`tests/test_ui.py`), the text-feature cache
  `~/.cache/vision-picar/text-features`, and the nightly's
  `~/Library/Logs/vision-picar/`. Renaming any of these under a running
  session breaks that session.
* **Files on the machines:** `~/.vision-picar-local-secrets` (desktop, Mac,
  Jetson), `~/.vision-picar-local-vlm.env` (Jetson, read by
  `picar-local-vlm`), `~/.vision-picar-serverless-secrets`, the tunnel's
  `/tmp/vision-picar-tunnel.log`, and the Jetson's worktrees
  (`~/vision-picar`, `~/vision-picar-service`, which `picar-stack` runs
  from). The systemd units are already `picar-*`.
* **AWS** (deploys, and costs while both copies exist): the stack
  `vision-picar-serverless`, the buckets
  `vision-picar-recordings-303351622021-us-east-2` and
  `vision-picar-deploy-303351622021-us-east-2`, Secrets Manager's
  `vision-picar-*-shared-secret`, and the EC2 tags in `tools/gpu/` and
  `tools/hailo/`. Neither S3 buckets nor CloudFormation stacks can be
  renamed: each means a new one, a copy, every reader moved over, then a
  delete.
* **The local checkout** `/home/anshu/vision-picar`: every worktree's path,
  and Claude Code's memory directory, are keyed on it.
* **Records, never rewritten:** `evaluations/` (~208 files of recorded
  output and paths), `docs/archive/`, and every dated plan, handoff and
  review that quotes an identifier as it was, plus the Claude Doc "ROS 2
  for vision-picar" (its own title).

**Recommendation (for the user to confirm):** do A, and B on a day no live
run or board bench is in flight. Do C only if a reason beyond the name turns
up: the AWS names are seen by no one but the engineer, and the move costs
deploys and a window with two of everything. D never, or last (it moves
every worktree and the memory directory).

**Criteria (drafts, to be confirmed by the user before any step starts;
CLAUDE.md section 7):**

1. After each step, the full suite passes (`ready --full`) and
   `git grep -i 'vision[-_]picar'` outside the records above lists only
   names that step leaves on purpose, each named in this section.
2. A: the deployed twin's title, header and home-screen name read the new
   name (a 390 px screenshot, and `curl` parity of `index.html` and
   `manifest.json` against `HEAD`); `/health` names each service by the new
   name on both servers.
3. B: during a transition of one release, every renamed file or path is
   read under its new name first and its old name second, so a machine not
   yet migrated keeps working; after migration the Jetson's stack comes back
   (`picar-stack`, `picar-local-vlm`, `picar-ngrok`) and the deployed twin
   connects, under the board lock.
4. C (if taken): no lost object (object counts and total bytes equal in the
   old and new buckets before the old is emptied), the walks Lambda and the
   consoles read the new names, and the old resources are deleted only on
   the user's word.
