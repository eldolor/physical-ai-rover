# 3.135 FMEA and resiliency tests on the Jetson, run from the desktop

*`PLAN-ros-alignment.md` section 3.135; index: [README.md](README.md).*

**Why.** The user (2026-11-01): a list of failure-mode (FMEA) and resiliency
tests for the Jetson in the plan, holding the two open items named that day
-- a long memory soak on the board (Stage 5's "memory-trend soak on the
Jetson", open) and S7 (chaos and soak, not started). Each failsafe so far was
shown once, mostly in process on the laptop or desktop (B3's drills, 3.84,
3.104, 3.80.E's OOM drill); none has been run on the board, under the whole
stack, with the faults coming one after another. 3.81 left ~500 MB over the
user's 0.5 GB floor (VE killed first), and 3.80.E criterion 6 FAILED on one
late wheel tick (0.127 s) as memory ran out, so a slow leak or a fault under
memory pressure is what the Rover would meet first. Companion section: 3.136
(performance tests on the Jetson).

**How the tests run (the user, 2026-11-01: "I will use the desktop to run
them because it has access to the jetson").** Every test is started from the
desktop, which reaches the board over ssh:

* The harness lives in `evaluations/jetson-fmea-3135/` on the desktop, and
  copies a git checkout of the commit under test to the board, as 3.131's
  `board_time.sh` does (`restart.sh` needs a git checkout, 3.131).
* Each board run is held under `python tools/jetson/board_lock.py run --why
  3.135 -- ...` (3.93), and a shared desktop lock (`tools/desktop_lock.py`,
  3.128) while it runs.
* Before a run: `picar-stack` and `picar-ngrok` stopped
  (`tools/jetson/README.md` sections 4-5), the local VLM held with
  `vlm_hold.sh` where a test brings up its own; after: the board put back as
  found (units, the hold flag, `~/.vision-picar-local-vlm.env`), checked by
  the harness, not assumed.
* The stack under test is the board's real one in **sim mode**: the robot
  server with `SIM_MOTOR_BOARD=fake` and `SIM_LIDAR=fake` (the firmware copy
  and the D500 on ptys), the brain, the ROS container
  (`vision-picar-ros:latest`, or this section's own tag if a fix needs one),
  YOLOE + CLIP, and VE through `picar-local-vlm`. Sim mode gives ground
  truth, so every "the robot stopped" below is judged on the simulator's
  true pose (`tests/footprint_sweep.py`'s rule), never on the readings the
  guards use (CLAUDE.md section 6, Safety).
* Faults are injected from outside the processes wherever possible
  (`kill -9`, `SIGSTOP`/`SIGCONT`, `docker kill`/`pause`, stopping a pty's
  writer, a vision URL pointed at a local listener that refuses or never
  answers) so the code under test is the shipped code. No `sudo` on the
  board without asking the user first (a clock step and a reboot each say
  so in their row).
* **Faults only in sim mode.** Nothing here runs with the Rover's motors
  until 3.26's arrival checks are done; the rows marked `[rover]` wait.

**Measures every test reports** (the progress half, section 7.4, is the
recovery: the robot's next mission).

* *Stopped:* true distance moved from the fault to rest, and the time to
  wheels zero (the fake board's setpoint log, monotonic stamps).
* *Contacts:* ground-truth contact samples, 0 everywhere.
* *Wheel loop:* `late_ticks` (dt > 2 x the 50 ms interval) and `max_dt_s`
  over the test's window, from the robot server's `wheel_loop` block.
* *Memory:* `MemAvailable` minimum, OOM kills from `/proc/vmstat`.
* *Outcome:* the mission's end state and reason as the brain reports them,
  and what the twin's status would show (3.86's readout names).
* *Recovery:* time from the fault's end until a new mission starts, and
  that mission's outcome, with no person touching the board.

**Criteria (written before building; CLAUDE.md section 7; confirmed by the user 2026-11-01):**

1. **Memory soak (F1).** On the board at 15 W, the stack in sim mode with VE
   resident and `tier_local_vlm_url` set, **4 hours** of back-to-back tiered
   missions with `tier_search: explore`, cycling `SIM_MAP` over
   `home_first_floor`, `complex_house` and three ProcTHOR houses, and a new
   target every mission from a list of 8 (so 3.81.E's new-target path runs
   every time), the cloud a local stub that answers. Sampled every 5 s:
   `MemAvailable`, each process's RSS and the GPU share (`memory_account.py`).
   * (a) `MemAvailable` minimum **>= 500 MB** for the whole run (the user's
     floor, 2026-10-14);
   * (b) the least-squares slope of each mission's `MemAvailable` minimum
     over the last 3 hours **>= -10 MB/h** (no trend that would cross the
     floor in a working day), and no process's per-mission minimum RSS grows
     by more than **50 MB** from hour 1 to hour 4;
   * (c) 0 OOM kills, 0 late wheel ticks;
   * (d) progress: >= 90% of missions end `found` (the sweeps' rate on these
     houses reported beside it) with 0 contacts.
   A run that dies of a cause outside the stack (the desktop loses the
   board, a power cut) is run again, not scored, and recorded.
   *Why 4 hours (amendment 1, 2026-11-01, before any run):* one power-on on
   the Rover's pack is estimated at ~1.0-1.5 h (3.137), so 4 h is ~3
   charges' margin, and covers a session on the charger (3.137.D). The soak
   runs on the board's wall supply, never its battery.
2. **Chaos soak (F19, S7).** On the board as in 1, missions as in 1, sized
   by faults, not hours (amendment 1, 2026-11-01, before any run): **at
   least 40 faults, one every 3-7 minutes** (seeded, uniform; ~3.5 h), drawn
   from F2, F3, F4, F5, F6, F7, F9, F10, F11, F12 and F17, each cleared by
   the harness after its row's duration. Once 3.137.A is merged, every
   ~60 min of the run is one simulated charge: the fake board drains to
   Power-off (F24, the power-off stubbed), then is reset to full and a new
   charge begins.
   * (a) every fault meets its own row's stop bar on ground truth;
   * (b) 0 contacts over the whole run;
   * (c) recovery without a person: after every fault a new mission is
     running within **90 s**, and no fault leaves a service down at the end;
   * (d) progress: missions with no fault in their window end `found` at
     >= 90%, and no end state is wrong for its fault (`found` only where an
     identity check really passed, 3.47's rule);
   * (e) criterion 1's memory bars hold over the whole run.
3. **Single faults (F2-F18, and F24 once 3.137.A is merged).** Each row's pass on the board, with the run
   counts in the row. A row that fails is recorded FAILED with its numbers
   and becomes its own plan section for the fix; it is not re-scoped here.
4. **The harness tells the truth.** Before any board run, on the desktop's
   local stack: each injector run once against a build with the guard it
   tests switched off (a planted bug: the watchdog disabled, the lidar
   freshness check removed, VE's OOM score at 0) must FAIL its row. A row
   whose planted bug passes is not scored until the harness is fixed.
5. **The board is left as found** after every run: units, the VLM hold flag
   and its env file as before, checked by the harness and recorded.

**Amendment 3 (3.135.C, 2026-11-02, written before the smoke run and the
scored run; no bar changed).** How criterion 1's workload is built and how
each bar is read off it (`evaluations/jetson-fmea-3135/soak.py`, `soak.sh`,
`soak_score.py`; `run.py soak`):

* *The stack is restarted with each house.* `SIM_MAP` is a start-time
  setting of the split body's programs and SLAM keeps its own map, so a
  house can change only by a new stack: each mission starts a fresh stack
  (`stack.py`: `truth_body.py`, two sensor programs, the fake D500, the robot
  server, the brain, on this section's ports; `ROBOT_DRIVE=ros`,
  `WORLD_MODE=ros`, `TIER_SEARCH=explore`, `LOCAL_VLM_URL` at the board's VE
  with the unit's own secret) and a fresh ROS container
  (`vision-picar-ros:latest`, no map volume, so every mission maps from
  empty), torn down after it. Every other brain setting is the default
  (`explore_goal_policy: rooms`, `find_room_labels: off`,
  `mission_time_limit_s` 1200). What lives for the whole 4 h: **VE, the
  board's own `picar-local-vlm` unit, as found** (never held, stopped or
  restarted by the harness; its PID and restart count recorded before and
  after), **YOLOE + CLIP** (`tools/jetson/perception_loop.py` at 4 Hz on the
  recorded frames, switched to each mission's target with
  `PERCEPTION_SWITCH_RELEASE=1`, i.e. 3.81.E's new-target path, every
  mission: in the simulator the brain's tiered perception is ground truth and
  loads no model, so this loop is the stack's perception), the $0 cloud
  stand-in (`evaluations/tiered-380/E/standin_cloud.py`), the docker
  daemons and the system. The stack's processes and the perception loop run
  at `oom_score_adj` -900 (`picar-stack`'s), VE at its unit's 1000. As
  3.136.B: the desktop off (`multi-user.target`), the twin's units stopped,
  15 W recorded. **So (b)'s per-process half can find a leak across the 4 h
  only in what lives 4 h**; a leak inside one stack's life (one mission,
  <= ~25 min) shows as that role's in-mission growth, reported beside with
  no bar. A soak of one house with no restarts would be a separate step.
* *Houses and targets.* Missions take the houses in turn:
  `home_first_floor`, `complex_house`, `procthor:val:0`, `procthor:val:2`,
  `procthor:val:3` (the first three usable ProcTHOR houses). A house has
  one red backpack and furniture, so no single list of 8 is present in all
  five (at most 7 names are); each house's **list of 8** is the first eight
  names of one fixed preference order present in that house (the red
  backpack, 3.96's mix, `complex_house`'s small things, then furniture;
  `soak.PREFERENCE`, pinned by `test_soak.py`). Within a house the list is
  taken in turn, and a target equal to the previous mission's is skipped, so
  every mission is a new target. The sweeps' rate on these 40 pairs, beside
  (d): the in-process explore sweep (`FakeNav`) finds 39/40 (procthor:val:3's
  box `exhausted`).
* *Run length.* Missions start until 4 h after the run's start (after the
  setup: VE checked ready, the sampler, the stand-in and the perception loop
  up); the mission running at 4 h ends by itself (or at the harness's cap,
  1,800 s, by a Stop). The run is that start to the last mission's end. A
  run that ends early (`run_end` not written) is not complete and is not
  scored as met.
* *(a)* the lowest MemAvailable over the run, the lower of the 5-s account
  (`memory_account.py sample`, root) and 3.136's 1-s sampler.
* *(b)* each mission's MemAvailable minimum is the lowest 5-s sample in
  [its start, its end]; the slope is a least-squares fit against the
  mission's midpoint, over the missions that start after the first hour.
  "A process" is a role: `memory_account.component()` (plus the simulator
  body, the fake lidar, the stand-in and the harness by name; anything else
  by its `comm`), a role's processes summed; RSS for the stack's named
  roles, and for a process outside the stack (`other: <comm>`) its
  anonymous memory (`Pss_Anon`), so a journal or image file it maps is not
  read as a leak. A role's per-mission minimum is
  taken only where it is present in every sample of the mission (a process
  that comes and goes has none); its growth is the median of hour 4's
  per-mission minima less the median of hour 1's (hours by mission start).
  The instrument (the sampler, the stand-in, the harness) is reported, not
  judged. The GPU's nvmap share per role is reported beside RSS, no bar.
* *(c)* OOM kills: the larger of vmstat's `oom_kill` delta over the run
  (which must have been read) and the dmesg count (a ring buffer: a count
  that fell reads unknown, never 0); late wheel ticks: the sum, over missions, of each robot
  server's `wheel_loop.late_ticks` read at the mission's end (that server's
  whole life); a mission whose stack came up with no reading fails (c).
* *(d)* found share over every mission begun (a stack that never came up
  counts, not found); contacts on `truth_body.py`'s ground truth as
  amendment 2 (< 1 cm, the whole log of each stack); a mission whose truth
  log has a hole over 0.2 s, or an unjudged gap, leaves (d) unmet.
* *The planted check* (criterion 4's spirit, run before the board):
  `soak_plant.py`, the real sampler over two stand-in processes through four
  40-s "hours" of 10-s missions, scored by the same `bar_b`: the planted leak
  (+25 MB a mission) must fail (b), the steady stand-in must pass.
* *Locks.* The exclusive board lock (`board_lock.py run --max` the run plus
  2 h; `soak.sh` keeps the board itself) inside the **shared** desktop lock:
  every number here is the board's, none is timed on the desktop.
* *Known limit (the bug pass):* the soak runs over one ssh session with no
  pty; if the desktop loses the board the soak goes on there while
  `board_run` restores the twin's units beside it. Such a run died of a cause
  outside the stack: re-run, not scored (criterion 1). `soak.sh` puts the
  board back in the systemd target it was found in.

**Amendment 4 (3.135.B, 2026-11-03, written before any scored board run;
no bar changed).** How criterion 3's runs are counted and scored
(`evaluations/jetson-fmea-3135/rows.py`, `run.py row`):

* *Run counts* are the row's. Where a row names none (F7, F10, F13) it is
  **5**. "5 each" (F3, F6, F17) is 5 per case, and each case is reported as
  its own line of the row.
* *A scored run* ran to a result (no harness `error`) and was valid (the
  board was driving forward at the fault, amendment 2). An errored or
  invalid run is recorded, not scored, and replaced by one more run, **at
  most 3 replacements a row**.
* *The verdict:* a row (or case) is **met** with its count of scored runs,
  every one passing; **FAILED** as soon as one scored run fails (the rest
  still run and are recorded); **incomplete** when the replacements run out
  first. Incomplete is not met and is not a guard's failure: it is run again
  once its harness cause is fixed.
* *Conditions, per row:*
  * One `board_run` per row (or case), with the twin's units stopped (sudo,
    as 3.135.C) and VE's unit left as found.
  * The exclusive board lock for that row only, released after it (3.141,
    3.142 and 3.143 share the board), inside the shared desktop lock.
  * Board-side numbers only. The power mode is recorded. The board must be
    left as found after each row: checked, not assumed (criterion 5).
* *A's six rows* use amendment 2's mover: a frontier mission in
  `scaled_house`, no ROS, no VE, the cloud a closed port. F8, F9, F10 and
  F13 run on it as built.
* *F6 and F7 are not scored until their nav2-goal planted check exists*
  (amendment 2). The goal mover, ROS's container on this section's stack, is
  written into the next amendment before its first run.
* *F8's "`picar-stack` back within 10 s"* is a property of the production
  unit, which the harness's stack is not under. It is its own case, F8-unit:
  a SIGKILL of the production `picar-stack`'s robot server, with the twin's
  units as found, 5 runs, timed to its `/health` answering again. It is run
  after F8's harness case and written into the next amendment before it
  runs. F8 is met only when both cases are.

**Amendment 5 (3.135.B, 2026-11-03, written before these rows' planted
