# 3.168 Rover bring-up tools, built and dry-run before arrival

*`PLAN-ros-alignment.md` section 3.168; index: [README.md](README.md).*

**Why.** The Rover arrives 2026-11-08 and 3.140.B (L0 bring-up) needs tools
that exist before it is plugged in. Written in `tools/rover/`, each dry-run
here against the fakes (`sim/fake_esp32.py`, `sim/fake_lidar.py`,
`sim/fake_camera.py`), so the day's time goes on the board and not on
writing a capture script. 3.140's `run.py coverage` must also pass.

**Scope.** Nothing is installed or changed on the Jetson; no board time. No
Rover motion and no flashing: **no tool sends a wheel or servo command.**
What only the real board can answer stays owed to 3.140.B.

**Criteria (written before building; CLAUDE.md section 7):**

1. **Nothing reaches the board's input.** Every serial tool opens its port
   read-only (`O_RDONLY`), so a write fails at the kernel. Pinned by tests:
   a write on that descriptor raises; `FakeEsp32.lines_in` is 0 after each
   tool has run against it; no source under `tools/rover/` holds a `T:`
   command, a serial library, or an esptool write or erase verb.
2. **L0.3, the route (`serial_route.py`, `install_udev.sh`).** Against both
   fakes on ptys it names each port's role (`board` by a `T:1001` line at
   115200, `lidar` by CRC-valid LD19 packets at 230400) and any process
   holding it. Rules are generated for what was found, and the header UART
   gets a kernel-name rule, a USB device a vendor/product rule (the report
   says which applies: the D500 is expected behind the driver board). The
   install script does nothing without `--yes`, and refuses a rules file
   with a `RUN` key. Not run on the board.
3. **L0.5, the compare (`board_compare.py`).** Against `FakeEsp32` as the
   board: no field differences for `stock` and for `fork`, the rate within
   20% of the fake's, `v` read as centivolts. Planted differences are each
   named: a missing field, `v` in volts, a third of the rate, a boot-text
   line, and a reset (the silent gap and its text; output silence only, as
   the board's input cannot be tested read-only). Speeds and odometers
   that stayed at zero are `not_exercised` and the row is not met (amended
   before any real run, review round 2).
4. **L0.6, the lidar (`lidar_check.py`).** `capture` then `score` against
   `sim/fake_lidar.Emitter` on a pty, with a wall and a box in the scene,
   through `robot/lidar_ld19.py`'s own parser and yaw: 0 CRC failures, 10 Hz
   +/- 10%, wall within 2 cm, box at 0 +/- 2 deg: L0.6's bars. Planted
   corruption over 0.1%, a box off by 5 deg, a wall off by 5 cm and a
   missing geometry argument each fail with the row named. A capture under
   28 s on the lidar's own clock is not met (amended before any real run,
   review round 1), and a wall behind the box does not move its bearing.
5. **L0.4, the dump (`dump_firmware.py`).** Only `esptool read_flash`: read
   twice, the two SHA-256 equal, the size as asked; kept outside the
   repository with a manifest; an existing dump is never overwritten; a
   held port refuses (as does every serial tool: setting the baud under a
   holder would garble its commands). Against a stand-in esptool (no bootloader is faked):
   a matching pair passes; a differing pair and a short read fail.
6. **L0.8, the camera (`camera_check.py`).** Through `robot/camera_stream.py`
   on `sim/fake_camera.py`: frame age p90 <= 100 ms and 0 stale frames
   served at L0.8's bars, timed from the first frame served. A source that stalls is refused (`CameraStale`),
   counted as refused and never as served. Not met under 10 minutes, nor
   with over 1% of reads refused (amended before any real run, review round 1).
   Every serial tool needs root on a real device, or a holder could hide.
7. **`run.py coverage` passes** on `dev`: every section in the index has a
   row or a stated exclusion.
8. `/code-review` (Sonnet, at most two rounds), `ready`.

**Results (2026-11-08; no board time, nothing installed).** Tools in
`tools/rover/`, pinned by `tests/test_rover_tools.py` (60 tests, 5 runs in a
row at load 11).

1. **Met.** `O_RDONLY`; a write raises; `lines_in` 0 after every serial tool;
   the source scan is clean. Stated limit (`serial_ro.py`): a freshly booted
   tty's kernel echo, for the instant before the raw settings land.
2. **Met on the fakes.** Roles heard on ptys; rules generated per case
   (header UART, USB by serial, by port, by interface; none for a role heard
   twice). Which applies is the real board's to say.
3. **Met on the fake**, stock and fork. A still board is `not_exercised`, so
   the fake compared with itself is not `met`: turn a wheel by hand.
4. **Met on the fake.** The command lines at full length: `capture` 30 s then
   `score`, exit 0, 0 CRC failures, 10.0 Hz, wall 0.0 cm off, box 0.0 deg.
   (That run's capture held 52 s of packets: the rig's feeder had a backlog.)
5. **Met against a stand-in esptool only.** No esptool on the desktop and no
   faked bootloader: the real tool's flags are untried.
6. **Met on `sim/fake_camera.py`** and on stubs for the age bar.
7. **Met:** `run.py coverage` passes; 3.145-3.168 added. A section merged
   after this one needs its row.
8. `/code-review` two rounds (Sonnet): round 1 ten findings, round 2 ten;
   the bugs fixed (`odlt` scale, a held port's baud, a wall read as the box,
   short captures, a lost port, duplicate USB identities, a hidden holder).
   Not changed: a wide box's bearing is documented (use a narrow one).

**Owed to the real board (3.140.B):** which ports exist and whether the D500
is its own USB device; real frames, boot text and the silence after a reset;
the board's input deafness (needs a write, which these tools cannot make);
the real lidar's bars; esptool's flags and the dump; each real camera for 10
minutes.

**Status:** done on the fakes 2026-11-08; L0.3-L0.6 and L0.8 run on the Rover.
