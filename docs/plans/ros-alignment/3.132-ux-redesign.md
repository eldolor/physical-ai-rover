# 3.132 A staged UX redesign of the twin and consoles

*`PLAN-ros-alignment.md` section 3.132; index: [README.md](README.md).*

**Why.** The user is not happy with the experience of any UI this project
built (2026-10-31). There are three user-facing pages:

* the twin (`web-twin/index.html` and `app.js`);
* the walks console (`control/admin.html` and `admin.js`, served at `/admin`);
* the metrics console (`control/metrics.html` and `metrics.js`, static).

`docs/guides/FEATURES.html` is not deployed. The review behind this section
used 390 px screenshots of every page and two read-only code audits. Six
things are wrong, ranked by how much they hurt:

1. **Nobody is designed for.** Every surface speaks to the engineer who
   built it:
   * The Sim tab names `control/brain_server.py`, "a SLAM map of your
     hallway at R5", and drills tagged "(B3.2)".
   * The Guide HUD uses 15 three-letter codes with no legend.
   * Toasts print raw outcomes: "Mission arrived_unconfirmed".
   * The consoles say "x-app-secret", "persistent volume", and "Replays are
     the controlled evidence -- same pixels, one variable".
2. **The page layout works against the tasks.**
   * Watching a mission means scrolling past the D-pad to 21 monospace
     readouts, or 29 under tiered.
   * Brain missions start on Sim, but their model picker is on Guide
     (`app.js` `2899`).
   * Settings sits behind a 34 px gear.
   * The header always says "sim mode".
   * An idle robot shows its watchdog in alarm red.
3. **Paid actions are silent.**
   * Opening `/admin` runs the paid judge on every unscored walk
     (`admin.js` `scorePendingWalks`).
   * A replay starts when its dropdown changes, with no confirm.
   * No cost is shown anywhere in the consoles.
4. **Real bugs.**
   * The active "Guide me" button is blue on green and unreadable
     (`index.html` `214` against `961`).
   * The metrics page loads with no secret, so a newcomer's first sight is
     an error.
   * Typing in the admin search collapses an open walk.
   * Admin has no doctype, charset, `lang`, `<label>` or ARIA.
   * A walk's name is a `div` that the keyboard cannot reach.
   * The metrics table scrolls sideways at 390 px.
5. **No shared look.**
   * Three palettes (`#12151A`, `#0f1115`, `#0b0e14`) and three corner radii.
   * About 50 hard-coded colours bypass the twin's own tokens.
   * Targets under 44 px: the gear is 34, close is 38, the rotate dismiss is 30.
   * ~~2 of 17 animations honour reduced motion.~~ Wrong (corrected
     2026-10-31, Stage 1's review): the twin's sheet already had a global
     reduced-motion rule. The audit counted only the per-animation rules.
   * No light mode.
6. **The structure makes every change costly.**
   * `app.js` is one 6,691-line closure with 216 `getElementById` calls.
   * There is no string catalogue.
   * About 70 UI-test assertions pin exact jargon.

**Audiences (proposed by the reviewer at the user's request, approved with
the plan 2026-10-31):**

| | Who | Their jobs | Surface |
|---|---|---|---|
| A, primary for the twin | anyone at home with the Rover, on a phone, with no project knowledge | find an object, survey the house, watch progress, Stop, drive by hand, read "found / couldn't find / needs you" | the twin, default (operator) mode |
| B | the engineer (the user, and sessions) | the sim, drills, telemetry, policies and models, recording walks, scoring, replays, metrics | the twin's Engineer mode (today's "Show developer readouts") and one merged Lab console |
| C | demo visitors | the phone-only "Guide me" arrow | kept, as a secondary entry |

A is primary because, once the Rover arrives, the twin is the surface a
person drives from (CLAUDE.md section 7). B keeps every readout.

**The user's choices (2026-10-31):**
* a staged redesign: vanilla JS, no build step, the deploy stays
  `service/static/sync.sh`;
* the twin first;
* the two consoles merged into one with tabs, keeping `/admin` and
  `/metrics` working.

**Constraints carried.** Nothing about how the robot moves changes:
* STOP is `/stop`, through arbitration and `robot/safety.py`.
* 3.84's person-Stop latch stays.
* 3.86's colour rule stays: only a safety veto takes the alarm colour.
* 3.76 D's dropped secret on a moved setup link stays.
* Stored data goes into `innerHTML` only escaped (3.76 F and N2).

Every changed behaviour gets a UI test, seen failing first and run in its
module's real order.

## Stages

Each stage after 0 states its own criteria in an amendment before it is
built. Each one ends with:
* `/code-review`, plus the Thermos pass where the stage is risky (the
  console's judge and replay are paid calls);
* 390 px screenshots in both themes;
* `ready`, then a push to `dev`.

Deploys are asked first.

* **Stage 0: baseline (records only).** A harness measures the metrics
  below on today's `dev`. The same harness judges every later stage.
* **Stage 1: one design system.** `web-shared/ui.css` holds:
  * tokens for colour, spacing, radius, type and motion;
  * dark and light themes;
  * the components.

  The twin's inline style moves out. Every target becomes 44 px, reduced
  motion becomes global, and the Guide-me contrast bug is fixed red-first.
  The new files go in `assets.json` and the static routes.
* **Stage 2: the twin's structure and words.** `app.js` is split into ES
  modules, one behaviour-identical move at a time. `strings.js` holds every
  sentence in two voices, operator and engineer. Outcomes and refusals are
  said plainly. Tests move from exact jargon to `data-state` attributes.
* **Stage 3: the twin's information architecture.**
  * Tabs: Home (Find/Survey, the live mission card, results), Drive
    (camera, D-pad, map), Record (walks, and Guide me) and Settings.
  * A STOP bar is visible on every tab while anything moves.
  * A one-sentence mission card, with the readouts behind Engineer mode.
  * A first-run connection wizard.
  * A header that names the real mode.
  * Idle is neutral, not red.
* **Stage 4: one Lab console.**
  * `control/lab.html` with Walks and Metrics tabs, one secret, and the
    shared CSS.
  * No paid call without a click.
  * Score and replay confirm with an estimated cost, from the token counts
    and the price table the eval tools already use.
  * Labels, keyboard rows, a focus-trapped slideshow, and filters.
  * Metrics as cards at phone width.
* **Stage 5: verify, document, deploy.** The harness's bars become suite
  tests. FEATURES.md, the twin's README and the specs change with the code.
  Deploys are asked first.

## Stage 0: the measurement harness

`evaluations/ux-3132/measure.py` uses Python Playwright and Chromium at
390 x 844. It starts this section's own robot, brain and admin servers
(`plan_section.py env` ports). It serves `web-twin/` from a separate plain
static server, as CloudFront does, so first run is the deployed case. It
writes `results.json` and screenshots to a run directory.

**Page states (12):**

| Page | States |
|---|---|
| Twin | first run, nothing saved (Guide) · Guide connected · Guide's Robot view · Sim idle (robot and brain connected) · Sim with a Find mission running (`frontier` policy, free) · Settings · Engineer mode on, Sim idle |
| Walks console | not connected · connected with walks · a walk expanded |
| Metrics | first open, no secret · loaded |

Light mode is screenshotted too (`prefers-color-scheme: light`).

Walk, model and metrics data come from Playwright route stubs, as in
`tests/test_ui_admin.py`, so no recordings volume, vision service or paid
call is involved.

**Metrics, fixed before measuring:**

* **M1, taps per task.** A scripted path per task counts taps (a click,
  tap or select). Typing into a field is counted apart, as fields. A task
  counts only if its goal state is verified; otherwise it is reported
  failed. The twin starts from its default tab.

  | Task | Goal state |
  |---|---|
  | T1 | first-run connect to the robot server: "Connected" |
  | T2 | start a Find: `POST /mission/start` answered 200 |
  | T3 | start a Survey: the same with `job: survey` |
  | T4 | Stop a running mission from the Guide tab: `POST /mission/stop` or the robot's `/stop` |
  | T5 | one manual FORWARD: `/action` FORWARD sent |
  | T6 | see the mission's state: the element naming it on screen; taps plus the scroll in px needed |
  | T7 | begin a recorded walk with a fake camera: the twin's recording-start request sent, stubbed |
  | A1 | open a walk's frames |
  | A2 | replay a walk under another model: the replay request sent, stubbed |
  | A3 | delete a walk: the DELETE sent, stubbed |
  | A4 | see the metrics with the secret saved by the walks console |

* **M2, accessibility.** axe-core 4.10.3 runs on each state with WCAG
  2.0/2.1/2.2 A and AA rules. It is fetched by version and checked against
  npm's sha512, then cached outside the repo. The count is the serious and
  critical violations (rules, and the nodes they cover).
* **M3, small targets.** The count is visible, enabled, interactive
  elements (button, a, input, select, summary, `[role=button]`,
  `[tabindex]` >= 0) whose box is under 44 CSS px wide or high. Inline text
  links are exempt (`display: inline`, the WCAG 2.5.8 exception).
* **M4, sideways scroll.** Whether the document's `scrollWidth` exceeds
  its `clientWidth` by more than 1 px.
* **M5, jargon in operator mode.** This covers the twin's visible text
  with Engineer mode off, plus toasts and labels' text. It is reported for
  the consoles, which serve audience B, but no bar is set there. A hit is
  any visible text matching the frozen deny-list in `measure.py`:
  * file names (`*.py`, `.yaml`, `.js`, `.json`, `.md`, `.html`);
  * plan codes (`B3.2`, `R5`, `3.84`);
  * snake_case identifiers;
  * `ENV_VARS`;
  * API paths (`/navigate`);
  * the terms SLAM, nav2, ROS, frontier, CLIP, YOLO(E), watchdog,
    tier(ed), x-app-secret, uvicorn, CORS, odometry, deliberation,
    corroboration, p50/p90/p99, drill, preempt(ed), brain service;
  * the HUD codes RMS, CLD, VF, STA, ERR, OUT, LATE, SEQ, OBS, VIS, ACT,
    TGT, VOTE.

  The count is distinct (text, pattern) hits.
* **M6, paid calls without a click.** Requests to paid routes within 8 s
  of opening a page, with no input. The paid routes are the walks
  console's `GET .../evaluation`, any `.../replay` POST, and the cloud's
  `/navigate`, `/room` and `/describe`. In each case the secret and
  services are already saved.

**Amendments (written before the recorded baseline runs).**

* **1. T3's goal is the twin's request.** Trial runs, made while building
  the harness, showed that the plain simulator's brain answers 400 to a
  survey: a survey needs explore, and explore needs nav2. So T3's goal
  becomes this: the twin sends `POST /mission/start` with `job: survey`,
  and the harness records the status it gets back. What T3 measures is the
  twin's taps; whether the backend can run a survey is not a UI question.
  T2 keeps its goal of an answer of 200.
* **2. T4 and T6 use a mission the person started on the twin.** The trial
  runs also showed that a twin which is connected and idle never notices a
  mission started elsewhere (the finding below). So the harness starts the
  mission from the Sim panel, uncounted, with a target that is in no house
  so that the mission keeps running. It then goes back to the Guide tab.
* **3. Fixes from `/code-review` of the harness.**
  * **M5's plan codes.** A section number matches only as `3.NN` that is
    not inside a larger number and not followed by a unit, so readouts
    such as 3.42 m or 3.70 V are not jargon.
  * **M6's route list.** It names every route that spends, by method:
    * `GET .../evaluation`, which scores on a miss;
    * `POST .../evaluate` and `POST .../replay`;
    * `POST` to the cloud's `/navigate`, `/room`, `/describe`, `/analyze`
      and `/guidance` (the twin's `VISION_SERVICE_ROUTES`, plus `/room`).

    It is read from every request the page makes, not only from those to
    the stubbed cloud.
  * **Goal checks.**
    * "Connected" means the status element's `is-ok` state; the earlier
      word match also matched "Not connected".
    * T6's goal is the panel showing the running mission (the brain
      running, the panel saying so), not just any text in it.
  * **The stubbed cloud** answers CORS and preflights, as the real one
    does.
  * **Robustness.** The run holds the desktop's exclusive lock (rule 7).
    It refuses ports that are already in use. Each task and state is
    isolated, so a failure is recorded against it and does not end the
    run.
* **4. Task paths follow the UI.** Each task's goal check is fixed. Its
  scripted path is how the current UI reaches that goal, and later stages
  rewrite the path for their UI. A browser `confirm()`, if a later UI adds
  one, counts as a tap.
* **Attempt 1 (2026-10-31, at `93d4deda`): criterion 2 FAILED.** Two runs
  on the same commit differed in two places
  (`evaluations/ux-3132/attempt1/`). Every task, M3, M4 and M6 number
  matched.
  * **Settings' M2: 1 serious against 0.** One `color-contrast` hit on a
    toast, "Mission Cancelled — Stop pressed". The harness's own reset had
    raised it, and axe caught it part way through its fade.
  * **Sim with a mission running, M5: 20 against 19.** The live safety
    reason `depth_grid_facing_away` was on screen in one run and not the
    other. What a running mission shows depends on where the robot is.
* **5. Repeatability, after attempt 1** (written before attempt 2).
  * States are measured settled: no toast on screen, no finite animation
    running, waiting at most 10 s.
  * Criterion 2 is judged on every M1-M6 number except M5 on the one live
    state, `twin.sim_mission`. There the baseline's M5 is the union of the
    hits over the recorded runs, and each run's count is kept. The Stage 5
    bar for M5 is 0, which a union cannot hide.

**Findings while building the harness (not measured as metrics; for Stage 3).**

* **F1. A mission started elsewhere is invisible to a connected twin.**
  The twin picks up a running mission only when it connects (`app.js`
  `connectBrain`, its `pollBrainOnce`). Once connected and idle, its
  liveness loop pings `/health` and nothing else.

  Reproduced: `POST /mission/start` through the API with the twin open. The
  Sim panel still read "idle" and its button "Start". A tap on that button
  started a second mission request.

  Audience A meets this whenever two phones share the robot, which is the
  observer promise the Sim panel's own text makes.
* **F2. A Start right after the D-pad ends the mission at once.** The D-pad
  and Start sit in the same Sim panel.

  Reproduced: FORWARD on the D-pad, then a Start about 1.5 s later. The
  mission ended `cancelled`, with `cancelled_by: dpad`. The brain's log
  says "twin-dpad is driving -- brain is lower priority and was refused",
  and the panel says "Cancelled — D-pad took over".

  The cause is arbitration working as designed: a person's claim lapses
  `watchdog_timeout_s` (1 s) after their last command or verb. To the
  person, though, the Start they just pressed was refused in their own
  name. "Drive into position, then Start" is the natural sequence.

  Any fix belongs to Stage 3 and must keep 3.84 and M4's ranks: for
  example, the twin waits for the lapse, or tells the person why.
  Between tasks, the harness waits 3 s for the lapse.

## Stage 1: one design system (criteria written 2026-10-31, before building)

**Scope.**
* The twin only. The consoles take up the shared file in Stage 4.
* No change to copy, layout order or behaviour. Stage 2 rewrites the words
  and Stage 3 moves things.
* `web-shared/ui.css` holds:
  * tokens for colour, spacing, radius, type and motion, with a dark
    theme and a light theme (`prefers-color-scheme`);
  * the components the twin shares with the consoles later: buttons,
    fields, the switch, panels, the section label, toasts, the focus ring,
    and the global reduced-motion rule.
* `web-twin/twin.css` holds the twin's own rules.
* `index.html` keeps no `<style>`. The `style=""` attributes that
  `app.js` toggles stay, until Stage 2.
* Readouts with their own palettes keep them in both themes: the map
  (N1's ordering), the camera and the overlays drawn on it.

**Amendment 6: two harness measurements, added before Stage 1 is measured.**
* **M2L.** axe's `color-contrast` rule, run on each state under
  `prefers-color-scheme: light`. The count is serious or critical nodes.
* **M7.** Animations and transitions still running under
  `prefers-reduced-motion: reduce`, counted when they last more than
  10 ms. They are read from `document.getAnimations()` on each settled

## Stage 2B: the twin's modules (criteria written 2026-11-01, before building)

**What it is.** `web-twin/app.js` (6,777 lines, one IIFE) starts to become
ES modules, one behaviour-identical move at a time. Nothing a person sees
or does changes.

**Measured first (2026-11-01, `dev` at `d65256b1`):**
* No section of `app.js` assigns a `let` that another section declares, so
  moved code never needs to write an import (imports are read-only).
* The sections are tightly cyclic. Guidance (2,048 lines), brain liveness
  (612) and the remote brain (293) call one another, and they read
  element constants (`document.getElementById(...)` at the top level) that
  other sections declare.
* The page's own `window` properties, against a blank page of the same
  origin: exactly `twinStrings`, in both voices.

**How a move is made.**
* **`app.js` becomes the entry module.** It is loaded with
  `<script type="module">`, and it keeps its IIFE and its indentation, so
  that change is a few lines. The `import` lines sit above the IIFE, and
  their bindings are visible inside it. `app.js` exports nothing.
* **Modules live in `web-twin/js/`.** Each moved block keeps its words,
  minus the IIFE's two spaces of indent. It gains `export` on the names
  other files use and `import` for the names it uses.
* **A module's top level only declares.** That means function declarations,
  and `const`/`let` whose initialiser reads only its own file and no page
  API (DOM, storage, `window`). A statement with a side effect, such as
  `applyStaticIcons();` or a listener, stays in `app.js` at its original
  place.
* **A module never imports `app.js`.** Modules may import one another.
* **Why this is behaviour-identical.** Inside one module, as inside the
  IIFE, function declarations are hoisted and `const`/`let` are in the
  TDZ (the temporal dead zone, before initialisation) until their line
  runs. A module whose top level only declares can be evaluated before
  `app.js`'s body without anything observable changing. The statements
  that do something still run in their original order.

**Criteria:**

1. **The UI suite after every move.** All UI tests (283 today:
   `tests/test_ui*.py`, `tests/test_frame_source.py`) pass after every
   move, in their modules' real order. `ready` passes before the push.

   imports transitively. Every file they reach is in

  the debug buffer. Before, a script error after the capture was recorded.
  Fixing it changes behaviour, so it belongs to Stage 5.
* **A deploy is not atomic.** An old `app.js` paired with a new module
  whose export was renamed fails until both are up. The upload order
  covers adding a module, not renaming one.
* **`voicedStatus` is exported.** It was a private registry, and keeping
  it private is left to Stage 3.
* **Opening `index.html` from `file://` no longer works.** Modules need
  HTTP. The robot server and CloudFront both serve it.

## Stage 3: the twin's information architecture (criteria written 2026-11-03, before building)

**Sequencing.** Stage 3 is built in two halves, in this order, like Stage 2.
Both halves' criteria are written here, before either is built.
* **3A, the layout.** The tabs, what goes on each, the STOP bar, the
  mission card, the header, and idle in neutral colours.
* **3B, the behaviours.** The first-run wizard, F1, F2, the Guide HUD's
  codes, and `voicedStatus` made private again.

**3A's scope.**
* **Four tabs, in the tab bar:** Home, Drive, Record and Settings. Home is
  the default, so a first visit and an unknown saved tab both open on Home.
  * **Home:** Find or Survey (the job, the target, Start or Stop, the cost
    hint, and Engineer mode's policy, ask, model and drill rows), the
    mission card, the mission's results ("where it looked"), and the
    autopilot's connect hint.
  * **Drive:** the camera view, the depth strip, the map, the D-pad, the
    look and turn-step rows, the safety line and the robot log. Engineer
    mode's raw readouts, the house row and Re-map stay with them.
  * **Record:** today's Guide panel as it is: Guide me, Robot view, Record
    this walk, Drive via brain and their Engineer mode pickers. Robot view,
    the recording mode, becomes its default for a device with no saved
    choice; Guide me is the secondary entry (audience C). Without this, T7
    would cost a tap more than the baseline, Record no longer being the
    default tab (written while building, before any measuring).
  * **Settings:** as it is. Its gear in the header becomes the tab bar's
    Settings button, which keeps the id `btn-settings`. The header's
    connection pill still opens Settings when something needs setting up.
* **Saved tabs from before.** A device that saved `guide` opens on Record,
  and one that saved `sim` (or the older `autonomous`) opens on Home. A
  saved `drive` opens Drive, which is a tab again.
* **Element ids do not change.** A panel moves to its tab with its ids, so
  `app.js` changes only where it names a tab.
* **A STOP bar on every tab while anything moves.** It shows while a
  mission runs, while Drive via brain runs, or while the robot server says
  someone holds the robot (`/health`'s driver). One tap sends the robot's
  `/stop`, as the D-pad's STOP does, and then ends the mission with
  `POST /mission/stop` if one runs. With no robot connected it sends only
  the mission's stop. Arbitration, 3.84's latch and the safety path are
  unchanged: the bar only calls the routes a person's STOP already calls.
  The robot's `/health` is read on every tab while the robot is connected
  and the page is visible, not only on Sim.
* **The mission card.** In operator mode, one sentence on Home names the
  mission's state, its target and how far it has got, for example
  "Searching for the red backpack -- 2 rooms so far" or "Found the red
  backpack". The telemetry grid's rows are Engineer mode's. In Engineer
  mode every row is shown as today.
* **The header names the real mode.** The eyebrow reads the robot
  server's `/health` mode in plain words (Simulator, Phone camera, Rover),
  or "Not connected". Engineer mode reads `sim mode`, `teleop mode` or
  `hardware mode`. The fixed "sim mode" goes.
* **Idle is neutral.** A watchdog that has fired while nothing runs is the
  robot at rest, and the readout says so in the neutral colour. During a
  running mission it is a fault, in amber. 3.86's rule holds: only a
  safety veto takes the alarm colour.

**3B's scope.**
* **A first-run wizard.** With no robot address saved and no setup link,
