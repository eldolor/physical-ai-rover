# 3.238 Hardware mode hangs at boot in tty.setraw

*`PLAN-ros-alignment.md` section 3.238; index: [README.md](README.md).*

**Why.** 3.228.C's board run (the desktop session, 2026-11-28) found that
after a fresh boot the robot server in hardware mode hangs at start-up and
never binds :8000. `py-spy` put it in `robot/hardware_robot.py`'s
`tty.setraw()` on `/dev/ttyTHS1`, the kernel waiting in `set_termios`.
After a boot the port is at its defaults (9600 baud, echo on), and
`setraw` applies its settings with `TCSAFLUSH`, which waits for the output
to drain. The inference (not proven on the board): the board's 115200
feedback stream arrives at a 9600 port with echo on, every byte is echoed
back out at 9600, and the output never drains. The workaround by hand was
`stty -F /dev/ttyTHS1 115200 raw -echo` before the stack; it lasts until
the next boot. The orchestrator asked for the fix in the cloud (no Rover).

**Criteria (written before building; CLAUDE.md section 7):**

1. A red-first test reproduces the hang without hardware, and the fix
   configures within 1 s under the same conditions. A pty cannot show the
   wait (found here: Linux's pty driver reports no pending output, so its
   `set_termios` never waits -- `setraw` on a pty with 15,360 bytes
   unread and echo pending returned in 0.3 ms), so the test models the
   serial driver: every `tcsetattr` that is not `TCSANOW`, and every
   `tcdrain`, waits until the test ends. The test also pins that the
   model reproduces the hang on dev's own call (`tty.setraw()`).
2. After set-up the port reads 115200, raw (no `ICANON`, `ECHO`, `ISIG`,
   `OPOST`, `ICRNL`, `IXON`/`IXOFF`), 8N1, `CREAD | CLOCAL`, `VMIN` 1,
   `VTIME` 0, and blocking (`O_NONBLOCK` cleared), on a real pty left at
   9600, cooked, echo on.
3. The existing tests that build a `HardwareRobot` or a `FakeEsp32`, and
   `tests/test_robot_contract.py`, pass unchanged.
4. No change to the safety path's behaviour: wheel feedback, heartbeat,
   stall detection and the reader are untouched (the diff is the open
   only), and frames arrive and are fresh after the modelled open.
5. A set-up that fails closes the fd.
6. (B, the desktop) After a cold boot of the Jetson, with no `stty` by
   hand, the stack in hardware mode binds :8000 at once and `/health`
   reports fresh wheel feedback.

## A: the open never waits (2026-11-28, cloud)

**The fix.** `robot/hardware_robot.py` gains `open_serial(port, baud)`,
which `HardwareRobot.__init__` calls in place of `os.open` + `tty.setraw` +
`tcsetattr`. Nothing on it waits on the line:

* `os.open(O_RDWR | O_NOCTTY | O_NONBLOCK)`: no wait for a carrier either.
* `tcflush(TCOFLUSH)` discards the echo backlog (a flush never waits).
* One `tcsetattr(TCSANOW)` sets the baud, `cfmakeraw`'s flags, 8N1,
  `CREAD | CLOCAL`, and no flow control (`IXON`/`IXOFF`/`IXANY`,
  `CRTSCTS`): the board's UART has neither, and either on would put bytes
  in the JSON or stall a write.
* `tcflush(TCIFLUSH)` drops what arrived at the old baud.
* `O_NONBLOCK` is cleared, so the reader's `select()` + `os.read()` and
  `_send()`'s `os.write()` behave as before.

`sim/fake_esp32.py` still calls `tty.setraw()` on its own pty's slave; a
pty never waits there (criterion 1's finding), so it is left alone.

## B: the cold-boot check (desktop, not run here)

Under the board lock (`python tools/jetson/board_lock.py hold --why
3.238.B`), with the replacement board fitted and the wheels off the floor:

1. Update the board's brain to a `dev` that holds 3.238.A, only on the
   user's word (`tools/jetson/README.md`).
2. Power the Jetson off and on (a cold boot, not a reboot), and do NOT run
   `stty` on `/dev/ttyTHS1`.
3. Before the stack starts, record the port's state:
   `stty -F /dev/ttyTHS1 -a | head -3` (expect 9600, `echo`: the
   condition 3.228.C found).
4. Start the stack in hardware mode as 3.228.C did (the drop-in with
   `ROBOT_MODE=hardware ROBOT_SERIAL=/dev/ttyTHS1`). Pass: `curl -s
   127.0.0.1:8000/health` answers within 10 s of the unit starting, and
   its wheel feedback is `fresh` with `frames` rising.
5. Record `stty -F /dev/ttyTHS1 -a | head -3` again (expect 115200,
   `-echo`, `-icanon`, `clocal`, `-crtscts`).
6. If it hangs: `sudo py-spy dump --pid <robot server pid>` and record
   where; then the workaround (`stty -F /dev/ttyTHS1 115200 raw -echo`) to
   restore service.
7. Put the board back as found, release the lock, and record the result
   here as criterion 6, met or failed.
