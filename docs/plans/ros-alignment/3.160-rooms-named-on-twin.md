# 3.160 Rooms a person names once, on the twin, saved with the map

*`PLAN-ros-alignment.md` section 3.160; index: [README.md](README.md).*

**Why.** (the user, 2026-11-06: features of a robot vacuum (Dreame) worth leveraging, for full autonomy; 3.158) A vacuum's app shows the rooms it cut from its map; the
person splits, merges and names them once, and every later job uses those
names. Here room names come from a model on each frame: the cloud's `/room`
was wrong on 51.4% of real frames (3.122), and CLIP's few-shot rooms did not
meet cost (3.54). A name a person gave once is right from then on, costs
nothing per mission, and makes "look in the kitchen", room priors (3.116)
and survey reports dependable.

**Scope.**
* After a survey (or on any saved map), the twin shows the map's room cut
  (`segment()`) with suggested names (the survey's labels); a person
  renames, merges or splits rooms in a few taps.
* The names are saved with the map (3.70.S4's store, keyed to the saved
  map's `map_id`, 3.50.D) and override any model's label for that room;
  a model's label is used only for a room nobody named.
* A re-map (3.50.D4) keeps names by overlap; a room it cannot match asks
  again.
* Maps and names are a home's floor plan: local only, never committed or
  uploaded unasked.

**Criteria (written in step A, before building).** At least: taps to name a
house's rooms (bar), names surviving a reload and a re-map (bar), the share
of mission room reads that use a person's name once named (100%), and the
UI's phone-size evidence (CLAUDE.md section 7).

## 3.160.A: criteria and design (written 2026-11-07, before building)

**What it rests on.** `brain/room_labels.py`'s `segment()` (the room cut, on
the brain's map, every 5 s on a mission; 3.118's numpy, exactly the old
answers), 3.70 S2's labeller (a model's name per room), 3.70.S4's store
(rooms and objects saved with the map, `control/inventory_store.py`'s
neighbour), 3.50.D's saved map (the bridge's `/maps` volume, versioned, 3
kept) and 3.50.D5's **`frame_id`** (`map-<8 hex>`: one id per saved map,
the same on every matched reload and through a re-map, new on a fall-back
or a fresh start; `None` in the sim's own world). The twin's map view on
Drive (Remote brain's World map, tap-to-goal, Re-map now) and 3.132's
operator voice and measure bars (`evaluations/ux-3132/measure.py`).

**D1. A named room is geometry on a saved map, not a cut's id.** The cut's
ids change whenever the map does, so a name is stored with the room's cells
(a 0.10 m grid, run-length coded) in the saved map's frame, under its
`frame_id`. Every read of the cut maps each cut room to a named room by
overlap: a cut room takes the name of the named room covering **>= 60%** of
it (largest wins); a cut room with none keeps the model's label (or none),
marked `source: model`.

**D2. The store.** One local file per `frame_id`
(`<room_names_dir>/<frame_id>.json`, `brain.room_names_dir`, default under
the brain's data dir beside the inventory), written atomically and fsynced,
holding `{frame_id, rooms: [{name, cells, set_at, by: "person"}],
history}`. Never in git, never uploaded: a home's floor plan (the scope's
rule; `INVENTORY_BUCKET`'s uploads carry labels and positions only and do
not include it). With no `frame_id` (no saved map yet, the sim's own world)
the editor is closed with a reason ("Survey first: names are kept with the
saved map"), never kept for one session.

**D3. Precedence.** Wherever a room's name is read (the survey's report, the
room prior's types (3.116), "look in the kitchen", 3.162's list, the twin's
card), a person's name wins over any model's label for that room, always;
the model is asked nothing for a room a person named (no paid `/room` call:
the labeller skips it).

**D4. The editor (operator mode, Drive's map).** After a survey, or on any
saved map, "Name rooms" draws the cut with each room's suggested name.
* Name: tap a room, type (or tap the suggestion), Done.
* Merge: tap "Merge", tap two rooms, Done (the larger room's name kept,
  editable).
* Split: tap "Split", drag a line across the room, Done (two rooms, the
  larger keeps the name).
* Each edit is one brain route call (`POST /rooms/names` with the
  `frame_id` it was drawn on; a stale `frame_id` is refused 409, as 3.88's
  picks are); no edit ever reaches the robot server, the bridge or nav2.
Strings in `web-twin/strings.js`, both voices; tokens from `ui.css`.

**D5. A re-map (3.50.D4) and a reload.** A reload on the same `frame_id`
reads the same file: names as they were. A re-map keeps the `frame_id` and
changes the map: D1's overlap rule names the new cut; a named room that no
cut room now covers by >= 60% is listed "Not found after the re-map: tap to
place it" and its name is used nowhere until a person places it (never
guessed onto a neighbour). A fall-back (a new `frame_id`) starts with no
names and says so.

**Not a safety veto.** Names steer nothing that moves the robot except
through explore's existing room inputs (3.116's prior, 3.125's `rooms`
policy), which choose among goals the rules already allow. `robot/safety.py`,
the arbitration and the bridge are untouched (rule 4).

**Ties to 3.158.** C6 (rooms named right) has its >= 95% bar only once this
is built; C5's rooms are the house sheet's rooms, which the user draws with
this editor; 3.162's list shows these names.

untouched (the orchestrator's constraint): precedence lives in
`RoomLabeller`, which reads the store by the pose's `frame_id`.

**Design change in B (D1), found by N4's test before any run counted.**
Naming by cut room (a cut room takes a stored room's name when 60% of it
lies inside) FAILED N4: with a house's true rooms stored, three re-maps kept
6 of 15 rooms in `scaled_house` and 24 of 39 in `home_first_floor` (0
wrong): the cut merges rooms across wide doorways, so a room a person split
comes back unnamed. Names now apply **per cell** -- a cell inside a person's
room carries its name whatever the cut does -- and the 60% overlap only says
which stored room a cut room is (the editor) and whether a stored room is
still on the map (`placed()`, 40% of its floor). The old rule's shortfall is
pinned as a recorded result (`test_the_cut_room_rule_alone_lost_rooms...`).
Also not as D2 wrote it: the directory is `ROOM_NAMES_DIR` (env, default
`recordings/room-names`), not a `brain:` key, keeping `control/brain_config.py`
and `config/robot.yaml` out of this step.

Reviews (`/code-review` and the Thermos pass, Sonnet, round 1), fixed and
pinned (8 tests): stored rooms were addressed by list position, so a second
phone on an older list could change the wrong room (now a revision every
edit names, 409 on a stale one); a damaged or non-object names file read as
"no names" and the next edit overwrote it (now `unreadable`: readers go on
without names, every edit is refused, the file untouched); the per-cell
lookups and the routes were Python loops over every cell (now numpy, one cut
an edit, `cut` and `owner` run-length coded); SLAM's map version moves while
the robot drives, so edits were refused (now judged on the cut's hash), and
the editor reloads when the map moves; an unplaced room could be a merge
target; empty names, `s<unicode digit>`, malformed split lines and a boolean
index raised or were taken (now refused); the history kept the raw name; a
drag cancelled by the browser stayed armed; an edit tapped while one was
saving vanished. Round 2 (Sonnet, on the fixes): a slow reload could land after
an edit and hide it (requests now numbered, an old answer dropped); an
automatic reload wiped a name being typed (skipped while a name field has
focus); the edit and the view disagreed about a lost room (an edit now
matches only rooms on this map); a lost room could never be forgotten
(`clear` allowed, a Forget button); a damaged file with coordinates far
outside any house could exhaust memory (now `unreadable`); the split drag
takes pointer capture. Kept as recorded: the labeller learns the saved map
from the pose its first ask sees, so a layer drawn before that has no names;
with the editor open while the robot drives, the rooms are re-cut every 5 s
(one `segment()` each).

Not built here, recorded: a find mission with no labeller reads no names
(the runner builds a layer only for a survey or `find_room_labels`); giving
every find the person's names needs `control/mission_runner.py`, a follow-up
once 3.153.A releases it.
