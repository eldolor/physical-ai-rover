## A. A local brain at the ladder's Power-off (3.137; seen in 3.170)

`POST /wheels` applies the ladder to a person (a rank check) and to the brain
(`is_autonomy`). `twin-local-brain` is neither: it ranks `DRIVER_LOCAL`. So at
Power-off, its non-zero wheel command reaches the motors. `/action` refuses it;
only `/wheels` has the gap. It is the same at Reserve and during a check at
rest, where `battery_refusal`'s own docstring and
`test_a_local_brain_rank_is_refused_at_reserve_too` already say a local brain is
refused.

**The change.** On arrival, every non-zero `/wheels` from a driver that is not
autonomy and not ROS asks `battery_refusal`, the one place the ladder's rules
live. At execution, under `motion_lock`, the same question is asked again, as
the brain's already is, so a level latched after arrival moves nothing. A zero
command is never refused. A person's Reserve scaling is unchanged.

**Criteria (written before building; CLAUDE.md section 7).** Through the real
app's `/wheels`, on the simulated body:

1. **Stability.** At Power-off, 20 non-zero `/wheels` from `twin-local-brain`:
   20 refused `battery_poweroff`, and the motors' commanded velocity stays 0 on
   all 20.
2. **Reserve and a check.** A non-zero `/wheels` from `twin-local-brain` is
   refused `battery_reserve` at Reserve and `battery_check` during a check.
3. **At execution.** A ladder that reaches Power-off after the arrival check
   and before the motors: a local brain's and a person's commands do not reach
   the motors.
4. **Progress.** At level `ok` the same request is applied, non-zero. A zero
   command at Power-off is not refused. A person at Reserve still drives, scaled
   as before.
5. **Nothing else moved.** `test_battery_ladder`, `test_shutdown`,
   `test_authority` pass unchanged; `arbitrate` and every safety bar unchanged
   in the diff.

The new tests are seen red with the fix removed, and run in their module's real
order.

## B. A lost final `/stop` reads as a live mission (3.164, criterion 1's amendment)

`mission_live()` is true once the brain has moved since its last `/stop`. If
the mission's final `/stop` is lost, nothing else ends it: 24 s later the robot
server records a watchdog trip for a brain that finished normally. 3.164 left
the fix, an explicit close from `control/`, to 3.156.D. 3.156.D merged without
one: no route or call in `control/` or `robot/` closes a mission on a normal
end.

**The change.**

* `POST /autonomy/resume` also answers `mission_id`, a number the server gives
  each brain Start.
* `POST /autonomy/mission-closed` (`x-driver`, `{"mission_id": N}`): only if that
  mission is still the open one and this driver's, it closes it. It reports only.
  It moves nothing, takes no authority, and leaves the latch, the lease, an
  existing trip, B3.1's clock and every wheel alone.
* `RemoteRobot` keeps the Start's id; `MissionRunner._end`, the single exit, after
  its final stop, sends the close on a daemon thread (`_end` can run on the
  brain's event loop). The id is read in `_end`, before the thread starts, so a
  retry cannot close the next mission.
* The close retries every 2 s for up to 20 s (below `trip_after_s`, 24 s), because
  a network blip that ate the `/stop` may eat the first close too. A refusal or a
  404 (an older server) ends the retries.

The three failsafes are untouched: B3.1 still fires on silence, B3.2 and B3.3
still end a mission. A brain that dies sends no close, so it still reads as a
trip. A dock return does not reach `_end` until it ends, so a return stays a live
mission.

**Criteria (written before building).**

1. **Stability, the defect.** A real `uvicorn` robot server at a short
   `trip_after_s`: a mission moves, its final `/stop` is never sent, the close is
   sent: `mission_live` false and `trip` null, read after `trip_after_s` + slack.
   10 of 10 through `MissionRunner` over `RemoteRobot` with its final stop made to
   fail. *Amendment before any run (2026-11-09):* the 10 of 10 is one run with
   `MISSION_CLOSE_REPEATS=10` (about 30 s alone); the suite repeats it twice.
2. **The close can be lost too.** The first closes fail and a later one lands
   inside the window: no trip.
3. **A stale close.** A close for an earlier id leaves the next mission open and
   able to trip. Another driver's close does nothing.
4. **Only a report.** A close leaves `autonomy_stopped`, an existing `trip`,
   `last_command_at`, the lease and the wheels as they were.
5. **A real hang still trips.** No close, silence past `trip_after_s`: a trip
   (the existing `test_a_brain_that_goes_silent_mid_mission_is_a_trip` unchanged),
   and a mission whose Start's reply had no id sends no close.
6. **Progress.** A mission over `RemoteRobot` with the stop working still ends as
   it did, with steps > 0, and exactly one close reaches the server.
7. **An older server.** A 404 on the close is one attempt, with no exception.
8. **Nothing else moved.** `watchdog_should_stop`, `watchdog_timeout_s`, `arbitrate`
   and every safety bar unchanged; `test_watchdog_integration`, `test_authority`,
   `test_goal_lease`, `test_failsafes`, `test_watchdog_reason` and the push gate
   pass.

The new tests are seen red with the fix removed, and run in their module's real
order.
