# 3.164 The watchdog record keeps a Stop's or fault's reason: the twin tells a hung brain from a finished mission

*`PLAN-ros-alignment.md` section 3.164; index: [README.md](README.md).*

**Why.** 3.86's open follow-up, queued by the user on 2026-11-07 as
desktop work. The robot server's B3.1 watchdog records `last_refusal` after
`watchdog_timeout_s` of silence, naming the LAST driver, not who went
quiet. That record replaces a Stop's, a fault's or a safety veto's refusal
about a second later, so the twin's readout loses the reason (3.86 rounds
6-7, rows 112-113 and 127: colouring the watchdog amber false-positived on
every mission end, so it was reverted). For full autonomy (3.158) the person
reading the twin after an unattended run must be able to tell "the brain
hung mid-mission" (a B3.1 trip) from "the mission ended and the robot went
quiet" (normal), and must still see why it last stopped.

**Scope.**
* The robot server keeps the last Stop/fault/veto refusal beside the
  watchdog's record instead of overwriting it, and says whether the
  watchdog fired while a mission or a goal was live (the brain's
  autonomy state or an accepted goal) or after it ended.
* The twin shows a B3.1 trip mid-mission as a warning, a quiet end as calm,
  and the last Stop/fault reason in both cases (3.86's words and colours).
* No change to who drives, the watchdog's timing or any safety bar (B3.1,
  rule 4); the record only.

## 3.164.A: design and criteria (written before building, 2026-11-08)

**What the code says, which changes the plan's first idea.** "The watchdog
fired while a mission was live" does not mean a hung brain.
* `watchdog_timeout_s` is 1 s, and a healthy tick waits far longer on a cloud
  call (`vision_timeout_s` 20 s, `arrival_confirm_timeout_s` 8 s,
  `room_label_timeout_s` 15 s). B3.1 fires in those waits, by design.
* A nav2 goal pauses for seconds while it plans.
* So a hang is a silence no healthy tick can make: B3.3 ends any tick at
  `tick_timeout_s` (30 s).
* The brain's `/stop` does not mean the mission ended either: `_safe_stop()`
  also runs on each blind step (a vision or camera failure) and before the
  return leg.
* `POST /autonomy/resume` is sent at every Start, including a Start then
  refused with nothing to relatch, so it alone does not make a mission live.

**Design: three facts on `GET /health`; the robot server only.**
* `last_refusal` keeps its meaning and shape (`control/health.py`, the live
  tests and the deployed twin read it).
* **`last_stop_reason`** (new): the last refusal that was not the watchdog,
  or a person's Stop (`/stop` from a manual driver, `person_stop`). Same
  fields as `last_refusal`. The watchdog never writes it.
* **`watchdog`** (new): `{mission_live, last_fired, trip, trip_after_s}`.
  * The mission record: opened by `/autonomy/resume` from an autonomous
    driver (the old record and its trip go); `moved_at` is that driver's
    last accepted move (`/action` other than STOP, `/wheels`, a goal);
    `stopped_at` is its last `/stop`. `/autonomy/relatch` or a person's Stop
    closes it. **`mission_live`:** moved since its last stop, in a record
    still open. A refused Start never moves, so it is never live. A person's
    tap goal after a mission is not the brain's, so it is not live.
  * `last_fired`: once per silence, beside `last_refusal`'s record:
    `{during, driver, seconds_ago}`; `during` is `goal` (a brain's leased
    goal), `mission`, or null.
  * **`trip`: the brain went quiet mid-mission.** Set once per mission, kept
    until the next Start (a quiet end after it must not erase it), on
    either:
    * `how: "silence"`: `mission_live`, silent for `trip_after_s`, and no
      navigator beat inside `watchdog_timeout_s` (a beating brain is alive,
      whatever nav2 is doing).
    * `how: "lease"`: 3.145's goal lease lapsed: at the lapse.
  * `trip_after_s` = 0.8 x `brain.tick_timeout_s` (24 s): above every healthy
    wait (20 s at most), below B3.3's deadline by more than a tick's own work
    before a hang (a hang after the tick's command makes a silence shorter
    than the deadline). A display threshold: it moves nothing.
* Both new fields are in `control/health.py`'s description list, never the
  verdict (M5).
* **The twin** (Engineer rows, as 3.86's are; the operator view is unchanged):
  * "Robot watchdog": `trip` -> warning (amber, 3.86: only a safety veto takes
    the alarm colour) saying the brain went quiet mid-mission; fired with
    `mission_live` -> today's amber "motors stopped"; otherwise today's calm
    "(at rest)". It reads the server's `mission_live`, not the brain's
    status, so it holds with the brain dead.
  * "Last refusal": `last_stop_reason`, in its kind's colour (3.86's words);
    with none, `last_refusal` as today, so an older server reads the same.

**Known limits (recorded, accepted here).**
* A killed brain with no leased goal reads as a trip 24 s after its last
  command, not at once; until then the row is amber as today.
* A hang straight after a brain's `/stop` with no move since (a blind step)
  reads calm: not `mission_live`. B3.2/B3.3 still end that mission.
* A tick hung while its navigator's heartbeat thread still beats reads calm
  at the robot server; B3.3 ends it and the brain's outcome names it.
* A drill's own short deadline (`drill_tick_timeout_s` 3 s) is not known to
  the robot server: the tick-hang drill below runs with the robot server's
  config set to the same deadline.

**Criteria.** Records in `evaluations/watchdog-reason-3164/`. Live runs: the
real `uvicorn` robot server and brain, `MissionRunner` through `RemoteRobot`,
`frontier` in the simulator, under the desktop lock (exclusive).
1. **A hung brain reads as a trip: 10/10 of each.** Mid-mission: the
   `tick_hang` drill; the brain SIGSTOPped; the brain SIGKILLed. `trip` is
   non-null with `driver: brain` within `trip_after_s` + 2 s of the last
   command. For the drill it is still there 5 s after the mission has ended
   (after B3.1's later quiet record). One SIGSTOP at the shipped config (24 s).
2. **Normal ends read calm: 0 trips.** At least 20 live missions ending in
   each way one can: `found`, out of budget or exhausted, the brain's Stop, a
   person's Stop. 3 s after the end: `trip` null, `mission_live` false,
   `last_fired.during` null. Progress half: each mission's outcome and steps
   are recorded, and every one moved (steps > 0). Plus a healthy wait: a
   mission whose ticks pause longer than the watchdog but under
   `trip_after_s` fires B3.1 mid-mission with `during: mission` and no trip.
3. **The reason survives: 100%.** 10 each of a person's Stop, a safety veto
   and a lapse (`autonomy_lapsed`), on the live server: `last_stop_reason`
   names it 10 s after the watchdog's record, while `last_refusal` reads
   `watchdog`.
4. **The twin.** UI tests at 390 px, each seen red first and run in module
   order: a trip amber with the words, a quiet end not coloured, the last
   Stop or fault reason shown in both, an older server unchanged. Phone
   screenshots of a trip and a quiet end.
   *Amendment before any run (2026-11-08):* a lapse needs a leased nav2 goal,
   and these live runs have no ROS, so its 10 are in process, over 3.82's fake
   bridge with the app's real watchdog loop
   (`test_a_lapse_is_a_trip_at_once_and_its_reason_is_kept`,
   `WATCHDOG_REASON_HOLD_S=10`). The person's Stop and the veto stay live.
5. **Nothing else moved.** `watchdog_should_stop`, `watchdog_timeout_s`,
   `arbitrate` and every safety bar unchanged in the diff;
   `test_watchdog_integration`, `test_authority`, `test_goal_lease`,
   `test_failsafes` and the push gate pass. In `robot/server.py`, the new
   code only assigns records and reads the clock; the watchdog loop makes no
   new blocking call.
