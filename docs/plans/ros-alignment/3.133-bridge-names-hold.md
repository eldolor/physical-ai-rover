# 3.133 The ROS bridge names its own goal hold

*`PLAN-ros-alignment.md` section 3.133; index: [README.md](README.md).
Opened 2026-10-31 on the user's word: 3.127's "Known limits" and review
rounds 1-2 named it the root fix, the user's call.*

**Why.** Since 3.127 the robot server's `POST /world/goal` refuses a goal
the bridge holds as `nav2_starting` or `slam_not_ready` instead of
`ros_unavailable`. It finds out by guessing from the shape of the bridge's
503 body (`world/bridge_faults.py` `hold_reason()`): a `nav2` object whose
`inactive_s` is at most `NAV2_START_MAX_S` (60 s), or a `slam` state in
`SLAM_PASSING`. Both reviewers named what the guess costs:

* a nav2 that crashes mid-run reads as "starting, or restarting" for 60 s;
* a nav2 whose answers flap never reaches the bar;
* a slow cold start past 60 s reads as ROS DOWN.

The bridge knows which holds will pass on their own, so it should say so.

**Checked before starting (2026-10-31):** no other session works on this.
`list_sessions`: the running cloud session is on 3.132 (the UX redesign;
nothing on the bridge, `bridge_faults` or the goal route); the desktop
session is a Jetson bench run. `git branch -r | grep plan/`: 3.80, 3.83,
3.98, 3.116 and 3.132, none on the hold. The highest section on `dev` was
3.132, so this is 3.133.

**Design.**

* **The bridge** (`picar_bridge/bridge.py`). Every `_goal_refusal()` body
  carries `hold`: `"nav2_starting"`, `"slam_not_ready"` or `null`. It is
  set only for a state that passes without anyone acting, as the bridge
  knows it:
  * **SLAM:** `slam_not_ready` while `slam_state` is `starting`,
    `checking` or `remapping` (the bridge's own `SLAM_PASSING`, next to
    the states it sets). `failed` is `null`: it is final.
  * **nav2:** `nav2_starting` only while nav2 has not been seen active in
    this bridge's life and the manager has never answered: no lifecycle
    manager yet, or asks still unanswered (Humble's manager serves
    `is_active` in the callback group that runs its start-up, so a start
    reads as unanswered asks; 3.105). It ends for good, never to return in
    this bridge's life, at the first answer of any kind:
    * active: the start is over, and a later inactive is a crash or reset;
    * not active (`success` false): the start-up returned and failed;
    * a call that raised: the manager failed. *(Amended in review round 2:
      a raised call is the transport, not a reply, and the start goes on.)*

    So a crash, a reset, a flapping manager, and a bring-up that failed
    are all `null`. A cold start holds for as long as it takes, with no
    time bar. *(Amended in review round 1: one ceiling in the bridge,
    `START_HOLD_MAX_S`, 300 s from its own start.)* (A fresh container restarts the bridge with nav2, so a
    container restart is a start again.)
  * The bridge's other 503, "nav2 is not up (navigate_to_pose has no
    server)", is only reached once nav2 has answered active, so it carries
    no `hold` (it is a crash).
* **The robot server** (`world/bridge_faults.py` `hold_reason()`): it
  reads `hold` on a 503 and returns it if it is one of `HOLDS`
  (`nav2_starting`, `slam_not_ready`), else None (`ros_unavailable`).
  `NAV2_START_MAX_S`, `SLAM_PASSING` and the body-shape guessing are
  deleted.
* **A bridge without the field (an image built before this), the
  deliberate choice: `ros_unavailable`**, as before 3.127, not 3.127's
  guess as a fallback. Why:
  * Keeping the guess keeps all three defects above on exactly the images
    that would use it, plus a second rule to keep in step.
  * What is lost is wording only, for one image's life: `retryable` is the
    same (true for any 503), so explore waits exactly as before.
  * The only images that could meet it are rebuilt from `dev` after this
    merge. On the desktop, `vision-picar-ros:latest` is rebuilt as the
    first step after the merge. The board runs no ROS container.
* **Unchanged:** `retryable` and `bridge_status`, explore's wait (it
  branches on `retryable`), the twin's labels and toasts (`GOAL_HOLD_TEXT`),
  the bridge's `/health`, every other route.
* **The contract across the wall.** The test feeds the bridge's real
  `_goal_refusal` bodies (stubbed ROS, `tests/test_review_376h1.py`'s
  fixture) through `hold_reason()` for every state above. A test also pins
  that the `hold` strings the bridge source can send are exactly
  `bridge_faults.HOLDS`. That is the user's alternative to a `DUPLICATES`
  entry in `tests/test_wall_linters.py`, which has a budget and checks
  values, not reasons.

**Criteria (written before building; CLAUDE.md section 7):**

1. **The bridge, red first** (`tests/test_bridge_hold.py`, on stubbed ROS):
   (a) `hold` is `nav2_starting` for a fresh bridge with SLAM ready: nav2
   not yet asked, no lifecycle manager, one ask in flight, an ask given up
   unanswered. (b) Once answered active, every later refusal is `null`: an
   inactive answer, an unanswered ask, the manager gone. (c) Answered not
   active, or a call that raised, before ever being active: `null`, and
   still `null` after later unanswered asks. *(Amended in review round 2,
   before the run: a raised call keeps the start; only a reply ends it.)* (d) SLAM `starting`,
   `checking`, `remapping`: `slam_not_ready`; `failed`: `null`. The bridge's
   `SLAM_PASSING` is pinned to every `slam_state` it assigns, except
   `ready` and `failed`. (a) and (d) fail on `dev` `0aeba203` (no `hold`
   key).
2. **The robot server, red first** (`tests/test_nav2_hold_reason.py`):
   these cases fail on `dev`:
   * `hold: "nav2_starting"` with `inactive_s` 300 (a slow cold start) is
     refused `nav2_starting`;
   * `hold: null` with a `nav2` body and `inactive_s` 4.2 (a crash 4 s
     ago) is `ros_unavailable`;
   * `hold: null` with `slam: "starting"` is `ros_unavailable`.

   `hold: "slam_not_ready"` is `slam_not_ready`. An unknown `hold`, a
   non-string `hold`, and a `hold` on a non-503 are all `ros_unavailable`.
   `retryable` and `bridge_status` are as before in every case.
3. **The fallback, pinned:** a 503 with no `hold` key (an older bridge's
   `nav2` or `slam` body) is `ros_unavailable`, retryable.
4. **The contract:** for each state in criterion 1, the bridge's own body
   through `hold_reason()` gives the matching reason (`nav2_starting`,
   `slam_not_ready` or None). The `hold` values in the bridge source equal
   `bridge_faults.HOLDS`.
5. **Unchanged:** explore waits on a held goal (3.127's test). These pass:
   the bridge, goal, Stop, reload and re-map suites (`test_nav2_ready_gate`,
   `test_review_376h1`, `test_ros_goals`, `test_stop_cancels_goal`,
   `test_refused_goal_hold`, `test_map_persist`), the wall linters and
   `test_ui_hold_labels`. Each new or changed test is also run in its
   module's real order.
6. **Specs in the same commit:** `docs/engineering/ros/ENGINEERING.md`
   (`/goal`'s 503 body) and `docs/engineering/world/ENGINEERING.md`
   (`POST /world/goal`).
7. **The gate:** `/code-review` and the Thermos bug pass every round, until
   neither finds anything medium or worse. Each round is recorded with
   `reviewed --thermos`, then `ready` passes.
8. **Live (owed; after the merge, on the desktop, the user's run):**
   `vision-picar-ros:latest` rebuilt from `dev`. A goal sent during a
   container start is refused `nav2_starting`, and explore waits (`WAIT`,
   no place failed). This also tests the assumption above that a cold
   start's manager never *answers* not-active before it is active. If it
   does, the start reads `ros_unavailable`: the safe direction, but this
   criterion fails.

## Review round 1 (`/code-review` medium and the Thermos bug pass on `288247da`)

Neither found a bug on the safety path. `retryable`, `bridge_status`,
arbitration and explore's wait are unchanged.

**Found by both, fixed red first: a start that never ends read as a hold
for ever.** Two ways it happened:

* a lifecycle manager that dies before its first answer (the launch
  respawns nothing) is "no manager" for good;
* a fresh slam_toolbox that never places the robot stays `starting`
  (Thermos; `_start_fresh`'s first-pose wait has no timeout).

**The amendment to the design, written here before the fix ran:** a start
has one ceiling, kept in the bridge, `START_HOLD_MAX_S` = 300 s from the
bridge's own start. Past it, nav2 still starting and SLAM still `starting`
send `hold` null. This bar is not 3.127's guess moved:

* it is the bridge's own clock, not the age of nav2's last change;
* it is 300 s, not 60 s: about 23 laptop starts (~13 s), and wide because
  the Jetson's cold start is unmeasured;
* it bounds only states the bridge enters at a start, so a crash an hour in
  is never read as one.

`checking` and `remapping` end on their own timeouts, so they hold at any
bridge age (pinned).

**Taken from `/code-review`:**

* the start flag is derived from `answered_at is None`, not kept as a
  second flag;
* a stale test name.

**Not taken:**

* An answered "not active" during a start's first instants ends the hold.
  From Humble's `lifecycle_manager.cpp`, the startup timer is created in
  the group before the group's executor spins, so the window is a narrow
  race. The user's rule is that a manager that answered failure is never a
  hold. Criterion 8 tests this live.
* An image without `hold` loses 3.127's naming. That is the deliberate
  fallback above; the desktop image is rebuilt from `dev` as the first step
  after the merge.
* The twin's `nav2_starting` text still says "(starting, or restarting)".
  Now only a start reads that way, but the user said the toast stays as it
  is. Left as a follow-up: one line in `GOAL_HOLD_TEXT` and a deploy.
* `/health` showing the start flag: outside "nothing else changes". The
  refusal body carries it.
