# 3.154 Explore's approach goal is aborted by nav2 while the previous goal's cancel is still in flight

*`PLAN-ros-alignment.md` section 3.154; index: [README.md](README.md).*

**Why.** Found by 3.136.B amendment 6's cancel record (3.136's section) on
3.141.F0's poller-on board window (2026-11-04, `dev` `ee2e897d`,
`evaluations/jetson-perf-3136/board/3141F0-on-20261104-2201/`), and the same
shape as 3.136.B run 2's two aborts (`board/run2-20261104-1857/`). Explore
cancels its live goal (`ExploreAgent._cancel()` before `_send(... "approach")`,
`brain/explore.py`), and the approach goal it sends next is ended ABORTED by
nav2 almost at once:

* **F0-on, both cases in mission 2:** the brain's cancel of the previous goal
  is recorded (`explore_cancels.jsonl`, under the previous goal's id), the
  approach goal is accepted ~70 ms later, and it is ABORTED 6-10 ms after
  nav2 reported it executing (`27eb4fcbd5a2`: executing 1793851830.164,
  aborted .174; `05695f580f7b`: .539 -> .545). No cancel was ever sent for
  the approach goal's own id, so 3.136.B amendment 6 rightly does not excuse
  it.
* **Run 2 (before the cancel record):** two `approach` goals, `98b1a9ba00cd`
  executing 1793840906.416 -> aborted .444 and `b62d423ef51f` .549 -> .553.
  nav2's own log at each: `bt_navigator` "Failed to get result for
  follow_path in node halt!", then "[navigate_to_pose] [ActionServer] Client
  requested to cancel the goal. Cancelling.", "Aborting handle.", "Goal
  canceled", and `controller_server` "Goal was canceled. Stopping the
  robot."

Inferred, from the timing only: nav2 Humble's `bt_navigator` is still
halting the tree for the previous goal's cancel when the new goal arrives,
and the halt's failure ends the new goal ABORTED. On the car this is a
failed approach right after a sighting -- the moment explore most needs its
goal -- and every 3.136.B window where it happens is invalid on nav2's item.

Two fixes are in view; the choice is this section's, made from data: wait
for the previous goal's cancel to finish (its result, through the bridge)
before sending the next goal, or send no cancel before a new goal, since a
new nav2 goal preempts the old one. It touches the goal path with 3.145 and
3.146.

**Read from the code before writing the criteria.** The cancel-then-send
happens twice:
* explore's `_cancel()` (a `DELETE /world/goal`) before
  `_send(... "approach")`;
* the bridge's own `send_goal` (`picar_bridge/bridge.py`), which calls
  `cancel_goal()` and sends the new goal at once.

So removing explore's cancel alone would leave the race in the bridge.

**Criteria (written before any measurement; CLAUDE.md section 7).** The
board is off-limits until the user is back (week of 11-23), so every run
here is on the desktop. Setup: the live robot server (`scaled_house`, sim)
and the ROS container (`tests/demo_explore.py` `stack()`), on this
section's ports, `PICAR_ROS_NETWORK=host`, under the exclusive desktop lock.
The driver is `evaluations/approach-abort-3154/`.

1. **The race, measured on `dev`.** The microbench sends goal A to a free
   point about 2 m away and waits until nav2 reports it executing. Then, as
   explore does, it sends `DELETE /world/goal` and at once posts goal B to
   another free point, and reads B's state for 3 s. 30 trials on `dev`'s
   image (`vision-picar-ros:latest`, `dev` `ed6875b5`'s bridge). Recorded:
   how many B goals end ABORTED with no cancel sent for B's own id, and how
   long after B was sent.
2. **The fix, chosen by rule.** Candidate (1), preempt: the bridge's
   `send_goal` sends the new goal without cancelling the live one, since
   nav2's navigator preempts it, and explore sends no `DELETE` before a
   new goal; its ownership check is kept. If (1) has 0 aborted B in 30, it
   is adopted. Otherwise candidate (2), wait (the cancel's result before
   the send), is built and measured the same way.
3. **The fix holds:** 30 trials of explore's sequence on the fix's image
   (this section's own tag, never `:latest`):
   * 0 B ABORTED;
   * every B reaches executing within 3 s;
   * A ends in a terminal state, so nothing is left driving.
4. **A Stop still stops:** 10 trials of `DELETE /world/goal` alone on an
   executing goal on the fix's image, each canceled within 2 s.
5. **Live explore:** 3 explore missions on `scaled_house` through the
   brain's HTTP API on the fix's image: found, 0 contacts, no `approach`
   goal ABORTED (the mission's status and the bridge's goal states).
6. **Red first:** unit tests show the bridge's `send_goal` and explore's
   approach no longer cancel first. They fail on `dev` and pass with the
   fix.
7. **Owed:** 3.136.B run 3 on the board, which waits on this section.
   Recorded as owed until the user is back.
