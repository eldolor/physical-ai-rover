# 3.232 The twin says when the robot or brain stops answering, and the shutdown card says what to do next

*`PLAN-ros-alignment.md` section 3.232; index: [README.md](README.md).*

**Why.** The user, 2026-11-27, on a phone after Settings' Shut down on
the board (which runs `mode: sim`, so 3.170's power-off is the stub): "I
can't tell if the jetson has actually shut down from this UI." Three gaps:

* The stub card said "it's a simulator" and "restart it to drive again".
  On the board that is a real computer, still on, and the card never
  said to press the power button.
* The card never changed after the request: the stub ignored the robot
  going quiet, so pressing the power button left the same words up.
* The robot's "Connected" (Settings and the header) was set once, at
  Connect, and never re-checked: a robot that is off still read
  Connected. (The brain's badge is re-checked every 5 s and was right:
  ngrok's offline page carries no CORS header, so the fetch fails and
  `markBrainLost` runs. Checked from the desktop the same day.)

**Design.** No new poll: the battery poll (3.137.B) already reads the
robot every 1-15 s on every tab, and it becomes the liveness check. The
rule as built, after two reviews: any reply from the robot server is an
answer. A gateway's 502-504, a tunnel's HTML 404 or no reply is a miss.
Two misses in a row read **Not answering** in the header and in Settings
until the robot answers again. The stub card becomes "The robot has
stopped answering" (naming the light) on the same two misses. A failed
power-off keeps its "still on" card, because its robot is running.

**Criteria.** Drafted before building, in the words below. Recorded
honestly: the first write of this file was refused by the tool (the file
had not been read yet) and was not redone, so the criteria reached this
file only after the first measurements. They are unchanged from the
draft, and the review that found the gap is what put them here.

1. The stub card's title says what to do (press the power button). Its
   body never says "simulator" and says the robot is still on.
2. After a stub shutdown, a robot that stops answering turns the card
   into the gone-quiet state, which still names the light.
3. A connected robot that stops answering reads "Not answering" in the
   header and in Settings; one that answers again reads "Connected".
4. A robot that answers, even with an error status, is never "Not
   answering".
5. A UI test per criterion 1-4 at the phone viewport, each seen to fail
   without its change, and the module passing in its real order.
6. A phone-size screenshot of each new state (CLAUDE.md section 7).

**Results (2026-11-27, desktop, `tests/test_ui_shutdown.py`, 390 px):**

* Criteria 1-3 met. Each test failed on the page before its change and
  passes after:
  * the stub test and the not-answering test, on the old page;
  * the flicker, failed-quiet, reload-off and reconnect tests, and the
    plain-text-500 case, on each review's previous commit.
* Criterion 4: the 401 case is a guard (the old page never said "Not
  answering", so it passes on both); the plain-text 500 case failed on
  the first cut, which counted only JSON replies.
* Criterion 5: the module (22 tests now) passes in its real order. In
  the first seven runs of the module (18 tests then),
  `test_while_it_answers_it_is_not_safe` failed once. It then passed
  alone and in the next five module runs. Recorded, not explained.
* Criterion 6: phone screenshots of the stub card, the gone card, and
  "Not answering" in Settings and in the header (seen in the session).
* Reviews:
  * First, a Sonnet reviewer found:
    * one dropped request flipped the stub card to "gone" and back
      (fixed: two misses, as the header counts them);
    * "Connected" could be painted during a Connect (fixed);
    * a gateway's JSON 502-504 counted as an answer (fixed).
  * Then `/code-review` of the branch found:
    * after a reload with the robot off, the stub card never turned
      (fixed: a current shutdown counts quiet without a connection);
    * a failed power-off read "most likely off" (fixed: only the stub
      turns);
    * the robot's plain-text 500 read as a miss (fixed);
    * the header said "Not answering" during a Connect (fixed);
    * recovery waited 15 s (fixed: 5 s while quiet);
    * the specs were not updated (fixed in the same commit);
    * the criteria above were missing (recorded above);
    * the flicker test watched too short a window (now sampled until
      two answers after the drop);
    * the time had no date (fixed).
  * Thermos was not run: the change touches no loop CLAUDE.md lists, and
    no recorded or stored data.
