# 3.178 A watch list: a few named valuables noticed on every mission

*`PLAN-ros-alignment.md` section 3.178; index: [README.md](README.md).*

**Why.** (the user, 2026-11-12: features of similar products and projects worth
building while the Rover waits on Waveshare.) The one shipping product near
this project's purpose is a robot vacuum (Narwal Flow 2, 2026): while cleaning
it notices wallets, keys and jewellery on the floor, alerts the person and pins
them on its map. It does not name everything; it watches for a short list.

That is the gap 3.46.C left. Naming **every** object on real frames failed its
75% bar with every namer tried and was closed by the user on 2026-10-10, so on
the car the inventory, 3.162's report and 3.172.C's recall know only the
target of the day. A short fixed list is an easier problem than open naming:
the shipped pipeline (YOLOE crops, then CLIP, gate P >= 0.8) is already asked
one name a mission; this asks it a handful. If it holds, every mission and
survey fills the memory that 3.172.C's recall and 3.175's "where did you last
see it" read, for the things people actually lose.

**Scope.**
* A list the person sets (default: keys, wallet, phone, glasses, remote; at
  most 8), watched on every mission and survey beside the target; sightings go
  to the inventory by the lidar as any detection does.
* A precision problem first: a wrong pin costs trust and, through recall, a
  drive. The gate may be stricter than the target's.
* Memory and time on the board are bars: more prompts through the text cache
  (3.81.C), no new model, the 250 ms perception budget kept.
* A: what the recorded corpus can say for free (which list items appear in the
  labelled walks at all). The real measurement needs the Rover's frames with
  list items placed on the floor.

**Criteria (written in step A, before measuring; CLAUDE.md section 7).** At
least: per-item precision and recall on a pinned frame set, with precision the
harder bar; pins per mission that are wrong (bar near 0); perception p90 and
`MemAvailable` on the Jetson with the list on against off; the target's own
find rate unchanged with the list on (stability).

## 3.178.A: criteria, design, and what the recorded walks hold (2026-11-13)

Written before any measurement of B or C (CLAUDE.md section 7). A changes
no code outside `evaluations/watch-list-3178/` and its test.

### What the recorded walks already hold of the list (free, offline)

`evaluations/watch-list-3178/count.py` -> `counts.json`, pinned by
`tests/test_watch_list_counts.py`. It reads committed files only: no
frames, models or network. The list is the default one (keys, wallet,
phone, glasses, remote), each with its names fixed in the script before
counting; only an exact name counts ("phone charger cable" and "phone box"
are not phones).

* **The labelled set holds no list item.** 3.92's set as 3.177.A pinned it
  (21 walks, 2,261 frames, set hash `00d12dbc44f6`) has six targets: a white
  phone charger cable, a blue bottle, blue and yellow running shoes, a grey
  backpack, a red (once "burgundy") backpack, and a woven laundry basket. A
  walk's `labels.json` flags only its own target, so the human reference holds
  **0 walks and 0 frames** for every list item. Neither recall nor precision
  for any list item can be computed from the recorded corpus as labelled.
* **The detector's own words, unadjudicated.** For each frame, 3.46's
  stored-object records (`evaluations/inventory-346/memory-*.json`, the
  same 2,261 frames) keep the prompt-free YOLOE name of the one stored box
  that scored highest for the walk's own target. That box is not a census
  of the frame. A list item's exact name appears on **1 frame** ("phone",
  `blue-bottle-20260907-185007/frame-0003.jpg`, P(target) 0.25, in both the
  `all` and `objects` variants). The near names on the 15 held-out walks
  ("payphone" 5, "phone box" 1, "boom microphone" 1) are not counted.
* **Not reachable from this session:** the frames themselves and 3.46's
  judge outputs (`recordings/inventory_eval/`, gitignored, on the desktop).
  The AWS keys here are rejected (`InvalidClientTokenId`). The judge listed
  up to 10 clearly visible unboxed objects per frame over 3,051 of 3,198
  frames and is already paid for. **A free follow-up on the desktop:**
  search those outputs and `detections.json` for the list's names (no new
  call), to learn which list items the rig walks show at all. That sizes
  B's by-eye check (criterion B3). It is not a substitute for C's placed
  items.

**What this means for B and C.** The corpus cannot measure the list's
recall. It can measure **wrong sightings**: the list's pass over 2,261
frames, with every sighting checked by eye, bounds the false pins before
the Rover. Recall waits for C's placed items.

### Design

* **The list.** `watch_list` in `config/robot.yaml`'s `brain:` block (and
  `control/brain_config.py` in step). It defaults to the five names above,
  holds at most 8 entries, and the person can set it from the twin later
  (not in B). Each entry is a short noun phrase, as the target is.
* **One pass, not two.** YOLOE is prompted once with the target plus the
  list (its prompt features come from 3.81's text cache, one entry per
  (model, texts), so a list seen before costs nothing and a new one costs
  one child-process encode, as a new target does). The crop cap
  (`max_crops`, 16) and the area ordering are unchanged. CLIP scores each
  crop once against the target, the list and the distractors (one image
  encode per crop, as today; the extra texts are a dot product each).
* **The target's answer is computed as today.** P(target) is the softmax
  over the target and `DEFAULT_DISTRACTORS` only. The list's texts never
  enter it, so a crop's P(target) cannot move. Only the crop set can move,
  if the list's prompts change YOLOE's boxes. Criterion B4 measures that.
* **A list item's probability** is the softmax over that item, the other
  list items, the target and the distractors. Including them makes keys
  and remote compete rather than both pass on one crop. **The list's gate
  is P >= 0.9**, stricter than the target's 0.8 (precision first), fixed
  here and not tuned on the frames that judge it.
* **Into the inventory.** A list sighting becomes a detection
  `{label: <item>, bearing_deg, confidence}` through the runner's
  `detections_fn`. On the car that is a function over the frame's
  `Perception`, which today has none (the default reads `frame["detections"]`,
  which only the simulator sets). Placement, looks and belief are the
  inventory's existing rules: the lidar's range at the bearing, one look per
  new viewpoint, and the report at `REPORT_BELIEF` (0.8, two independent
  hits).
* **A pin** is a reported landmark (belief >= `REPORT_BELIEF`) whose label
  is a list item. The mission report gains a `watch` block listing each
  item's pins (position, room, belief, last seen). That block is what
  3.175's "where did you last see it" and 3.172.C's recall read. A list
  item that is the day's target is counted once, as the target.
* **The simulator.** Its frames already name every visible object
  (`complex_house` holds keys and a TV remote among 16 small things), so in
  the simulator B tests the plumbing and the report, not the namer's
  accuracy. 3.46's noise model (3 deg bearing sigma, 10% misses, 5% of
  frames with one wrong-class label) is kept, but its wrong labels never
  name a list item, so on its own it cannot make a wrong pin. B adds a
  list-labelled false detection: on 5% of frames, one detection whose label
  is drawn uniformly from the list, at a uniform bearing in the field,
  seeded. That is what criterion 2 tests the pin rule against.
* **No new model.** If B's bars need one, B fails as written and the
  section stops for the user's call.

### Criteria for B (the list into the inventory; the board's time and memory)

The frame set is 3.92's pinned set (hash `00d12dbc44f6`, 2,261 frames).
Perception rows follow P24: board (GPU) and laptop (CPU) rows are never
mixed, and every timed number names its device.

1. **Plumbing, in the simulator.** A tiered or frontier mission on
   `complex_house` with the list on reports the keys and the TV remote as
   pins whenever the robot's camera passed within 2.5 m of them with a
   clear line of sight. Bar: **>= 90% of such passes** over a sweep of
   **>= 20 seeded missions**, under 3.46's noise model.
2. **Wrong pins in the simulator.** Under the same noise model (with the
   list-labelled false detections above) and sweep, a
   pin with no list item of its label within 0.5 m. Bar: **<= 0.1 per
   mission** (at most 2 over 20 missions).
3. **Wrong sightings on recorded frames (the precision bound).** The list
   pass over the 2,261 pinned frames at P >= 0.9, with every sighting's crop
   checked by eye and the calls recorded per crop (3.46 amendment 12's
   method). Bars: **<= 2 frames of 2,261** with a wrong sighting, and **<= 2
   of 21 walks** with any. The true sightings found are reported per item;
   no recall is claimed from them.
4. **The target is unchanged (stability).** Over the same 2,261 frames,
   `control/perception_eval` with the list on against off, at the shipped
   gate (0.8): target TP on >= list-off TP minus 5 (1% of the 535 visible
   frames), and target FP on <= list-off FP. In the simulator, the sweep's
   arrival rate and outcomes with the list on equal those with it off,
   mission by mission.
5. **Time on the board** (the Jetson at 15 W, GPU, `board_lock` held, the
   VLM held off per 3.80). Per-frame perception over the 2,261 frames, list
   off and on: **p90 on <= 250 ms**, and **p90 on <= p90 off x 1.10**. The
   first frame after a new list (the text encode) is reported apart and may
   not exceed 3.81 T1's new-target cost by more than 20%.
6. **Memory on the board.** `MemAvailable` sampled at 1 Hz over the same
   runs. Bars: **the steady-state median with the list on is within 50 MB
   of the median with it off**, and **the minimum never drops below
   500 MB** (3.81.F's floor).

A progress metric is paired with each stability one: 1 and 3 (found and
right) are reported with 2 and 4.

### Criteria for C (on the Rover's frames)

1. **Placements, fixed before the run.** Each list item is placed on the
   floor **>= 10 times**, across **>= 3 rooms**, at real-house spots
   (beside the sofa, under a table, in a hall). Look-alike decoys stay
   where they are: a TV remote near the phone's spot, a glasses case, a
   coaster, a phone charger. Placements are logged with a measured
   position before each mission. An item with fewer than 10 placements is
   not judged.
   **The pinned set is chosen before any frame is seen.** Before the first
   run, `evaluations/watch-list-3178/rover/plan.json` is committed: the
   mission ids, each mission's start pose, target and placements, and the
   rule that **every frame each listed mission records is in the set**. No
   frame or mission is dropped after it has been looked at. A mission that
   aborts for a reason outside perception (a fault, a stuck wheel) is
   re-run under a new id and recorded with its reason, and the aborted one
   stays in the record. Once the runs end, the set is hashed (each frame's
   sha256, 3.177's rule) and the hash is committed before any scoring.
2. **Per-item precision** over pins (a pin is right when it is within
   0.5 m of a logged placement of its item). Bar: **>= 95% for every
   judged item**.
3. **Per-item recall** over placements the camera covered (in the field,
   within 2.5 m, not occluded, per the inventory's own miss geometry). Bar:
   **>= 60% for every judged item** pinned within 0.5 m. Precision is the
   harder bar; a recall failure with precision met is recorded as such.
4. **Wrong pins per mission.** Bar: **<= 0.1** (at most 2 over >= 20
   missions).
5. **The target is unchanged.** Paired missions with the list off and on
   over the same placements, >= 10 each: the arrival rate with the list
   on is no lower than with it off minus 10 points.
6. B5 and B6 repeated on the Rover's own frames, with motors running.

A failed bar is recorded as failed. An amendment is written before the run
it affects.
