# 3.170 A Shut down button on the twin: a clean power-off before the Rover's hard power button

*`PLAN-ros-alignment.md` section 3.170; index: [README.md](README.md).*

**Why.** The Rover's hardware power button cuts the Jetson with no clean
shutdown. The user asked (2026-11-08, through the orchestrator) for a routine:
tap Shut down on the phone, wait for the twin to say it is safe, then press the
button. The button itself stays a hard cut; nothing here softens or delays it.

**Limits of this section.** Tests and live runs use the stub or a harmless
command only. No board use: no real power-off, no polkit rule. 3.137.C's real
power-off and the rule's install are for when the user is present. No twin
deploy (asked separately).

## Design

**One sequence.** `POST /power/shutdown` on the robot server starts 3.137's
`power_off()`: the wheels at rest, `battery.shutdown_steps` in order (the
brain's mission, ROS, the local VLM), `os.sync()`, `poweroff_cmd`. It stays out
of the battery ladder: the ladder's level does not move, so the brain and the
twin never read a person's shutdown as a flat pack.

**Who may call it.** A strict gate of its own, not `require_secret()`:

| `APP_SHARED_SECRET` | `poweroff_cmd` | Answer |
|---|---|---|
| set | any | the right header is served; anything else 401 |
| unset | set (the car) | **403, always**: a route that can power off the robot is never open |
| unset | none (the stub) | served: local dev and the suite, where nothing can power off |

Only a person's rank may ask (`driver_priority == DRIVER_MANUAL`, an unnamed
caller counting as a person, as everywhere): the brain, teleop and ROS get 403.

**The route is public only through the tunnel.** `service/tunnel/proxy.py`
forwards `/*` to the robot server, so it needs no entry there. The robot server
is not behind CloudFront or API Gateway, so `tests/test_serverless_routes.py`
has no entry to add.

**The stop goes first, by the existing path.** The route sets its latch, then
calls the same `stop()` as `POST /stop` with a person's name: the wheels zero,
a nav2 goal ends, autonomy latches, and a mission ends `cancelled` as after any
person's Stop. No new movement path. After that:

* A person's commands and ROS's are refused `shutting_down`.
* The brain's are refused by the Stop's latch, as they already are, so it ends
  its mission the way it knows.
* `POST /autonomy/resume` lifts nothing while the shutdown runs, so a Start
  cannot undo the latch.
* `POST /stop` still answers.

**Mid-mission.** The phone's confirmation names the live mission, and the
shutdown ends it. The twin also sends the brain its `POST /mission/stop`, without
waiting on it, so a brain that is down costs nothing. On the car,
`shutdown_steps` names the brain's stop (3.137.C sets it).

**Exactly once.** A lock around `power_off()`'s guard, because it now has more
than one caller. A second tap, a retried request or the ladder firing during it
gets the same run's state, with `started: false`.

**What the twin says.** `GET /battery`'s `ladder.request` is null, or
`{by, seconds_ago, phase, settle_s}`, on the chain the twin already polls.
`phase`:

| Phase | Meaning |
|---|---|
| `stopping` | the wheels and steps; the power-off has not begun |
| `powering_off` | `poweroff_cmd` started, or returned 0 |
| `failed` | `poweroff_cmd` returned non-zero or timed out; the robot is still on |
| `stub` | this robot has no power-off; nothing was powered off |

`powering_off` is marked before the command runs: `systemctl poweroff` returns
at once, and the server may be killed before the phone reads the result.

The twin's banner, on every tab, across a reload:

| What the phone knows | Says |
|---|---|
| answering, `stopping` or `powering_off` | not yet: do not press |
| quiet **after** `powering_off` | wait `settle_s`, then safe to press once the Jetson's light is out |
| quiet **before** `powering_off` | it cannot know; do not press until the light is out |
| `failed` | it could not power itself off: still on, and the button is a hard cut |
| `stub` | nothing was powered off |
| answering again with `request` null | a fresh boot: the banner clears |

The phone cannot see the power. A dropped connection is expected and is not
proof, so even the best case names the light. `settle_s` (30 s) is a placeholder
until 3.137.C measures the board.

## Criteria (written before building; CLAUDE.md section 7)

1. **The gate.** With a secret set, a missing or wrong header is 401. With no
   secret and a power-off command, 403. Neither stops the wheels, latches
   anything or runs a step. No secret and the stub is served. The brain's, ROS's
   and teleop's names are 403. Pinned in tests for each row.
2. **One sequence, in order.** The steps recorded in `ladder.shutdown` are
   wheels, each step, sync, poweroff, from `power_off()`; the wheels are stopped
   before the first step; the battery ladder's level stays `ok`.
3. **Exactly once.** 20 concurrent POSTs against a live server, plus a retry
   after the run ended and a ladder Power-off during one: the power-off command
   ran once, every time. Live, 10 of 10 (a command appending to a file).
4. **The mission.** Pressed mid-mission on a live stack: the mission ends
   `cancelled`, before the power-off command, and no wheel motion follows the
   press. Live, 10 of 10. With the brain down: the route answers, the step that
   needs it fails and is recorded, and the sequence still finishes. Live, 10 of
   10.
5. **Nothing else moves.** After the press a person's `/action` and `/wheels`
   and a person's goal are refused `shutting_down`, the brain moves nothing, a
   Start lifts no latch, and `POST /stop` answers 200. Every existing safety,
   authority and watchdog test passes unchanged.
6. **The phone.** At 390 px, in operator mode: a Shut down control in Settings,
   usable with the brain down and the robot up. Tapping it asks for confirmation
   first and sends nothing; Cancel sends nothing; the confirmation names a live
   mission; a double tap sends one request. Every string is in `strings.js`. UI
   tests seen red first; phone screenshots.
7. **Honest states.** One UI test per row of the table above; none but the
   quiet-after-`powering_off` row, after `settle_s`, says it is safe; that row
   names the light; a reload keeps the state; a refused request (401, 403) says
   why and leaves the button usable. Live, against a real server: the phases as
   read over HTTP, with the server killed after `powering_off`, 10 of 10.
8. **The hardware button.** No code, unit or config touches it. Checked by
   reading the diff.

The push gate passes.
