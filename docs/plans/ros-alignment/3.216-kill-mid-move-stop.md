# 3.216 A robot-server death mid-move: the board stops inside the gap

*`PLAN-ros-alignment.md` section 3.216; index: [README.md](README.md).*

**Why.** 3.202.C's soak3 (`3.202-sim-chaos-soak.md`, Status, soak3; logs
in the desktop's `~/picar-runs/3202/soak3`) found a real contact. Fault 18
(K3) SIGKILLed the robot server 0.3 s into a 0.3 m/s FORWARD with 34.7 cm of
true gap. With no veto left, the fake board (`sim/fake_esp32.py`, the
Rover's firmware copied from source) drove on until its heartbeat zeroed
the wheels, 1.54 s after the kill; the car hit the wall at 1.06 s and stayed
pinned. The host sets that heartbeat to 1.5 s (`HEARTBEAT_MS`,
`robot/hardware_robot.py`), chosen to sit above the robot server's 1 s
watchdog. At 0.3 m/s, 1.5 s is 45 cm of blind travel against a 20 cm bar,
and the real Rover would do the same: the heartbeat is the board's only
stop of its own (CLAUDE.md 3c). The user, 2026-11-25: "fix first, then
re-run" (re-running 3.202's soak is 3.202's, after this merges).

**What the heartbeat and the watchdog each watch.** They guard different
links. The watchdog (B3.1, 1.0 s) watches the link from the brain to the
robot server; while the server lives it re-sends the standing command
every 50 ms wheel period, so the board keeps hearing it. The heartbeat
watches the link from the robot server to the board, and acts only when the
server is gone (dead, hung, or the line cut). "Above the watchdog so that
one acts first" orders two guards that never race: a brain silence never
starves the board.

**Candidates** (the orchestrator's brief):
* (a) a shorter heartbeat. The firmware already takes it at run time
  (`T:136`, `CMD_HEART_BEAT_SET`, which the fake board copies), so this is
  a host constant, not a firmware change: nothing to flash.
* (b) the stop distance tied to that blind time: the vet's reaction term
  (`T_REACT_S`, `robot/safety.py`) covers the heartbeat plus one wheel
  period, so speed x (heartbeat + period) + braking fits the room the vet
  keeps.
* (c) anything else the firmware offers, such as a command with its own
  expiry.

**Criteria (written before building or measuring; CLAUDE.md section 7).**
Thresholds in metres and seconds. Safety is judged on ground truth only:
the body's `gap_cm`, `tests/footprint_sweep.py`'s geometry, which shares
no code with the vet.

1. **G, the primary bar (ground truth):** `evaluations/kill-stop-3216/sweep.py`
   on 3.135's split stack (the shipped robot server and the fake board on a
   pty, the fake D500, no brain), the robot server SIGKILLed as 3.202's K3
   kills it. Grid: FORWARD and REVERSE; verbs at speed 25, 50, 75 and 100
   (0.15-0.60 m/s, every verb speed the server allows) and a standing
   `/wheels` command at 1.0 m/s (`/wheels` has no linear cap below the
   board's 2.0 m/s window); start gaps of the shipped bar plus 5, 20 and 45 cm;
   the kill at 0.1, 0.5, 0.8, 0.95 and 1.1 of the time to cover that extra:
   150 runs. **Bar: in every judged run, the least true gap after the kill
   is >= 3.0 cm** (no contact by footprint_sweep's 1 cm G bar, with 2 cm
   to spare). A run whose board was not driving at the kill is void; **at
   most 25 % void** (the 1.1 kills land at or past the line, where the vet may already have stopped the robot), or the sweep did not test the kill.
   *Why 3 cm and not 20.* The 20 cm bar is the live veto's stopping room
   for a robot whose veto is alive. It budgets reaction, braking and the
   lidar's age. A server death is a fault with no veto, and its bar is no
   contact, with the margin the project already lets a deliberate move end
   at: `CREEP_MARGIN_CM`, 3 cm. Asking the full 20 cm after a death would
   add the whole blind distance on top of the live bar, at every speed and
   at every moment. That is criterion 3's progress, spent on a fault.
2. **B, braking, on paper until 6.9(d):** the fake board's PID is ideal (it
   stops the instant its setpoint drops), so the sim cannot judge braking.
   A test pins, for every v from 0.01 to 2.00 m/s in 0.01 steps:
   `required_clearance_cm(v) >= 3 + 100 x (v x (heartbeat + 0.05 s) +
   v^2 / (2 x DECEL_M_S2))`, with braking at its 0.5 m/s^2 placeholder.
   It must fail on today's code (at 0.6 m/s, 48 cm against 132 cm with the 1.5 s heartbeat). It is
   re-checked against the measured deceleration on a working Rover board.
3. **P, progress (a fix must not win by crawling):**
   * (P1, in process) 3.22's verb sweep (`tests/verb_sweep.py`, three
     houses, speeds 50 and 100): the straight verbs' total distance driven
     is **>= 97 %** of the shipped code's on the same seeds, with its own
     bars still met (0 contacts, 0 under 18 cm).
   * (P2, the real path) three frontier missions on `scaled_house` through
     the brain's HTTP API on 3.135's stack, before and after: **found count
     no lower, and median mission time no more than 15 % longer**.
4. **C, cadence (the heartbeat never trips on a live server):** across the
   sweep's runs and P2's missions, from the board's own log of every `T:1`
   (`kill_body.py`): **the longest gap between two `T:1` sends while the
   command is non-zero and the server lives is <= half the heartbeat**,
   and the board never zeroes a moving setpoint while the server lives.
5. **R, the rules:** no new movement path and no write to the serial line
   outside `HardwareRobot`'s existing sends (rule 4; `tests/test_wall_linters.py`
   passes); the watchdog stays 1.0 s and watches the brain; the heartbeat
   watches the robot server, at least 4 wheel periods long; both roles are
   written apart in the safety and motor-board specs, which change in the
   same commit as the code.

A failed candidate is recorded as failed. An amendment to a criterion is
written here before the run it affects.
