# 3.153 The camera frame read under an OOM squeeze: a mission failed on GET /frame 503

*`PLAN-ros-alignment.md` section 3.153; index: [README.md](README.md).*

**Why.** Found by 3.152.B's first crash-loop run (d30, 2026-11-04 21:43-22:00
on the board, rev `9dfc6d63`; records in
`evaluations/local-vlm-3152/board/d30-20261104-2132/` on branch
`plan/3.152-local-vlm-down`). The run is a VE OOM crash loop beside 3.135.C's
live stack (`Soak`):
* a hog holding 3,392 MB at `oom_score_adj` 100;
* 7 VE kills, every one VE's;
* `MemAvailable` down to 20 MB at the kills.

Mission m000 (`home_first_floor`, red backpack, tiered) ended `failed` at step
12. Its end reason was `step failed: GET /frame -> HTTP 503:
{"detail":"timed out"}`, raised in `control/mission_runner.py`
`get_camera_frame` through `RemoteRobot`. The mission ended 687 s into the
window, 4 s after VE's kill at 683 s, so the squeeze around a kill stalled the
robot server's frame read past its deadline.

Every check 3.152.B makes of the stack held through it:
* the robot server and the brain answered `/health` on all 810 samples;
* no process but VE was killed;
* the wheel loop ran 0 late ticks in that mission (the run's 4 were in a
  later mission, m002, max 0.235 s).

So a camera read that times out once in a memory squeeze is enough to end a
mission as `failed`, and no health bar sees it. On the car the camera is
`robot/camera_stream.py` (3.90 A: newest frame, stale -> 503), not the sim's
frame. Which path stalled here, and whether one 503 should fail a mission
under B3.2's budget, is this section's to find (the orchestrating session,
2026-11-04: criteria left to this section's session).

**Found before the criteria (2026-11-05, from the code):** the 503's text,
`timed out`, is the backend's own exception passed through the robot
server's `/frame` route (`robot/server.py`: any exception -> 503 with its
message). In the soak's split-body simulator `get_camera_frame` is
`sim/body_client.py`'s HTTP read of the sensor program, `FRAME_TIMEOUT_S`
3 s, so the sensor program stalled in the squeeze and the read timed out.
`RemoteRobot` raises any HTTP error as `RobotTransportError`, and
`MissionRunner._tick`'s catch-all ends the mission `failed` on the first one:
B3.2's consecutive-failure budget covers only the vision path
(`VisionUnavailable`). On the car the frame is `robot/camera_stream.py`'s
(stale -> 503), which a squeeze or a USB hiccup can make answer 503 once
just the same.

**Criteria (written before building; CLAUDE.md section 7):**

1. **A camera read that fails is a transient fault with a budget.** A
   frame read through the mission's robot gate that raises is
   `CameraUnavailable`; the tick that met it takes no further action, and the
   mission continues. `DEFAULT_MAX_CAMERA_FAILURES` (3) consecutive such
   ticks end it `failed`, its reason naming the camera and the last error; a
   tick that completes resets the count; `status.camera_failures` reports it.
   Every other robot error still ends the mission at once (as today), and a
   Stop, a preemption or a halt during a failed read are unchanged. Pinned
   red first in process: one failed read mid-mission today ends `failed`.
2. **In process:** a sweep of explore and tiered missions with one failed
   frame read injected at a random tick ends with the same outcome as the
   same mission without it (all of them); a camera that never comes back ends
   `failed` after exactly 3 consecutive failed ticks, the robot never moved by
   a failed tick.
3. **Live, the desktop's split-body stack** (3.135's `stack.py`, sim mode, the
   desktop lock): one tiered find mission through the brain's HTTP API, the
   sensor programs stopped (`SIGSTOP`) for 4 s mid-mission -- the cause
   itself, past the 3 s frame read -- then resumed: the mission does not end
   `failed` on it (the status shows `camera_failures` rose and reset), and
   ends as an unperturbed mission does. No board needed.
4. The suite passes; `/code-review` and the Thermos pass (the mission loop
   is risky), at most two rounds.
