# 3.211 nav2's NavFn A* fails to extract plans: the trip home aborts

*`PLAN-ros-alignment.md` section 3.211; index: [README.md](README.md).*

**Why.** 3.70.M3's live find (`evaluations/find-last-seen-370/live-m3.jsonl`)
ended with the trip home `failed: nav2_aborted`. `ReturnTrip._driving`
(`brain/dock.py`) saw nav2 abort the staging goal twice, then the dock goal
twice. 3.205's live run 2 failed the same way after a 939 s find. 3.198 fixed
the final approach, which this return never reached, so this is a different
failure. Opened by a trace worker for the orchestrator, 2026-11-21.

## The trace (2026-11-21, before anything is built)

**The recorded data cannot answer it.** M3's brain and ROS logs did not
survive its session (3.204 says so too); the row keeps only
`ret: {failed, nav2_aborted}`. What the records do show:

* **Long finds are where it happens.** Returns failed after M3's find
  (1078 s, 40 goals) and 3.205's run 2 (939 s, 33 goals). Every short live
  find docked: M2 live k 0-2 and k 4.
* **The end pose does not decide it.** 3.205's run 1 docked from
  (16.8, 5.1); its run 2 aborted from (16.7, 5.3).
* **The `nav2_starting` refusal does not decide it.** M2 live k 0 was refused
  the same way and docked.

**A reproduction** (this worker, the cloud container, 4 cores; a trace, not a
measurement: load max 5.06, 18 of 295 samples over 4). It used
`stale.py live` on `vision-picar-ros:trace-plan-3.70`, built from `dev`
`f8fa8ef9` by `build-cloud.sh`, with a side tracer of truth, `/world/pose`
and `/world/goal` every 2 s. The survey ended `out_of_budget` 1750 s
(`map-3859d4ac`, 57 reported); the reload `matched`. The find ended
`out_of_budget` 1162 s (29 goals). The return **docked** (0.020 m). **The
abort did not reproduce in one try**, which fits about 2 in 3 long finds.
What the logs show:

* **The pose was not lost.** Pose against truth had a largest error of
  **0.056 m** over 1,205 samples, survey and find. 3.204's inferred
  mis-localisation did not occur here.
* **nav2's planner failed 57 times**: 30 in the survey, 27 in the find. **All
  57 were the same NavFn error:** `Failed to create a plan from potential
  when a legal potential was found. This shouldn't happen.`, followed by
  `GridBased: failed to create plan with tolerance 0.10`. No failure was a
  start or goal in lethal cost, and none was off the map.
* **The find's first goal, the recall, took 6 of these failures**
  (1795276388-421 s) and survived by luck. It is the same goal M3 lost
  ("aborted after 0.3 m and 18.6 s").
* **Why such failures abort a goal.** Humble's default
  `navigate_to_pose_w_replanning_and_recovery.xml` replans at 1 Hz inside a
  `RecoveryNode number_of_retries="6"`. Each planning failure that survives
  one costmap clear fails the pipeline once, and the goal aborts on the
  seventh. Its success while following does not reset the count. A long goal
  replans many times, so it is the goal most exposed. A trip home across the
  house is one; so is a far recall.
* **Keepout marks** (`robot/wedge_watch.py`): 7 in the survey, 0 in the find.
  None was live at the return. They stay a second suspect, not ruled out,
  because they stay live through a return (`mission_runner` clears them at the
  mission's end).
* **Elsewhere:** the same error appears in 14 of the Jetson FMEA ROS logs
  (`evaluations/jetson-fmea-3135/`): 17 of their 69 planning failures.

**The cause, as far as it is shown.** nav2 is configured with
`nav2_navfn_planner/NavfnPlanner` and `use_astar: true` (`nav2.yaml`). On this
stack, that planner often fails to trace a path through a potential field it
has just computed. Enough failures in one goal abort it. **Inferred, not
traced for M3** (its logs are gone): M3's four aborts are this mechanism. Each
back-off between `ReturnTrip`'s tries moves the robot about 9 cm, so the
same start and goal geometry keeps failing. A1 below decides whether the
mechanism is real at a measurable rate. If it is not, this section stops and
reports.

**The candidate fix:** `use_astar: false`, NavFn's Dijkstra expansion.
A partial A* field is the usual reason gradient descent finds no path through
it. The change is inside `service/slam/` (CLAUDE.md rule 3). No safety or
brain code changes. A different planner (Smac 2D) is the fallback if A2 fails.

## 3.211.C: the path shape on `scaled_house` (opened 2026-11-23)

**Method, written before any run.**
* **The instrument is R6's** (`tests/demo_nav_goals.py`, 3.15): a fresh
  stack, the scripted mapping lap, the six `SCALED_GOALS` in order, the
  unreachable goal, the D-pad tap. Ground truth at 5 Hz.
* **One addition, beside it:** for each goal, the first non-empty plan the
  bridge reports (`GET /world/goal`'s `plan`, the global planner's path from
  where the goal started), scored on the simulator's truth: its length, and
  the least and median distance from a plan point to a wall or object
  surface (`clearance_m`). Rows keep these numbers, not the points.
* **Two arms on one image,** `vision-picar-ros:plan-3.211`, built from this
  branch (its `service/slam/` is `dev`'s). **F** runs the image's own
  `nav2.yaml` (`use_astar: false`). **T** mounts a copy that differs only in
  `use_astar: true` (3.211.A's way). `demo_explore.stack()` starts each run
  fresh (`SIM_MAP=scaled_house`, `PICAR_ROS_NETWORK=host`) and takes the
  desktop's exclusive lock.
* **Three runs per arm, interleaved** T, F, T, F, T, F, so a drift of the
  desktop falls on both arms.
* **Load:** the 1-minute load average is sampled every 10 s through each
  run. A run whose largest sample is above 4 is invalid for C3 and C5's time
  (3.79) and is repeated once; if the repeat is invalid too, it is recorded
  invalid and those bars are judged on the valid runs. Fewer than two valid
  runs in an arm: that bar is **not judged**, not met.
* **Logs:** `PICAR_KEEP_LOGS` (3.212) keeps every run's robot, brain and ROS
  logs locally.

**Criteria (written before any run; CLAUDE.md section 7).** "Every F run"
means each of F's runs on its own; T's numbers are the reference.

|---|---|---|
